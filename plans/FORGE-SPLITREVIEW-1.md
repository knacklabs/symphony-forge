# After a conflict, close reviews only the conflict fix, and plans keep task files apart

2 parts · Risks: none one-way · New moving parts: none

## What changes for you

- After a task brings in main and fixes a conflict, close reviews only the lines that resolved the conflict, keeps the earlier clean review, and still runs all tests in full. A merge with no conflict needs no new review. Today that holds only when the task's own diff stays the same; after this change it holds for every merge without a conflict.
- The planner searches the code for each task's Scope before writing it, and the plan check refuses two tasks whose Scopes can touch the same file unless one waits for the other through After. Shared names go to the first task or to a small last wiring task.
- New client repos get both at init. Existing client repos get both on upgrade, and a story already in flight gets the refusal at its next plan check, with a plain next step.

## Why

Close reuses an earlier review only when the whole branch diff is unchanged. A task that fixes a conflict after another task merged gets a full new review, and so does a task whose merge with main was clean but touched a file the task also changed, because the saved diff fingerprint holds file versions. Each full review takes time. Task start checks file overlap only against started tasks, and with stacking on by default an overlapping task is usually stacked, not refused, so plans with shared files reach building and cause the conflicts. The worker brief also allows edits outside Scope, so some conflicts come from files no Scope check can see. Forge already needs Git 2.38 or newer for git merge-tree, which also has git show --remerge-diff, so the review step adds no new Git minimum.

## Done when

1. **A task that merges main with a conflict is reviewed only on its conflict fix, and its tests still run in full.**
2. **A plan with two tasks whose Scopes can touch the same file, and no After link between them, is refused before approval, and the refusal names both tasks.**
3. **Stories already in flight get that refusal at their next plan check with a plain next step; new and existing client repos both get both changes.**

## Risks

<!-- Each one-way step: deleting data, a destructive migration, a new vendor. -->

Risks: none one-way. Each part reverts with its pull request. No data is deleted and no setting is added.

Trade-off: after a merge, the model looks only at the lines that fix a conflict, and at nothing when the merge had no conflict. It can miss a bad mix of main's new code and the task's own code when Git merges the text without a conflict, for example main renames a function that the task calls. The full tests that close still runs on the merged code are the guard for that case. (Source: your decision, 6 Nov 2026)

Trade-off: the plan check compares Scope entries by their start, up to the first wildcard. A broad folder such as `src/forge/` in one task and a file under it in another counts as the same file, so the plan is refused until one task waits for the other. By the planner's count, 13 of the 72 plans on main with two or more tasks would be refused today if they were read again. The way out is to name files, add After, or move shared names to the first task. A story that is already approved is not checked again, so its lead can still add a shared file below `## For the builders` without a new approval. (Source: your decision, 6 Nov 2026)

Trade-off: a clean merge where main and the task changed the same lines the same way no longer gets a new review. An existing test pins a new review for that case, and this part changes the test. The planner chose this because the merge is clean and the model already reviewed the task's own change. The owner can choose to keep the review for that one case.

### Done-when details

1. Conflict-only review.
   - Meaning of "conflict lines". Let R be the commit of the last clean review and M the newest default-branch commit that the head contains (`git merge-base origin/<default> HEAD`, the same ancestor `fingerprint` uses). The conflict lines are the lines where the head differs from what Git's own merge of R and M gives, outside Forge's records (`review.BOOKKEEPING`). For one merge this is exactly `git show --remerge-diff` of that merge. For several merges since R, one merge of R with M covers them all, so the model reads one diff, not one per merge. Merges with no conflict add nothing. Any later edit by the worker also differs from Git's merge, so it is reviewed too, which is right because nobody reviewed it. Git's merge itself is `git merge-tree --write-tree R M`; with a conflict it writes the tree with conflict markers and exits 1, and `close.py:699` already treats exit codes 0 and 1 as normal.
   - Which diff the model gets. A new module `src/forge/merge_review.py` builds a base commit whose tree is Git's merge, with R as parent, with the records paths set to the head's files. In the review clone, `review.run` checks out a snapshot of the head's files on top of that base and passes the base to Autoreview, as the sign-off branch does. A fix to lines outside the earlier reviewed diff, for example a caller changed to match a rename from main, is part of the head's difference from Git's merge, so the model sees it and nothing else. It reads other code as context. A blocking finding on these lines blocks close as any finding does, and a later close repeats the repair review from the new review commit.
   - When it applies. All of these hold: a review is recorded with no blocking finding; its commit R is an ancestor of the head; the default branch's commit M is an ancestor of the head and is not an ancestor of R (main moved into the branch since R); the item is not stacked on an unmerged task (`review_ref` does not start with `forge-stack/`, and `stacked_on` is empty); close did not replay the branch; for a task, `plans/<KEY>.md` is the same at R and at the head, because the story doc is part of what a review read. Otherwise nothing changes: today's reuse for an unchanged branch diff and today's full review.
   - Close. In `close.py:303`, the `fresh` expression also becomes true when the difference described above is empty (a clean merge with no later edit). Close then records the new fingerprints through the existing `refreshed` path (`close.py:311-314`), so the pull-request check (`prcheck.py:404`) and `forge next` (`nextstep.py:651`) see a current review. When the difference is not empty, the review runs with the conflict-lines base and a new block in `templates/review.md` (`conflict-review`, in place of `repair-review`): "This merge brought in the default branch; earlier lines were reviewed clean at <commit>; review only these lines; a P1 or worse problem in them is a finding". The tests run in full on both paths, as today.
   - Tests. `test_1` in `tests/test_splitreview_close.py`, with `client(env, previous)` for a new repo and an adopted one. (a) Main changes a distant line of a file the task also changed: close merges, the review count stays at 1, and the tests run. (b) Main and the task change the same line: close refuses with the conflict message, the test resolves and commits the merge, close runs again: two reviews in all, the stub's recorded diff (extend `tests/stubs/autoreview` to record `git diff --name-only` of its `--base`) names only the file where the conflict was fixed, and the prompt holds the conflict-review text and not the repair text. (c) The same as (b) with two merges since the review (a clean one, then a conflict one): one review, one diff. (d) The conflict fix also edits a second file that the task never touched: the diff names both files. (e) A blocked conflict review refuses close as any blocked review does. (f) A task whose previous review had an open finding keeps today's repair review. `test_2` of the existing file changes to expect one review.
   - Size. The review part is about 90 lines of code (the new module about 65, the hooks in `review.py` about 8, one line in `close.py`) plus about 12 lines in `review.md`, and tests. Score against the budget: F 3 (every story with parallel tasks meets main moving), H 2 (the full review is a slow step; principle 10), C 2 (up to 150 lines, no new model call). 3 x 2 = 6, at least 2 x 2 = 4. It passes.

For every two rows, it refuses when some Scope entry of one `_overlap`s some Scope entry of the other (import `task._overlap` with the usual `# pyright: ignore[reportPrivateUsage]`) and neither task reaches the other through After, directly or through a chain of After entries inside this story (an After entry that names another story's task is not a chain). ### New and existing repos

- New repos (`forge init`, adoption): the new texts through the synced guide, the story template and the brief; the new code from the first story. A first story that shares a file between tasks is refused at its first read.
- Existing repos (upgrade, then `forge sync`): the same texts. Code arrives with the Forge release. Stories already approved are not blocked at task start or by `forge next`. Stories in planning meet the refusal at the next read or approval. No file in the app changes.
