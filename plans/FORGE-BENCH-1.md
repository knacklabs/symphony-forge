# Score each Forge release on the same reference app

2 parts · Risks: none one-way · New moving parts: none

## What changes for you

- After a Forge release is tagged, your agent builds one small app from the same fixed notes about a made-up business. Claude builds it inside your agent's own Claude Code session, on your laptop, for the length of one app build. Your Claude plan pays. Nothing runs on GitHub, nothing is added to GitHub, and a pull request never starts this run.
- The app gets a score from checks that use no AI model. The checks ask: does the app build, do its own tests pass, how many design problems does the design checker find, and do sign-in, a list, a form, a dashboard and one job work in a browser or through the app's address. The score reads like "6 of 8 checks pass", with each number beside it.
- The agent shows this score next to the score of the previous scored release and says whether it went up, went down or stayed the same. It also shows the minutes the build took, and the tokens (the units a model is billed in) when the session can report them. The first run has no earlier score and says so.
- Each score is saved as one small file for its release in Forge's own repo, through a normal fix. The history of scores lives there, so the next run reads the previous score from the repo.
- Nothing starts the run on its own. After two runs you see how much the build costs and how much it loads your laptop, and you decide how often it should run.
- The run never holds a release. If the build fails, the app still gets a score, and the checks that could not run count as failed.
- Client repos get nothing. A new client repo and an existing client repo get no new file, setting or step from this story. (Source: the Forge review rules; this is a test of Forge itself, so it lives in Forge's own repo.)

Design: none (no screen; the score appears in the agent's reply and in a small file)

## Why

Nothing today shows whether a new Forge release makes the apps it builds better or worse. Forge's tests prove that Forge's own commands work. They do not build a whole app from client notes, so a release can make the apps worse and nobody sees it until a client does. Releases come often (v1.2.34 on 9 November 2026, v1.2.35 on 10 November), so a score on each release shows the direction early.

## Done when

1. **After a release, your agent builds the reference app for that release from the fixed notes, with Claude only, in a scratch folder outside the Forge repo, and scores it. The steps are in the maintainer guide. Nothing else starts it, a pull request never does, it never holds the release, and a failed build still gets a score.**
2. **The built app is scored by checks that use no model: it builds, its tests pass, the design checker's problem count, and a check for each of sign-in, a list, a form, a dashboard and one job. The result is one headline ("N of M checks pass") and the number behind each check.**
3. **The agent shows this score beside the previous scored release's score, with up, down or same, and the minutes and, when reported, the tokens the build used. The score is saved as one small file per release in Forge's repo through a normal fix. When the notes, the checks or the design checker changed since the previous score, it says "new baseline" and shows no direction.**
4. **The notes describe an invented business that needs sign-in, a list, a form, a dashboard and one job. They name no real company, and every one of the five has an expected check that finds it by role and label (the job, by its address).**
5. **A new client repo and an existing client repo get no new file, setting or step from this story.**

## Risks

Risks: none one-way. A saved score is a small file that reverts with its fix.

Trade-offs, in plain words:
- One build per release is noisy. The same release built twice can score a point apart, so a one-point change may mean nothing. The plan adds no repeat builds. If the first runs show the score moving with no release change, a later story can add repeats.
- The build runs on your laptop. It starts the app and its database in Docker for the checks, so your laptop is busier for the length of one build. The load is not measured yet. Scores can differ a little with laptop load, for example when a check times out on a busy machine.
- The build runs in a scratch folder with no GitHub pull request, so it does not run `forge close` or Forge's review. The score measures what a release ships to an app (the guide, the skills, the starter code, the rules and the design checker), not Forge's review. Review findings and review rounds are not in the score.
- The build is unattended, so Claude does not follow Forge's story flow (no approval, no pull request, no close). It uses the guide, skills, rules and starter code that the release ships, and it works in the folder without committing. A change to the flow itself (the worker brief, the review) is not measured. The builder is a normal helper of your agent's session, so nothing but its instructions keeps it inside the scratch folder.
- The job check proves that the job does its work when called. It does not prove that the app schedules it, because the made-up client runs its own scheduler and calls the app each night.
- The session may not report tokens. The score then shows "not reported" for tokens. Minutes are always shown.
- A browser check that fails on a real app looks the same as a check that is wrong. The first run is read by a person once; a check that is wrong is a bug in the benchmark, not in the release.

Model cost: on your Claude plan, and the size is unknown until the first run. One run is one Claude build session for a small app. It uses many model calls (every file read, edit and command is a turn), so it is far larger than any other Forge job. Recorded data from Forge's own repo is the only scale I have: one Codex review of the v1.2.35 release change used about 5.3 million input tokens (95 percent from cache) and 26 thousand output tokens in 10 minutes. A full app build is expected to be larger. No number is known, and Forge has no price table, so the run reports minutes and, when the session reports them, tokens. It does not turn them into money. The first run measures them, and the second shows whether the first was typical. The guide tells the agent to stop a build that runs over 120 minutes and score what exists; that number is my choice, not measured. Every other part (the checks, the score, the saved file) uses no model call. A model that looks at screenshots is left out (see Notes).

### Settled (with the reason)

1. **The score comes only from checks that use no model.** The checks, in order: (a) the app builds, (b) the app's own tests pass, (c) the design checker's problem count (pass when 0), (d) one check each for sign-in, a list, a form, a dashboard and a job (5 checks). Total 8 checks. A check that did not run counts as failed and the summary says "did not run". Reason: the owner's cost rule. The cheapest design is the first one. The headline is a plain count, with no weights, so a reader sees what moved.
2. **The expected checks are fixed Playwright specs in the Forge repo, run against the running built app.** They find things by role and label, like the shipped rule specs, and never by markup, because Forge ships no screens. The notes name each thing in the client's words (for example "a list of orders", "a New order form with a Save button", "a count of orders due today"). The specs do the action (sign in, save an order) and check the result. The made-up client runs its own scheduler, which calls `POST /api/jobs/mark-late-orders` each night as a signed-in staff member; the job check makes that call and then looks at the orders list. The app is not asked to schedule anything. The starter's own test command removes its stack when it ends, so the fixed checks cannot follow it. `benchmark/checks.toml` holds one `[app]` entry with a `start` command, a `ready` address, a `ready_timeout` in seconds (default 300) and a `stop` command, and the script runs the 5 fixed browser and job checks between start and stop, after build, tests and design checks. If `start` fails or the address does not answer within `ready_timeout`, the 5 app checks count as failed with the reason "the app did not start", `stop` still runs, and the score is still written (a startup failure is a low score, not a crash). The builder takes the real `start` and `stop` from how `scripts/test.mjs` starts the stack. The script's own test uses a small web server as the app.
3. **No `forge close`, no review and no rounds in v1.** Reason: close needs a GitHub pull request, and a story needs a person's approval through Plan Mode (`src/forge/approval.py`), so neither can run unattended. The guide's steps give the builder subagent the repo that `forge init --starter` makes (guide, skills, starter code, rules, design checker), the fixed notes, and one rule: build the app from the notes in the scratch folder, using the repo's guide, skills, rules and starter code; no person is here, so do not start stories or fixes, do not run `forge close`, do not commit, and do not wait for an approval. Forge's hooks fire only on commit, so leaving the work uncommitted avoids them; the scorer reads the working folder. Review findings, rounds and `app_baseline` results are Notes questions.
4. **Where it runs and when: the agent's own Claude Code session, by hand, after a release.** The guide's new step 5 of "Releasing Forge" (the owner decided on 11 Nov 2026: "In Claude Code") says, in order: (a) make a scratch folder outside the Forge repo with `git init` and a local bare folder as `origin`; (b) in it, run `forge init --starter react --actions no` with Forge installed from the release tag (`uvx --from git+https://github.com/knacklabs/symphony-forge@<tag> forge init ...`, the form this guide uses for an upgrade), so it scores that release and never a newer `main`; an error from the last `gh api` step after the first commit is expected and the repo is ready; (c) note the time, start one `worker` subagent in the background with the scratch folder's absolute path, the text of `benchmark/notes.md` and the rule of Settled 3; stop it after 120 minutes and score what exists (a number chosen, not measured); (d) note the time and the tokens the subagent reported; (e) run `python scripts/bench_score.py` (Settled 7); (f) commit the new file in `benchmark/results/` through a normal fix (`forge fix start ... --kind mechanical`). Nothing else starts it. No new Forge command, no workflow and no GitHub secret. A person can follow the same steps, but they are written for the agent.
5. **Claude only.** The builder is the scratch repo's own `worker` subagent, so its model is the scratch repo's `[models.build.claude]` entry: `claude-sonnet-5-5` at effort `low` today (what a new client gets), and its own helpers use `claude-haiku-5-5`. The guide names that entry and says no Fable or Astra model is used. `test_1` asserts the guide names no `fable` or `astra` model.
6. **The score's home is the repo.** The script writes one small file per release, `benchmark/results/<release>.json` (for example `v1.2.36.json`), and the agent commits it through a normal fix. The next run reads the previous score from that folder: the file with the highest release number below this one (numbers compared as numbers, so `v1.2.10` is above `v1.2.9`). One home for the fact (principle 2): a score is a fact about a release, Forge's repo already keeps release facts and their history in git, a file is reviewed with its fix, and reading it needs no GitHub call, no token and no expiry. A GitHub run artifact would expire and need a lookup. The board is not changed. The score never lives in a second place.
7. **One script, one checks file.** `scripts/bench_score.py` (Python standard library only, like `scripts/smoke_select.py`) reads `benchmark/checks.toml` (an `[app]` entry, a `baseline` list of file paths, and each check: name, command, kind `pass` or `count`), runs the commands in the built app's folder, and writes the result and the comparison. Its command line, pinned by Task SCORE: `python scripts/bench_score.py <app-dir> --checks <toml> --release <tag> --usage <json-file> --results <folder>`, with the summary text on stdout. It writes `<folder>/<release>.json` (the checks, `passed`, `total`, the baseline id and the usage) and finds the previous score in the same folder. The usage file is JSON with exactly these keys: `input_tokens` (integer or null), `output_tokens` (integer or null), `turns` (integer or null), `minutes` (number). A null prints as "not reported". The agent fills them from what the session can report (tokens and turns may be null) and from the clock for `minutes`, which is always known. Tests pass their own small checks file with simple commands, so the script needs no other test seam.
8. **A baseline id stops a false comparison.** The result holds a short id made from the bytes of the files listed in `baseline` in `benchmark/checks.toml`: `benchmark/notes.md`, `benchmark/checks.toml`, the specs, `src/forge/templates/design/ui-checks.js` and the bundled impeccable folder `src/forge/templates/skills/impeccable/`. When the previous result has another id, the summary says "new baseline" and shows no direction. Reason: a changed check, or a changed design checker, changes the score without the app getting better or worse. The cost is that a release that changes the design checker shows no direction once.
9. **The notes.** `benchmark/notes.md`: an invented business, "Breadbox Wholesale", that sells bread to local shops. Staff sign in. They see a list of orders, add an order with a form (shop, item, quantity, delivery date), see a dashboard with the number of orders due today and the number late, and the client's own scheduler calls the app each night at one address, which marks late orders. Short, in the client's words, no screens, no stack. The name is invented; the plan did not check that no real company has it, so a reviewer reads it once.
10. **What this story removes or replaces.** Nothing. It adds one script, one folder of fixed files, a folder of saved scores and one guide step, and removes no process. The only step for the people who build or close work is the agent's run after a release, started by hand. The cost is the model run and nothing else.

## Notes

- **Scores (F x H >= 2 x C).** F 2 (once per release; releases come every day or two, but the problem of a release making apps worse is not known to be that frequent), H 2 (a release can make apps worse without anyone seeing it), C 3 (a script and a checks folder of more than about 150 lines, and a large model run). 2 x 2 = 4 < 2 x 3 = 6. Below the bar. Kept because the owner asked for it. The owner chose the cheaper form on 10 and 11 Nov 2026: start it by hand, in Claude Code, with no workflow and no key. The model-free scoring keeps the cost to the one build session.
- **Decided: in Claude Code.** "In Claude Code" (owner, 11 Nov 2026): the benchmark build does not run on GitHub. The agent starts it by hand in its Claude Code session after a release. Reason given: Claude Code can do it itself, and the GitHub version needs an API-billed key and an untried setup. Earlier on 10 Nov 2026 the owner chose "by hand first" and to decide on a tag trigger after two runs; that question now reads: after two runs, decide how often to run it.
- **Later options (wording for `plans/ideas.md`, the owner's decision after two runs).**
  - Run the release score on GitHub, if laptop load is a problem. It needs a Claude key in GitHub secrets that bills per use, a workflow that starts by hand or on a release tag, Forge and the pinned Claude SDK installed on the runner, and a Claude-only `forge.toml`. The score file in the repo stays the one home, so the script and the checks are reused as they are. The first design of this plan (a by-hand workflow with a required release input, a result artifact and a read of the previous run) is in the git history of this plan file.
  - Run it on every release tag.
- **Open question: a model that judges screenshots.** Optional, adds a model call per screen and a second source of noise. Recommended answer: no. The browser checks and the design checker already look at the rendered pages.
- **Open question: review findings and rounds.** The score leaves them out because they need `forge close`, which needs a GitHub pull request, and a story needs a person's approval. A scratch GitHub repo per run would allow them, but needs a token that can create and delete repos and adds a second model cost. Recommended answer: leave them out of v1; ask again after two runs.
- **Earlier read rounds.** Rounds 1 to 3 read the GitHub design; their dispositions are in `plans/FORGE-BENCH-1.read.md`. The findings that still apply are kept: no story flow (Settled 3), the app is started for the fixed checks and a failed start still scores (Settled 2), the design checker is in the baseline id (Settled 8), the job check proves the work and not the schedule (Settled 2), and fixed usage keys (Settled 7). The findings about the workflow, the Claude key, the runner setup, the previous-run lookup and the `GH_TOKEN` no longer apply. A new read follows.
- **Not verified.** (1) That `forge init --starter` finishes in a scratch folder with a local bare remote on the laptop, and that only its last `gh api` step fails. (2) That a `worker` subagent started from the coordinator's session can work in a folder outside the repo, and what token numbers its completion report gives.
