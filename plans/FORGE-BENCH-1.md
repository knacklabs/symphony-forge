# Score each Forge release on the same reference app

2 parts · Risks: none one-way · New moving parts: one release workflow, one Claude access key

## What changes for you

- After a Forge release is tagged, your agent starts one run by hand and names the release to score. GitHub's own computers (called CI) build one small app from the same fixed notes about a made-up business. Claude builds it. Your laptop does nothing, and a pull request never starts this run.
- The app gets a score from checks that use no AI model. The checks ask: does the app build, do its own tests pass, how many design problems does the design checker find, and do sign-in, a list, a form, a dashboard and one job work in a browser or through the app's address. The score reads like "6 of 8 checks pass", with each number beside it.
- The run's summary page shows this score next to the score of the previous scored release and says whether it went up, went down or stayed the same. It also shows how many tokens (the units a model is billed in) and how many minutes the build used. The first run has no earlier score and says so.
- Nothing starts the run on its own yet. After two runs you see the real cost and decide whether it should run on every release tag.
- The run never holds a release. It starts after the tag. If it fails, or the access key is missing, it says so and stops.
- You do one thing: add a Claude access key to the Forge repo's secrets on GitHub. Without it, the run prints a notice and does nothing.
- Client repos get nothing. A new client repo and an existing client repo get no new file, setting or step from this story. (Source: the Forge review rules; this is a test of Forge itself, so it lives in Forge's own repo.)

Design: none (no screen; the score appears on GitHub's own run summary page)

## Why

Nothing today shows whether a new Forge release makes the apps it builds better or worse. Forge's tests prove that Forge's own commands work. They do not build a whole app from client notes, so a release can make the apps worse and nobody sees it until a client does. Releases come often (v1.2.34 on 9 November 2026, v1.2.35 on 10 November), so a score on each release shows the direction early.

## Done when

1. **After a release, one run that a person or an agent starts by hand names the release to score. It builds the reference app for that release on GitHub's computers from the fixed notes, with Claude only. Nothing else starts it, and a pull request never does. It never holds the release, and with no key or a failed build it says so and ends.**
2. **The built app is scored by checks that use no model: it builds, its tests pass, the design checker's problem count, and a check for each of sign-in, a list, a form, a dashboard and one job. The result is one headline ("N of M checks pass") and the number behind each check.**
3. **The run's summary shows this score beside the previous scored release's score, with up, down or same, and the tokens and minutes the build used. When the notes, the checks or the design checker changed since the previous run, it says "new baseline" and shows no direction.**
4. **The notes describe an invented business that needs sign-in, a list, a form, a dashboard and one job. They name no real company, and every one of the five has an expected check that finds it by role and label (the job, by its address).**
5. **A new client repo and an existing client repo get no new file, setting or step from this story.**

## Risks

Risks: none one-way. The key can be deleted from GitHub's secrets at any time, and the workflow reverts with its pull request.

Trade-offs, in plain words:
- One build per release is noisy. The same release built twice can score a point apart, so a one-point change may mean nothing. The plan adds no repeat builds. If the first runs show the score moving with no release change, a later story can add repeats.
- The build runs in a scratch repo with no GitHub pull request, so it does not run `forge close` or Forge's review. The score measures what a release ships to an app (the guide, the skills, the starter code, the rules and the design checker), not Forge's review. Review findings and review rounds are not in the score. Adding them needs a scratch GitHub repo and a token that can create and delete repos; that is a later choice.
- The build is unattended, so Claude does not follow Forge's story flow (no approval, no pull request, no close). It uses the guide, skills, rules and starter code that the release ships, and it works in the folder without committing. A change to the flow itself (the worker brief, the review) is not measured.
- The job check proves that the job does its work when called. It does not prove that the app schedules it, because the made-up client runs its own scheduler and calls the app each night.
- The run needs a Claude access key that does not exist yet. Until you add it, nothing is scored.
- A browser check that fails on a real app looks the same as a check that is wrong. The first run is read by a person once; a check that is wrong is a bug in the benchmark, not in the release.

Model cost: unknown until the first run; this is the main cost of the story. One run is one Claude build session for a small app. It uses many model calls (every file read, edit and command is a turn), so it costs far more than any other Forge CI job. Recorded data from Forge's own repo is the only scale I have: one Codex review of the v1.2.35 release change used about 5.3 million input tokens (95 percent from cache) and 26 thousand output tokens in 10 minutes. A full app build is expected to be larger. No number is known, and Forge has no price table, so the run reports tokens, turns and minutes. It does not turn them into money. The first by-hand run measures them, and the second shows whether the first was typical. The job has a hard time limit of 120 minutes, a number I chose and did not measure. Every other part (the checks, the score, the summary) uses no model call. A model that looks at screenshots is left out (see Notes).

### Settled (with the reason)

1. **The score comes only from checks that use no model.** The checks, in order: (a) the app builds, (b) the app's own tests pass, (c) the design checker's problem count (pass when 0), (d) one check each for sign-in, a list, a form, a dashboard and a job (5 checks). Total 8 checks. A check that did not run counts as failed and the summary says "did not run". Reason: the owner's cost rule. The cheapest design is the first one. The headline is a plain count, with no weights, so a reader sees what moved.
2. **The expected checks are fixed Playwright specs in the Forge repo, run against the running built app.** They find things by role and label, like the shipped rule specs, and never by markup, because Forge ships no screens. The notes name each thing in the client's words (for example "a list of orders", "a New order form with a Save button", "a count of orders due today"). The specs do the action (sign in, save an order) and check the result. The made-up client runs its own scheduler, which calls `POST /api/jobs/mark-late-orders` each night as a signed-in staff member; the job check makes that call and then looks at the orders list. The app is not asked to schedule anything. The starter's own test command removes its stack when it ends, so the fixed checks cannot follow it. `benchmark/checks.toml` holds one `[app]` entry with a `start` command, a `ready` address, a `ready_timeout` in seconds (default 300) and a `stop` command, and the script runs the 5 fixed browser and job checks between start and stop, after build, tests and design checks. If `start` fails or the address does not answer within `ready_timeout`, the 5 app checks count as failed with the reason "the app did not start", `stop` still runs, and the score is still written (a startup failure is a low score, not a crash). The builder takes the real `start` and `stop` from how `scripts/test.mjs` starts the stack. The script's own test uses a small web server as the app.
3. **No `forge close`, no review and no rounds in v1.** Reason: close needs a GitHub pull request, and a story needs a person's approval through Plan Mode (`src/forge/approval.py`), so neither can run unattended. A scratch GitHub repo with a repo-create token would add a vendor secret and a second cost. The harness gives the Claude session the repo that `forge init --starter` makes (guide, skills, starter code, rules, design checker), the fixed notes, and one instruction: build the app from the notes in the working folder, using the repo's guide, skills, rules and starter code; there is no person to ask, so do not run `forge start`, `forge fix`, `forge story` or `forge close`, do not commit, and do not wait for an approval. Forge's hooks fire only on commit, so leaving the work uncommitted avoids them; the scorer reads the working folder. The Claude run is one turn of the pinned SDK driver (`claude_turn.py`). The workflow installs exactly this for a Claude-only build, and runs no `forge doctor`: Node 24, uv and Python 3.11 (as `starter-smoke.yml` does), Forge from the named release tag, and the pinned Claude Agent SDK by the same one-line call that `codex-smoke.yml` uses for the Codex SDK (`from forge import claude_sdk; claude_sdk.install()`). After `forge init`, the workflow writes `tools = "claude"` and `workers = "claude"` into the scratch repo's `forge.toml`, because init sets them only when it detects a Claude login and no Codex login. `forge doctor` would otherwise report the missing Codex login and stop, and it installs the Claude SDK only when Codex is also installed (`src/forge/doctor.py`, `needs_claude_sdk`). Nothing the build needs comes from a Codex install, a Codex login or `OPENAI_API_KEY`. If `claude_sdk.sdk_problem()` is not empty after the install, the run prints a notice and ends. The SDK wheel carrying its own Claude program is NOT verified; the first live run shows it. Review findings, rounds and `app_baseline` results are Notes questions.
4. **Where it runs and when.** A new workflow `.github/workflows/release-bench.yml` on GitHub's Ubuntu computers. The only trigger is `workflow_dispatch`, with one required input, `release` (a release tag such as `v1.2.36`). No tag trigger and no `pull_request` trigger (the owner decided on 10 Nov 2026 to start by hand; see Notes). The job checks out that tag and installs Forge from the same tag (`uvx --from git+https://github.com/knacklabs/symphony-forge@<release> forge init ...`, the form `docs/guide.md` uses for an upgrade), so it scores that release and never a newer `main`. The script's `--release` is that input. A manual run must start from a workflow that `main` holds; the workflow file in `main` is the one that runs, and it scores any tag named. It is not a required check and nothing waits for it. `timeout-minutes: 120`, with the number chosen, not measured. Without the key secret it prints a notice and skips, as `codex-smoke.yml` does.
5. **Claude only.** The session uses the model in the new repo's own `[models.build.claude]` (what a new client gets). The workflow names no Fable or Astra model. A test asserts that.
6. **The score's home is the run.** The score script writes one result file, saved with the run as a workflow artifact, and writes the comparison text to the run summary (`GITHUB_STEP_SUMMARY`). The next run lists `gh run list --workflow release-bench.yml --status success`, newest first (every run of this workflow is a by-hand run), and takes the first run that has a saved result file (an unexpired artifact named `bench-result`, read with `gh api repos/{owner}/{repo}/actions/runs/<id>/artifacts`), then `gh run download` for that run. A run that skipped for want of the key, or failed before scoring, saved no file, so it is passed over and the next older run is used. With no such run, `--previous` is left out and the summary says there is no earlier score; a missing lookup never fails the job. The summary names the release it scored. The lookup step sets `GH_TOKEN: ${{ github.token }}` for the GitHub command line, and the job has `actions: read`, as `forge-next.yml` does. No new file in the repo and no new record format beyond the one result file. The board is not changed. Adding the line to the GitHub release notes is a Notes question.
7. **One script, one checks file.** `scripts/bench_score.py` (Python standard library only, like `scripts/smoke_select.py`) reads `benchmark/checks.toml` (an `[app]` entry, a `baseline` list of file paths, and each check: name, command, kind `pass` or `count`), runs the commands in the built app's folder, and writes the result and the comparison. Its command line, pinned by Task SCORE: `python scripts/bench_score.py <app-dir> --checks <toml> --release <tag> --usage <json-file> [--previous <result-file>] --out <result-file>`, with the summary text on stdout. The usage file is JSON with exactly these keys: `input_tokens` (integer or null), `output_tokens` (integer or null), `turns` (integer or null), `minutes` (number). A null prints as "not reported". The workflow fills them from the final `result` event of the Claude turn (`num_turns` is read in `src/forge/worker.py`; the `usage` field names are NOT verified here and the builder checks them against a real result event) and from the job clock for `minutes`. Tests pass their own small checks file with simple commands, so the script needs no other test seam.
8. **A baseline id stops a false comparison.** The result holds a short id made from the bytes of the files listed in `baseline` in `benchmark/checks.toml`: `benchmark/notes.md`, `benchmark/checks.toml`, the specs, `src/forge/templates/design/ui-checks.js` and the bundled impeccable folder `src/forge/templates/skills/impeccable/`. When the previous result has another id, the summary says "new baseline" and shows no direction. Reason: a changed check, or a changed design checker, changes the score without the app getting better or worse. The cost is that a release that changes the design checker shows no direction once.
9. **The notes.** `benchmark/notes.md`: an invented business, "Breadbox Wholesale", that sells bread to local shops. Staff sign in. They see a list of orders, add an order with a form (shop, item, quantity, delivery date), see a dashboard with the number of orders due today and the number late, and the client's own scheduler calls the app each night at one address, which marks late orders. Short, in the client's words, no screens, no stack. The name is invented; the plan did not check that no real company has it, so a reviewer reads it once.
10. **What this story removes or replaces.** Nothing. It adds one workflow, one script and one folder of fixed files and removes no process. It adds no step for the people who build or close work. The cost is the model run and nothing else.

## Notes

- **Scores (F x H >= 2 x C).** F 2 (once per release; releases come every day or two, but the problem of a release making apps worse is not known to be that frequent), H 2 (a release can make apps worse without anyone seeing it), C 3 (a new workflow and job, a secret, and a large model run). 2 x 2 = 4 < 2 x 3 = 6. Below the bar. Kept because you asked for it. The owner chose the cheaper form on 10 Nov 2026: start it by hand. The model-free scoring keeps the cost to the one build session.
- **Open question: where you look.** The plan puts the score on the run's summary page. Alternative: also add the same text to the GitHub release notes for the tag with one `gh release edit` call, because `releases.dates` already reads GitHub releases. Recommended answer: run summary only for now; add the release-notes line after you have read two scores.
- **Open question: a model that judges screenshots.** Optional, adds a model call per screen and a second source of noise. Recommended answer: no. The browser checks and the design checker already look at the rendered pages.
- **Open question: review findings and rounds.** The score leaves them out because they need `forge close`, which needs a GitHub pull request, and a story needs a person's approval. A scratch GitHub repo per run would allow them, but needs a token that can create and delete repos and adds a second model cost. Recommended answer: leave them out of v1; ask again after two runs.
- **Open question: the Claude access key.** Someone must add it as a repo secret before the first run.
