# Faster checks and CI for client repos

2 parts · Risks: none one-way; four accepted limits · New moving parts: Oxlint with its type-aware add-on, Nx's Oxlint plugin and the landmines testing rules in place of ESLint; TypeScript 6 kept beside TypeScript 7 for tools

## What changes for you

- New apps made from the TypeScript starter and from the Python starter check their types with TypeScript 7, the new compiler that Microsoft rewrote as a native program. Microsoft reports full builds 8 to 12 times faster. TypeScript 6 stays installed beside it only for tools that still need its programming interface (Nx and Vite); the app's own type checks and builds use TypeScript 7. (Source: the owner's request, 17 Nov 2026)
- New starter apps lint with Oxlint instead of ESLint. Every Oxlint rule group is on as an error, and the rules that use type information are on. The module boundary rule (which part of the app may import which) keeps today's allowed imports through Nx's Oxlint plugin. The starters' own rules stay: dates, times, numbers and money are formatted only through the shared helpers; React's rules check the app's own code; in the Python starter, a module's web code uses another module only through its contracts. The lint settings list each rule that is off, with a one-line reason. (Source: the owner's request, 17 Nov 2026)
- New starter apps also turn on five testing rules from the open-source landmines package as errors. A test may not replace real code with mocks or fake functions (spies that only watch are allowed, and network calls go through MSW, which must fail on any request it does not expect), may not wait a fixed time or poll for a recorded call, and may not hide a flaky test with retries or longer time limits. (Source: owner, 18 Nov 2026)
- Existing apps keep their setup. Forge's health check (`forge doctor`), and Forge's file refresh (`forge sync`, which `forge upgrade` runs), print one line for each of these changes that the app does not have yet: TypeScript 7, Oxlint, and the testing rules for an app that already uses Oxlint. Printing these lines changes no file. The agent asks the owner, and makes a change only through a fix, the same way the suggested quick-test setting works today. Forge's guide gives the steps for each change. (Source: the owner's request, 17 Nov 2026)
- Not in this story: Vitest test groups filled by recorded test time. The CI time story does it, for new TypeScript starter apps with more than one test group. Pytest groups keep their split by recorded time. (Source: the owner's answers, 17 and 18 Nov 2026)
- Not in this story: running lint, type check, build and tests as separate pull request checks at the same time. Each extra check spends about 77 seconds on setup, so it no longer pays off. Another story, on CI time, may add one separate check later, only if its time report shows that it helps. The pull request check stays one job, as today. (Source: the owner's decision, 18 Nov 2026)
- What each repo gets. A new starter app gets TypeScript 7, Oxlint and the five testing rules at setup. Any other new repo gets the suggestion lines when it uses an older TypeScript, ESLint, or Oxlint without the testing rules. An existing repo gets the suggestion lines and the guide after it upgrades to the release with this change; nothing else in it changes.
- Cost. No model call is added, and no CI job is added. How much faster lint is in a new starter is not measured yet; the builders record the times before and after.

## Why

Client checks are slow. In a starter app, one test command runs lint, the type check, the tests and the browser tests one after another, in one CI job, so a pull request waits for the sum of all four. Two of the slowest tools in that chain have faster replacements: TypeScript 7 (released 8 July 2026) compiles about ten times faster, and Oxlint lints in a fraction of ESLint's time. ESLint's rules that use type information depend on TypeScript's programming interface, which TypeScript 7 does not have until version 7.1, so the linter moves too. Today the only workaround is to wait for the checks.

## Done when

1. **A new app made from either starter checks its types with TypeScript 7, and its build and tests still pass.**
2. **A new app made from either starter lints with Oxlint instead of ESLint, with every rule group on as an error and the rules that use type information on; a change that breaks the module boundaries or the shared-format rule fails lint, and the lint settings give a reason for each rule that is off; the five testing rules are on as errors, so a test that mocks a module fails lint.**
3. **In an app without these changes, the health check and the upgrade name each change the app does not have yet without making it, and the agent applies one only after the owner agrees, through a fix.**

## Risks

Risks: none one-way. Each part reverts with its pull request. Only new starter apps change by default; an existing app changes only when its owner agrees.

Accepted limits, in plain words:
- Oxlint runs Nx's module boundary rule through Oxlint's plugin interface, which Oxlint marks as alpha, and Nx marks its Oxlint plugin as experimental. The starters pin exact versions, so a change comes only with a deliberate update. The boundary rule is also the slowest part of lint: Nx measured about 15 seconds against 2.7 seconds without it, on a repo of 67 projects.
- Every rule group on includes the nursery group, which holds rules still in development. A newer Oxlint can add new errors. Because the versions are pinned, this happens only when a dependency refresh raises Oxlint.
- TypeScript 6 stays installed beside TypeScript 7 until Nx and Vite support the programming interface that TypeScript 7.1 brings.
- The testing rules come from a young open-source package (version 0.1.0, published on 17 Nov 2026, MIT license). The starters pin it exactly, so a new version changes nothing until Forge raises the pin.

### Tool facts (checked online on 17 Nov 2026)

- TypeScript 7.0 went GA on 8 July 2026; npm `typescript@7.0.2` gives the native `tsc`. 7.0 ships no programming interface; a new one is planned for 7.1. Tools that import `typescript` use the compatibility package `@typescript/typescript6` (6.0.2, `tsc6` binary) through an npm alias. It changes defaults (`strict` on, `types` `[]`, `rootDir` `./`) and removes `baseUrl`, `moduleResolution` `node10`/`classic`, and `target es5`. https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/
- Nx's TypeScript 7 guide: put `"typescript": "npm:@typescript/typescript6@^6.0.2"` and `"@typescript/native": "npm:typescript@^7.0.2"` in the root `package.json`; `npx tsc` then reports 7.0 and `npx tsc6` reports 6.0. It names the `@nx/js/typescript` plugin, `vite` and `typescript-eslint` as tools that still need the 6.0 interface. https://nx.dev/docs/kb/typescript-7
- Decorator metadata: the native compiler ported `experimentalDecorators` and `emitDecoratorMetadata` emit (typescript-go pull request 2343). https://github.com/microsoft/typescript-go/issues/2343 . Not confirmed by the release notes; the starter's live API tests prove it.
- Oxlint: seven categories (`correctness`, `suspicious`, `pedantic`, `perf`, `style`, `restriction`, `nursery`); `.oxlintrc.json` accepts comments; setting `plugins` replaces the default plugin set; `overrides` take `files`, `rules`, `plugins`, `env`; `jsPlugins` is alpha; `options.typeAware` and `options.typeCheck` go only in the root config. https://oxc.rs/docs/guide/usage/linter/config
- Type-aware linting is stable: `oxlint-tsgolint` v7 is built on TypeScript 7.0.2 and covers 59 of typescript-eslint's 61 type-aware rules. https://oxc.rs/blog/2026-07-22-type-aware-linting-stable . npm on 17 Nov 2026: `oxlint` 1.94.0 (needs `oxlint-tsgolint` 7.0.2007 or later), `oxlint-tsgolint` 7.0.2007.
- React Compiler rules in Oxlint: the `react` plugin's correctness group holds all of `eslint-plugin-react-hooks`' recommended rules, except `config` and `gating`. https://oxc.rs/blog/2026-08-18-react-compiler-support
- `eslint/no-restricted-globals` and `eslint/no-restricted-properties` exist in Oxlint; `no-restricted-syntax` does not (checked against the rules list). https://oxc.rs/docs/guide/usage/linter/rules/eslint/no-restricted-properties.html , https://oxc.rs/docs/guide/usage/linter/rules/eslint/no-restricted-globals.html
- `@nx/oxlint` arrived in Nx 23.2 (3 Sep 2026), experimental; it needs Oxlint 1.70.0 or later. Register `"jsPlugins": ["@nx/oxlint/boundaries-plugin"]` and the rule `@nx/enforce-module-boundaries` with the same `depConstraints` syntax as ESLint. https://nx.dev/blog/nx-23-2-release , https://nx.dev/docs/technologies/oxlint/introduction . npm on 17 Nov 2026: `nx` and `@nx/oxlint` 24.0.6 (10 Nov) and 23.3.2 (12 Nov); `@nx/oxlint` 24.0.6 depends on `@nx/eslint-plugin` and `@nx/js` of the same version.
- Vitest's `--shard` splits by file count, not time. A custom `sequence.sequencer` can override `shard`. Vitest's results cache stores each file's last duration under Vite's `cacheDir`. https://vitest.dev/guide/improving-performance , https://vitest.dev/config/sequence , https://vitest.dev/config/cache

### Options weighed

1. **Separate CI checks for lint, type check, build and tests.** Planned as a `{step}` placeholder that `forge.yml` filled per job. Removed on 18 Nov 2026 by the owner: each extra job spends about 77 seconds on setup, so it no longer pays off. FORGE-CITIME-1 may add one static job later, only if its time report shows that it helps.
2. **Vitest groups by recorded time.** Two designs were weighed. (a) A starter sequencer that splits files by Vitest's own results cache, with `forge.yml` saving and restoring that cache. GitHub restores only one cache entry per step, so a grouped nightly run leaves each group's times in a separate entry, and the times converge only over several runs. (b) A committed durations file, as pytest-split uses, which someone must refresh and commit. Both cost about 60 lines plus a moving part, and new apps start at `groups = 1`, where no split happens. Score below; cut, and the owner agreed (Notes).
3. **Oxlint's own type check (`--type-check`) in place of `tsc`.** Not asked for; `tsc` 7 stays the type check.
