# Faster checks and CI for client repos

3 parts · Risks: none one-way; four accepted limits · New moving parts: Oxlint with its type-aware add-on and Nx's Oxlint plugin in place of ESLint; TypeScript 6 kept beside TypeScript 7 for tools

## What changes for you

- New apps made from the TypeScript starter and from the Python starter check their types with TypeScript 7, the new compiler that Microsoft rewrote as a native program. Microsoft reports full builds 8 to 12 times faster. TypeScript 6 stays installed beside it only for tools that still need its programming interface (Nx and Vite); the app's own type checks and builds use TypeScript 7. (Source: the owner's request, 17 Nov 2026)
- New starter apps lint with Oxlint instead of ESLint. Every Oxlint rule group is on as an error, and the rules that use type information are on. The module boundary rule (which part of the app may import which) keeps today's allowed imports through Nx's Oxlint plugin. The starters' own rules stay: dates, times, numbers and money are formatted only through the shared helpers; React's rules check the app's own code; in the Python starter, a module's web code uses another module only through its contracts. The lint settings list each rule that is off, with a one-line reason. (Source: the owner's request, 17 Nov 2026)
- In a new starter app's pull requests, lint, type check, build and tests run as four separate checks at the same time, not one after another in one job. Each check still runs only for the parts of the app that the change can reach. The required tests check stays one check, and it passes only when all four pass. A change to documents alone skips the four checks and passes, as it skips the tests today. On the laptop, close still runs them as one command. (Source: the owner's request, 17 Nov 2026)
- Existing apps keep their setup. Forge's health check (`forge doctor`), and Forge's file refresh (`forge sync`, which `forge upgrade` runs), print one line for each of these three changes that the app does not have yet. Printing these lines changes no file. The agent asks the owner, and makes a change only through a fix, the same way the suggested quick-test setting works today. Forge's guide gives the steps for each change. (Source: the owner's request, 17 Nov 2026)
- Not in this story: Vitest test groups filled by recorded test time. It scored below Forge's bar for added work, because new apps start with one test group and small test suites, and the owner agreed to leave it for later work. The notes keep a ready design. Pytest groups keep their split by recorded time. (Source: the owner's answer, 17 Nov 2026)
- What each repo gets. A new starter app gets TypeScript 7, Oxlint and the four separate checks at setup. Any other new repo gets the suggestion lines when it uses an older TypeScript, ESLint, or package scripts for lint, type check or build. An existing repo gets the suggestion lines and the guide after it upgrades to the release with this change. Its generated workflow file keeps its one tests job until the owner agrees to the separate checks; as on every upgrade, only the Forge release named in that file changes.
- Cost. No model call is added. A pull request uses more CI runner minutes, because each of the four checks installs the app's packages. How much sooner a pull request finishes is not measured yet; the builders record the times before and after.

## Why

Client checks are slow. In a starter app, one test command runs lint, the type check, the tests and the browser tests one after another, in one CI job, so a pull request waits for the sum of all four. Two of the slowest tools in that chain have faster replacements: TypeScript 7 (released 8 July 2026) compiles about ten times faster, and Oxlint lints in a fraction of ESLint's time. ESLint's rules that use type information depend on TypeScript's programming interface, which TypeScript 7 does not have until version 7.1, so the linter moves too. Today the only workaround is to wait for the checks.

## Done when

1. **A new app made from either starter checks its types with TypeScript 7, and its build and tests still pass.**
2. **A new app made from either starter lints with Oxlint instead of ESLint, with every rule group on as an error and the rules that use type information on; a change that breaks the module boundaries or the shared-format rule fails lint, and the lint settings give a reason for each rule that is off.**
3. **In a new starter app, each pull request runs lint, type check, build and tests as separate checks at the same time, each only for the parts the change can reach, and the required tests check passes only when all of them pass; a change to documents alone skips them, as today.**
4. **In an app without these changes, the health check and the upgrade name each change the app does not have yet without making it, and the agent applies one only after the owner agrees, through a fix.**

## Risks

Risks: none one-way. Each part reverts with its pull request. Only new starter apps change by default; an existing app changes only when its owner agrees.

Accepted limits, in plain words:
- Oxlint runs Nx's module boundary rule through Oxlint's plugin interface, which Oxlint marks as alpha, and Nx marks its Oxlint plugin as experimental. The starters pin exact versions, so a change comes only with a deliberate update. The boundary rule is also the slowest part of lint: Nx measured about 15 seconds against 2.7 seconds without it, on a repo of 67 projects.
- Every rule group on includes the nursery group, which holds rules still in development. A newer Oxlint can add new errors. Because the versions are pinned, this happens only when a dependency refresh raises Oxlint.
- TypeScript 6 stays installed beside TypeScript 7 until Nx and Vite support the programming interface that TypeScript 7.1 brings.
- Each separate check installs the app's packages, so a pull request uses more runner minutes.

### Tool facts (checked online on 17 Nov 2026)

- TypeScript 7.0 went GA on 8 July 2026; npm `typescript@7.0.2` gives the native `tsc`. 7.0 ships no programming interface; a new one is planned for 7.1. Tools that import `typescript` use the compatibility package `@typescript/typescript6` (6.0.2, `tsc6` binary) through an npm alias. It changes defaults (`strict` on, `types` `[]`, `rootDir` `./`) and removes `baseUrl`, `moduleResolution` `node10`/`classic`, and `target es5`. https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/
- Nx's TypeScript 7 guide: put `"typescript": "npm:@typescript/typescript6@^6.0.2"` and `"@typescript/native": "npm:typescript@^7.0.2"` in the root `package.json`; `npx tsc` then reports 7.0 and `npx tsc6` reports 6.0. It names the `@nx/js/typescript` plugin, `vite` and `typescript-eslint` as tools that still need the 6.0 interface. https://nx.dev/docs/kb/typescript-7
- Decorator metadata: the native compiler ported `experimentalDecorators` and `emitDecoratorMetadata` emit (typescript-go pull request 2343). https://github.com/microsoft/typescript-go/issues/2343 . Not confirmed by the release notes; the starter's live API tests prove it.
- Oxlint: seven categories (`correctness`, `suspicious`, `pedantic`, `perf`, `style`, `restriction`, `nursery`); `.oxlintrc.json` accepts comments; setting `plugins` replaces the default plugin set; `overrides` take `files`, `rules`, `plugins`, `env`; `jsPlugins` is alpha; `options.typeAware` and `options.typeCheck` go only in the root config. https://oxc.rs/docs/guide/usage/linter/config
- Type-aware linting is stable: `oxlint-tsgolint` v7 is built on TypeScript 7.0.2 and covers 59 of typescript-eslint's 61 type-aware rules. https://oxc.rs/blog/2026-07-22-type-aware-linting-stable . npm on 17 Nov 2026: `oxlint` 1.94.0 (needs `oxlint-tsgolint` 7.0.2007 or later), `oxlint-tsgolint` 7.0.2007.
- React Compiler rules in Oxlint: the `react` plugin's correctness group holds all of `eslint-plugin-react-hooks`' recommended rules, except `config` and `gating`. https://oxc.rs/blog/2026-08-18-react-compiler-support
- `eslint/no-restricted-globals` and `eslint/no-restricted-properties` exist in Oxlint; `no-restricted-syntax` does not (checked against the rules list). https://oxc.rs/docs/guide/usage/linter/rules/eslint/no-restricted-properties.html , https://oxc.rs/docs/guide/usage/linter/rules/eslint/no-restricted-globals.html

Vitest's results cache stores each file's last duration under Vite's `cacheDir`. https://vitest.dev/guide/improving-performance , https://vitest.dev/config/sequence , https://vitest.dev/config/cache

### Options weighed

1. **Separate checks through a new forge.toml setting that lists the steps.** Rejected: a new setting (cost 3), and `repo.py`, which reads settings, is at 1,199 lines.
2. **Separate checks through a `{step}` placeholder (chosen).** It works like `{group}`: the command opts in by naming `{step}`, CI fills `lint`, `typecheck`, `build` or `test` per job, and every run outside CI gets `all`. No setting, no change for repos without it.
3. **A separate workflow file in the starter.** Rejected: Forge owns and rewrites `forge.yml`, and the required `tests` check must stay one gate.
4. **Vitest groups by recorded time.** Two designs were weighed. (a) A starter sequencer that splits files by Vitest's own results cache, with `forge.yml` saving and restoring that cache. GitHub restores only one cache entry per step, so a grouped nightly run leaves each group's times in a separate entry, and the times converge only over several runs. (b) A committed durations file, as pytest-split uses, which someone must refresh and commit. Both cost about 60 lines plus a moving part, and new apps start at `groups = 1`, where no split happens. Score below; cut, and the owner agreed (Notes).
5. **Oxlint's own type check (`--type-check`) in place of `tsc`.** Not asked for; `tsc` 7 stays the type check.

### Decisions

**TS7: TypeScript 7 in both starters.**
- In both starters' root `package.json`, replace `"typescript": "5.9.3"` with `"typescript": "npm:@typescript/typescript6@6.0.2"` and add `"@typescript/native": "npm:typescript@7.0.2"`, exact versions as the starters pin everything. Regenerate each `pnpm-lock.yaml` with the starter's own pnpm (`corepack pnpm install --lockfile-only`, then `--frozen-lockfile`).
- Remove `baseUrl` from `apps/web/tsconfig.json` and `libs/shared/ui/tsconfig.json`; keep their `paths` (they resolve from the tsconfig's folder). Add nothing else unless `tsc` 7 reports an error; then fix that one setting in `tsconfig.base.json` (for example `types`) and say so in the pull request.
- First step, before other edits: build the API with TypeScript 7 and run the starter's live API tests, because NestJS needs decorator metadata. If they fail only because the metadata is missing, point the API `build` target and the `typecheck` script's `tsc -b apps/api/tsconfig.json` at `tsc6`, keep every other `tsc` call on 7, and say so in the pull request. Item 1 still holds: the type checks run on TypeScript 7.
- Record the wall time of `corepack pnpm run typecheck` in a fresh starter before and after, in the pull request text.

**CHECKS: separate CI checks and the suggestions.**
- `repo.grouped` also fills `{step}` from `FORGE_STEP`, with `all` when it is unset. Keep `repo.py` at or under 1,200 lines (one added line at most, or rewrap the replace chain).
- `review.passed_record` adds `FORGE_STEP` to its key on the existing lines, so two steps never reuse each other's pass. `review.py` gains no line.
- `prcheck.ships`: when the pull request command (`quicktest.group_command(cfg)`) contains `{step}`, use the multi-job template even with one group, and make the `tests` matrix an `include` list: `{step: lint, group: 1, groups: 1}`, `{step: typecheck, ...}`, `{step: build, ...}`, then `{step: test, group: g, groups: N}` for each test group (`N` from today's group rule). The docs-check `test-only` output keeps all four steps and one test group. Each leg sets `FORGE_STEP: ${{ matrix.step }}`, `FORGE_GROUP` and `FORGE_GROUPS` from the matrix, and is named `${{ matrix.step }}`, or `test group g of N` when N > 1. The gate job stays the one required `tests` check and needs every leg. A docs-only change keeps today's rule: the legs keep the `docs-only != 'true'` condition, so they are skipped and the gate passes with `docs only: tests skipped`. The nightly full-suite job does not change; there `{step}` is `all`. Without `{step}` the workflow is the same as this release writes for that repo today: on upgrade only the Forge version in its header and install lines changes, as on every upgrade.
- The step names are fixed: `lint`, `typecheck`, `build`, `test`. `# ponytail: fixed names; a setting only when a client needs others.`
- Init writes `fast_test = "node scripts/test.mjs {base} --step {step}"` for both starters; `test` stays `node scripts/test.mjs`.
- `starter/scripts/test.mjs` takes `--step <lint|typecheck|build|test|all>` (default `all`, today's behaviour). Install and Prisma generation run for every step. Only `test` and `all` start the Docker stack, install Playwright and check `/health`. With affected parts, `lint`, `typecheck` and `test` run only that Nx target for the affected projects (and the library fallbacks for lint and tests); `test` also runs `web:e2e` when `web` is affected, as the script does today, because the browser suite is a separate `e2e` target; `build` runs the `build` target of affected projects that have one. With no base or a shared change: `lint` runs `pnpm run lint`, `typecheck` runs `pnpm run typecheck`, `build` runs `scripts/test-build.mjs`, `test` runs `test:api`, `test:hooks` and `test:browser`. `--list` prints only the chosen step's commands.
- `starter-python/scripts/test.mjs` takes the same `--step`. A step only filters the commands that today's selection already picks for the change: it never adds a command that the selection leaves out (a web-only change still runs no Ruff, `mypy`, `test:imports` or `test:api` in any step). Per step: `lint`: `api-types` first (each CI job starts from a clean checkout, the generated API types are ignored by git, and type-aware lint needs them), then the web linter, plus `ruff check` and `ruff format --check` when the API is affected. `typecheck`: `api-types`, `tsc --build`, plus `mypy` when the API is affected. `build`: `api-types`, then `vite build`. `test`: `test:imports` and `test:api` when the API is affected, the affected Vitest run, `test:browser`, with the stack. With no base, `all` keeps `pnpm test`, and each single step runs its package scripts as listed. `uv sync` runs for the steps that need Python.
- `quicktest.faster_checks(top, cfg)` prints at most three lines, each only when it applies, and never edits a file. Call it from `doctor.py` beside `quicktest.suggest`, and from `sync.py` beside `quicktest.combined_note` (`:749`). Not from `upgrade.py`: the upgrade that moves a repo to this release runs the older installed release's `upgrade.py`, but it runs the new release's sync (`upgrade.py:216-220`), so sync is where the first upgrade prints the lines, as `combined_note` already does.
  - The root `package.json` lists `typescript` with a major version below 7, and no `@typescript/native`: `Faster type checks: TypeScript 7's native compiler can replace TypeScript <version> here. Follow "Faster checks for an existing app" in the Forge guide, then ask the owner.` Read the major from the first number in the range after any leading `^`, `~`, `>=`, `>`, `=` or `v` (so `^5.9.3`, `~5.4.0` and `>=5` count); skip a value with no number (for example `workspace:*`, `catalog:` or `latest`).
  - It lists `eslint` and not `oxlint`: `Faster lint: Oxlint can replace ESLint here. Follow "Faster checks for an existing app" in the Forge guide, then ask the owner.`
  - `test_place` is `ci`, neither `test` nor `fast_test` contains `{step}`, and `package.json` has at least two of the scripts `lint`, `typecheck` and `build`: `Faster pull requests: lint, type check, build and tests can run as separate checks at the same time.
