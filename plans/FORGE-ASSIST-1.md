# Client apps get an optional in-app assistant

Parts are set when a client asks · Risks: none one-way · New moving parts: the LangGraph libraries, a daily clean-up timer in the API, the Mainline model client

## What changes for you

- Forge keeps an assistant module as a template. It is not in a new app. When a client asks for the assistant, the client's agent copies the module into that client's new or existing app by following the guide. There is no new command. Forge ships no Assistant page, no route and no menu entry for it: the client's agent builds the page during design and implementation, in that client's design. The story is planned now and built when the first client asks. (Source: your decisions, 28 Oct, 3 Nov and 4 Nov 2026)
- On the Assistant page that the client's agent builds, a signed-in person types a question in plain words. The assistant answers in text. When the answer is data, it shows one of five fixed parts from the app's design system: a table, a chart, stat tiles, a detail card or a confirm card. Code picks the part from the typed result of the tool that ran. The model never writes page markup. Forge ships the five parts as components, and the small pieces of code (React hooks) that read the answer as it streams in and handle the confirm card. It ships no page. (Source: your decision, 28 Oct 2026) (Source: your decision, 3 Nov 2026)
- The agents skill gets written rules for the Assistant page, and the guide points to them. The rules say what every client's page must do. Examples: Send is off while an answer comes in, the model's text shows as plain text, a change shows its confirm card with Confirm and Cancel before anything is saved, a used-up budget shows one plain line and the page stays usable, and the history screen shows the person's email followed by ", via the assistant". The client's agent writes the page's browser tests for these rules. Forge ships no test of the page itself, because it ships no page. (Source: your decision, 3 Nov 2026)
- The assistant runs in the app's own API. We build the server code only for the language of the client that asks, NestJS or FastAPI. The second language waits until a client needs it. It uses LangGraph's prebuilt tool-calling agent and nothing custom: no hand-made graph. It works through the app's own MCP tools. (Source: your decisions, 28 Oct and 4 Nov 2026)
- The assistant acts as the signed-in person, with that person's permissions. It cannot read or change what the person cannot. Each change it makes appears in the change history as the person, marked "via the assistant": the change-history list from the API and its CSV file show the person's email followed by ", via the assistant". The change-history screen is built by the client's agent, and the written rules tell it to show the same text. This fills the value that the agent-ready story stores and shows it, as that story's plan says. (Source: your decision, 28 Oct 2026; the screen text is the agent-ready story's plan) (Source: your decision, 3 Nov 2026)
- Reads run at once. Every write first shows a confirm card with the plain-words change. Nothing is saved until the person confirms. A write carries a retry key, so a repeated confirm or a resent message makes one change. A confirm card expires after 15 minutes. (Source: your decision, 28 Oct 2026; the 15 minutes is the agents skill's default)
- The starters have no report yet, so the assistant in a new app answers with text, tables and detail cards. When an app has a report service, the assistant answers questions about numbers (totals, trends, counts) from it, as a chart or stat tiles. The assistant does not run its own queries. The starters' own tests prove the chart and tiles with a stand-in report. (Source: your decision, 28 Oct 2026; the starters have no report, as the agent-ready story's plan says)
- The model, the key, the allowed models and the spend budget come only from Mainline. The app holds `MAINLINE_AI_KEY` and no provider key. A client that asks before Mainline's model service is ready has to wait. Nothing in the Forge repo describes that service yet, so this is still unknown. The models the assistant may use are the ones on the app's Can use list. When the budget is used up, the person sees one plain line and the rest of the app works. (Source: your decisions, 28 Oct and 4 Nov 2026)
- Each person's chats are kept 30 days after the last message in the chat, in the app's Postgres through LangGraph's Postgres checkpointer. Then they are deleted. Nobody else reads them: not another person, not an admin, not an agent tool. (Source: your decision, 28 Oct 2026; counting from the last message is the planner's choice)
- The first version leaves out voice, sending a message during an answer, a way to reach a human, an automatic quality check of answers, and summaries of long chats. The Notes give the reason for each. (Source: your decisions, 28 Oct and 4 Nov 2026)
- The five components take every colour from the app's design system. A test fails if one of them uses a fixed colour, and a written page rule tells the client's agent to build the page in the client's design. (Source: your decision, 4 Nov 2026)
- A new app from a starter has no module, no library and no table for the assistant. An existing app gets no file on upgrade. Both get the written page rules and the copy steps in the agents skill and the guide, an existing app with `forge sync`. (Source: your decisions, 28 Oct, 3 Nov and 4 Nov 2026)
- The build follows the agents skill, web chat only. Its rules for the shape of the agent, the turn, tool design, output and side effects, safety, cost and tracing, and testing apply. Where the plan does not meet a Must rule, it says why, in the builders' section. (Source: your decision, 28 Oct 2026)

Design: none (Forge ships no Assistant page. The five parts use the design system's existing components and take each client app's own design, and the client's agent builds the page in that design; owner rules, 28 Oct and 3 Nov 2026)

## Why

A client that wants to ask its app a question in plain words would build its own assistant: its own model keys, its own chat storage, its own write checks. Each build would choose these rules by hand. The starters already have what an assistant needs: one door for every action and MCP tools with the person's permissions after the agent-ready story. This story adds the one module that joins them, with the parts and the written rules for its page, so a client's assistant is a switch and a page that its agent builds in the client's design, and not a project. (Source: your decision, 3 Nov 2026)

## Done when

1. **In an app that has turned the assistant on, a question sent to the assistant's API streams back the answer as text, plus a table or detail card when the answer is data, and a chart or stat tiles when the app has a report. The five components and the chat hooks that ship with the module draw and read exactly what streams back.**
2. **Every change that the assistant would make stops at a confirm card first, and the confirm card component and the chat hooks send the person's decision. Nothing is saved until the person confirms. A repeated confirm, or a message sent again with the same key, makes one change.**
3. **The assistant acts as the signed-in person: it sees and changes only what that person's permissions allow, and each change is recorded in the change history as that person, via the assistant, in the history list and in its CSV file.**
4. **Each person's chats are kept 30 days after their last message, then deleted, and no one else can read them.**
5. **The model, the key, the allowed models and the budget come from Mainline. The app holds no provider key, and a used-up budget shows one plain line without breaking the app.**
6. **A new app from a starter has no assistant module, and an existing app gets no file and no change on upgrade. Both get the page rules and the copy steps. A test copies the module into a new app and runs it, and a test fails if a component uses a fixed colour.**

## Risks

Risks: none one-way. Each part reverts with its pull request. The assistant tables are new and hold only chats that the module makes.

Trade-off: the module is not in a starter, so the normal starter tests do not cover it. A test copies it into a new app and runs it. That test runs only when the module changes, so a starter change can break the module until the module next changes. The module also has only the copy steps for a way in, with no command.

Trade-off: a chat is deleted 30 days after its last message, so an active chat can live longer than 30 days from its start.

Trade-off: the clean-up runs on a timer inside the API. If the API is down for a day, the deletion runs when it is back.

Trade-off: Forge ships no Assistant page, so Forge cannot test one. Forge proves the API, the five components, the chat hooks and the written rules. Only a client's built page can prove that Send is off while an answer comes in, that the confirm card and its buttons work on the page, that a used-up budget leaves the page usable, and that the page looks right in the client's design. The first real run happens in the first client app that builds the page. (Source: your decision, 3 Nov 2026)

Trade-off: the first client that asks pays for building the page in its own design. The API, the components and the rules are ready for it. (Source: your decision, 3 Nov 2026)

- No new permission. Every signed-in person can use the endpoints, because `SessionGuard` already needs a session. Each tool checks its own permission.
- One function, `ownChat(account, chatId)` (Python `own_chat`), loads a chat for its owner and answers `404 NOT_FOUND` for any other person, an admin too. Every route with `:id` calls it first, before the advisory lock, the model, the checkpointer or a resume.
- Endpoints, under `/api/v1/assistant`:
  - `POST /chats` makes a chat. It answers `{ id }`.
  - `GET /chats` lists the caller's own chats, newest first.
  - `GET /chats/:id` gives the caller's own chat with its messages and any open confirm card. Another person's chat answers `404 NOT_FOUND`, for an admin too.
  - `POST /chats/:id/messages` takes `{ text }` (1 to 4,000 characters) and the `Idempotency-Key` header. It answers `text/event-stream`.
  - `POST /chats/:id/confirm` takes `{ confirmId, decision: 'confirm' | 'cancel' }` and answers the same stream.
- Stream events: `text` (`{ delta }`), `block` (`{ kind, props }`), `confirm` (`{ confirmId, title, lines, expiresAt }`), `limit` (`{ message }`), `error` (`{ message }`) and `done`.
- The five blocks, in `@app/assistant-contracts` as zod schemas (Python generates the same JSON shape from Pydantic models, and `libs/assistant/contracts` holds the TypeScript types):
  - `table`: `{ columns: { key, label }[], rows: Record<string, string | number | null>[], total?: number }`.
  - `chart`: `{ type: 'bar' | 'line', xKey, series: { key, label }[], rows: Record<string, string | number>[], unit? }`.
  - `stats`: `{ tiles: { label, value, unit? }[] }`.
  - `detail`: `{ title, fields: { label, value }[] }`.
  - `confirm`: `{ confirmId, title, lines: string[], expiresAt }`.
- Choosing a block. `libs/assistant/server/src/assistant.display.ts` (Python `app/assistant/display.py`) holds one map from tool name to a function that turns that tool's typed result into block props. `DISPLAY` is an exported record. A `<feature>_search` tool maps to `table` and a `<feature>_get` tool to `detail`, as its result fields say. The starters have no report tool, so the map has no `chart` or `stats` entry; an app that adds a report adds its entry in the same record, and the stand-in report in the tests does the same. A tool with no entry shows its summary text only. Code makes the block. The model's text sits beside it and cannot change it.
- Writes. A tool whose annotations say `readOnlyHint: false` stops at `interrupt()` with `{ tool, args }` before it runs. The `confirmId` is the id that LangGraph gives that interrupt. The model is bound with parallel tool calls off (`parallel_tool_calls: false`) and the prompt says to propose one change at a time, so a chat has at most one open interrupt. "Mark these two projects complete" gives one card, then, after the person decides, the second. The stream sends a `confirm` event. `confirm` resumes with `Command(resume=...)`; `cancel` resumes with a refusal that the model sees as the tool's result. A `confirmId` that is not the chat's open interrupt answers `409 CONFLICT` "That change is no longer waiting." and runs nothing. The retry key for the write is `<chatId>:<toolCallId>`, which is the same on every re-run of the node. A create tool takes it as `idempotency_key`. An update, delete or restore has no key and is safe to run again.
- Expiry. `confirm` after `expiresAt` (15 minutes after the card is made) answers with the stream's `error` event "That change expired. Ask again." and runs nothing.
- Tables, in the `assistant` schema: `chat` (`id` uuidv7, `accountId` link, `threadId`, `createdAt`, `lastMessageAt`), `usage` (`id`, `accountId`, `chatId` link, `kind` text with a named check (`llm`), `inputTokens`, `outputTokens`, `costMicros` nullable, `createdAt`). The checkpointer's own tables sit in the `assistant` schema too (`PostgresSaver.setup()` run in the module's migration step, not at start). All columns follow the database skill: uuidv7 ids, `timestamptz`, named checks.
- Clean-up. The module starts one timer when it is imported. Each hour it deletes chats whose `lastMessageAt` is more than 30 days old: `deleteThread(threadId)` on the checkpointer, then the `chat` row, inside one transaction where the driver allows it. `usage` rows stay (they hold no text). The timer is idempotent, so two API instances running it do no harm. The 30 days and the hour are named constants.
- The agent. One `createAgent` (Python `create_agent`) per turn, with the Mainline chat model, the tools from `listTools(context)` turned into LangChain tools whose `func` calls `callTool(name, args, context)`, the Postgres checkpointer, the person's `thread_id`, and `recursion_limit` 6, with parallel tool calls off. Before the agent runs, `handleTurn` checks the text for a secret: a run of 13 to 19 digits (spaces and dashes allowed) that passes the Luhn check, or a word such as password, passcode, PIN or one-time code followed by `is`, `:` or `=` and a value. On a match it answers with the stream's `error` event "Do not send passwords or card numbers here. Use the app's own screens for those." and runs nothing: no model call, no checkpoint, no `lastMessageAt` change. The run context holds the person's principal with `viaAgent: 'the assistant'` (Python `via_agent="the assistant"`); the model cannot pass a user id. The system prompt is one file, `assistant.prompt.ts` (Python `prompt.py`), at most 12 KB, with a `PROMPT_VERSION` constant. Tool definitions stay in the first part of the prompt and `tool_choice` stays auto.
- The Mainline client: one file, `mainline.ts` (Python `mainline.py`). It builds the chat model from `MAINLINE_AI_URL` and `MAINLINE_AI_KEY`, checks that `ASSISTANT_MODEL` is on the app's Can use list when the module starts (a model not on it stops the start with a plain message), and turns a refusal for budget into the stream's `limit` event with the line "The assistant is paused for now. The rest of the app works as usual." A refusal because the chat is too long for the model gives the `limit` line "This chat is too long. Start a new chat." No other file reads `MAINLINE_AI_KEY`.

### How the build meets the agents skill

These sections of the agents skill apply: Agent shape, The turn, Tool design, Output and side effects, Safety and privacy, Cost and tracing, Testing and prompt changes. The sections Fast decisions before the model, Context and the prompt cache, Memory: writing, Memory: recall and Spoken chat do not apply, because this story has no classifier, no memory notes and no speech; a later story that adds one takes that section. A Must rule about a thing the change does not have (an image, a file, a note) is not broken. The rules that need a decision here:

- **Agent shape.** The prebuilt agent loop only, behind one `handleTurn` function (owner decision). A step limit of 6 per turn, as the skill's default says. After two failed tries at one goal, the assistant says it cannot do it and points the person to the matching screen. No request log is written: the skill's default of logging the exact request in dev would hold chat text outside the 30-day rule. The builder reads once what `createAgent` sends and what each node returns, and the prompt-size case covers growth.
- **The turn.**
  - Fail once quietly: a `RetryPolicy` on the model node, one retry, a 20 s provider wait, and one honest error line when it fails again.
  - Speed target: first text within 7 s for 95% of turns. The trace line carries the first-text time. The stream shows text as it is written.
  - Not met, with the reason: *acknowledge fast through an inbox table* and *steering*. The web request is the queue, and the written page rule turns Send off while a turn runs, so no second message arrives in a running turn. One run per chat is held by a Postgres advisory lock on the chat id; a second message gets `409 CONFLICT` "The assistant is still answering." Needs the owner's OK (Planner choice 4).
- **Tool design.** The tools are the app's MCP tools, which FORGE-MCP-1 builds to these rules. The assistant shows at most 15 tools. If an app has more, the turn passes the 15 whose features the person can use, ordered by the person's last use, and the plan for that client says so.
- **Output and side effects.**
  - Identity comes from the signed-in session (`@CurrentAccount()`), never from the model.
  - Code owns facts: a block shows the tool's own values; the model's text never repeats a figure that a block holds, and the prompt says so.
  - Writes run once with a confirm: `interrupt()` before the write, a retry key on the write, and the 15-minute expiry. The limit check is the service's own, in its transaction.
  - One reply path: the message endpoint takes `Idempotency-Key` through the agent-ready helper (`RetryKeys.once`, Python `create_once`), action name `assistant_message`. A resent message with the same key gives back no second turn.
  - Limits never break a feature: a refusal for budget, or a model stop reason, gives the `limit` line and a log line `limit_hit`.
- **Safety and privacy.**
  - Delete means every copy: the clean-up removes the chat row and the checkpoints. Nothing else holds chat text: the history keeps the action and not the words, the trace line holds no message text, and no tool or admin screen reads a chat.
  - Never take secrets: code checks the text before the agent runs (see The agent) and refuses, so a secret reaches no model call and no checkpoint. The prompt also tells the assistant to refuse and to point to the screen. The check finds a labelled password or a card number; a bare unlabelled password is not found, and the prompt is the only guard for it.
  - Not met, with the reason: *a way to a human* and *consent before personal questions*. The app has no human inbox, and the assistant asks no personal question; it works only on the app's own data. The assistant's help line says "Ask an admin of your organisation for anything the assistant cannot do." Needs the owner's OK (Planner choice 4).
- **Context.** Not met, with the reason: *the context ceiling and summary*. A chat keeps its whole history, and a provider refusal for length shows the `limit` line "This chat is too long. Start a new chat." A summary step is not worth its code for the first clients. Needs the owner's OK (Planner choice 4).
- **Cost and tracing.** Every model call goes through the one Mainline client. Each turn writes one `usage` row for the person. Each turn writes one JSON log line with `promptVersion`, a hashed account id, the tools called, the timings and the `limit_hit` flag. There is no tracing provider, so there is nothing to erase there.
- **Testing and prompt changes.** Bug first and one job per layer, as the skill says. The tests use a stub of Mainline's model service that is a test file only; production code has no test setting. The prompt has a byte budget test. Not met, with the reason: *a calibrated judge*. No quality judge exists yet, and the cases use answer keys. Needs the owner's OK (Planner choice 4).
