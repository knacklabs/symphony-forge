# Starter ships no screens

6 parts · Risks: none one-way · New moving parts: none

## What changes for you

- New client apps from `forge init` get the API, the rules, the skills and the guide, with no sign-in, Members, Projects, Change history, Join or app shell screens, in both the React and Python starters. They also keep the web build setup that carries no screen: the build and test configuration, the theme file, the shadcn components and the API client. (Source: your decision, 31 Oct 2026: "We only save the important characteristics and best practices to build with forge, not the actual screens"; you confirmed the build setup stays)
- Each client's agent builds every screen in that client's own design. Every API that a person uses gets its screen, built by the agent when it builds the API, with no need to ask. APIs that only machines call (webhooks, endpoints for agents or other systems, background jobs) get no screen. (Source: your decision, 31 Oct 2026)
- The design comes first. Before any screen, the app has its design: drafted on a design canvas from the client's brand when the client has none, and a neutral design when there is no brand at all. The approval of the design joins the one approval of the prototype plan; another story builds that approval. This story only states the order in the guide. (Source: your decision, 31 Oct 2026)
- The basic screens are sign-in, forgot password, reset password, accept invite, members and settings. They are built first in every prototype, in the client's design. The demo still opens on the client's business task, and the basic screens are shown last. (Source: your decision, 31 Oct 2026)
- Forge ships no reference screen. It ships exact written rules for sign-in, reset password, accept invite and members, and browser tests that every client app's version of those screens must pass. The tests find things by role and label, never by markup. Examples: sign-in locks after failed tries, no answer lets anyone guess which accounts exist, a reset link works once, an invite link expires, an admin cannot remove themself. (Source: your decision, 31 Oct 2026)
- No email yet. When the app has no mail provider, the admin sees the invite link and the reset link in the app, and copies them to send by any chat. Email through SNS comes later. (Source: your decision, 31 Oct 2026)
- impeccable and emil-design-eng are required for every screen and every user-facing text a client's agent writes. Forge ships both skills to every client repo, with or without a web app, as it ships the Simplified Technical English skill. The licences allow it. The Mac and Windows installers install both. (Source: your decision, 31 Oct 2026)
- `forge task feature` builds a feature's API, agent tools, change history and tests. It writes no pages any more; the agent builds the feature's screens in the client's design. (Needed by: the removal of the starter screens, because the command copies the Projects pages)
- Forge's review reports a person-facing API that has no screen, in a client repo that has a web app. In Forge's own repo, the review reports any new screen in Forge's templates. (Source: your decision, 31 Oct 2026)
- A client repo that already exists keeps all its app code when it upgrades. It gets the new guide text, skills and review rule with `forge sync`. It does not get the sign-in lock, the shown links or the rule tests, because those are app code and app tests. (Source: the Forge review rules)

Design: none (this story removes screens and adds none; each client app's own design covers every screen)

## Why

Each client app has its own design. The starter's screens fit none of them, so the client's agent must remove or rebuild them before the real design can start. Forge should keep only what holds for every app: the API, the rules, the skills and the tests that every version of a basic screen must pass. Today, without a mail provider, nobody can get an invite link or a reset link, and the API has no sign-in lock.

## Done when

1. **A new app from `forge init`, with either starter, has no screen files. Its API tests pass, the built app still serves its page, and the starter smoke run is green.**
2. **`forge task feature` builds a feature's API, tools, history and tests and writes no page, in both starters and in an app from an earlier release.**
3. **An existing client repo's app files do not change after upgrade and `forge sync`.**
4. **In a new app, the API locks sign-in after failed tries without telling anyone which accounts exist, and it gives the admin the invite link and the reset link with no mail provider. The app ships the written rules and browser tests for sign-in, reset password, accept invite and members; they stay off until the agent builds the screen.**
5. **The guide and the app-baseline skill say who builds the screens and in what order: design first, every person-facing API gets its screen in the client's design, machine-only APIs get none, basic screens first with the demo opening on the business task. The review reports a person-facing API with no screen in a repo that has a web app, and Forge's own `AGENTS.md` review rules report a new screen in Forge's templates. A new repo gets this at init and an existing repo with `forge sync`.**
6. **A client repo gets the impeccable and emil-design-eng skills at init and with `forge sync`, and the Mac and Windows installers install both.**

## Risks

Risks: none one-way. Each part reverts with its pull request.

Trade-offs, in plain words:
- A new app has no screen to click until the agent builds the first ones, so the prototype's first step is longer. This is what you chose.
- Forge cannot run the shipped screen tests, because it keeps no screen to run them against. Forge proves that they compile and are listed, and its API tests prove the same behaviours. The first real run happens in the first client app that builds the screens.
- The two design skills add about 4.4 MB to every client repo, also a repo with no web app (impeccable is about 2.2 MB for each of the two agent hosts). You chose this (31 Oct 2026).
- A story that was planned against the removed Members or Projects screens needs its plan checked (see Notes).

### Settled (with the reason)

1. **The web app folder keeps a build-only setup and loses every screen** (owner confirmed). Kept: `apps/web` config files, `index.html`, a `main.tsx` that mounts only the providers (no router, no routes), `index.css`, `libs/core/web` without its two screen parts, `libs/shared/ui` without `auth-page-frame.tsx`, the new specs. Reason: deleting the whole folder would also change both Dockerfiles, both API servers, both test scripts, the Nx project list and the lock files, and would lose pinned and tested rules (React Compiler on, shadcn only, theme tokens, axe check).
2. **Delete the module web libraries completely** (`libs/{auth,history,organisations,projects}/web`), including hooks and hook tests. Reason: hooks serve the screens; the agent writes hooks for its own screens as `frontend.md` shows.
3. **API routes, `libs/*/contracts` and the Python `libs/shared/api-types` stay.** Reason: only screens go; the client's screens use them. The Projects module stays as the model that `forge task feature` copies for the API.
4. **`forge task feature` stops writing web files.** Delete `src/forge/feature_web.py`, `src/forge/templates/feature/link-picker.tsx`, `_wire_web` and the web lines of `feature.py`, and the browser specs of `feature_tests.py`. Reason: the command copies the Projects pages, which are going. About 700 lines of Forge code go (principle 6).
5. **One new spec, `apps/web/e2e/served-app.spec.ts`,** keeps the browser step alive and runs now: the built page loads with its title and the `app-env` meta tag, an unknown path falls back to `index.html`, `/api/...` keeps answering JSON, and the axe check passes. `vitest.config.ts` gets `passWithNoTests: true` because `test:hooks` has no test left. Reason: proves the Docker build still serves the web page.
6. **The rule specs ship at init, in the starter, not through `forge sync`.** They live in `apps/web/e2e/rules/` (`sign-in.spec.ts`, `reset-password.spec.ts`, `accept-invite.spec.ts`, `members.spec.ts`). Reason: Forge never changes client app code after init, and a spec synced into an existing app would fail on screens built to the old design. An existing repo gets the written rules in the skill and keeps its own tests.
7. **The rule specs stay off until the screen exists.** `playwright.config.ts` has one list, `pendingScreens = ['sign-in', 'reset-password', 'accept-invite', 'members']`, that feeds `testIgnore`. The agent removes a name from the list when it builds that screen; the worker brief and the skill say so. Reason: a new app has no screen, so a live spec would fail the first test run, and a skip that detects the screen is hidden behaviour. No check enforces the removal (principle 4); the existing P1 `Gate: UI check` and the new `Screen:` rule cover a screen built without its spec.
8. **The admin always gets the link** (owner, 31 Oct 2026, also when email is sent). `POST /api/v1/invites` answers `data: { message, link }`, and a new `POST /api/v1/members/{accountId}/reset-link` (admin only, for an active member of the admin's own organisation, 404 `MEMBER_NOT_FOUND` otherwise, also for an account of another organisation, as `changeRole` scopes by `organisationId`) answers `data: { link }` and records `member.reset_link_created` in the history. Both still send the email when a mail provider is set. Reason: no setting and no extra endpoint tell the screen whether a provider exists; showing the link to an admin always is the least code. A retried invite (same retry key) answers the stored message with no link; the admin makes a new invite to get a link, which replaces the old one. The invite route's "Production requires a mail provider" refusal is removed.
9. **The sign-in lock: five failed sign-ins for one email within 15 minutes lock that email for the rest of the window** (owner, 31 Oct 2026). A locked email answers `429 SIGN_IN_LOCKED`, "Too many tries. Try again in 15 minutes.", even with the right password. An email with no account gets the same counting and the same answers as one with an account, so the lock gives no hint. An unknown email also costs the same password work: `signIn` checks the password against a fixed dummy hash made with the real hash settings, so response time does not show which accounts exist. A good sign-in clears the count. Storage is one new table keyed by the lower-cased email, with the database skill's rules and an expand-only migration (Prisma for TS, Alembic for PY). Reason: F 2 (credential stuffing hits any app that is online), H 3, C 3 gives 6 >= 6.
10. **Sign-up keeps `409 EMAIL_ALREADY_REGISTERED`.** The "no guessing" rule covers sign-in, forgot password and reset password. Reason: a visitor who signs up with a used email must be told, and one-company apps close sign-up.
11. **`--pass-with-no-tests` in PY `scripts/test-browser.mjs`.** Reason: each spec file runs by name, and a file that `testIgnore` skips would otherwise fail the run with "no tests found".
12. **Boundary lint and the screen layout in `frontend.md` stay** as rules for the screens the agent adds. Their tests add a small module web library to the fresh app, as an agent would, and expect the lint to catch a cross-module import.
13. **`tests/test_python_starter.py::test_3` ("tests fail when the API changes a field the web app uses") is deleted.** Reason: no web code uses the field any more; no test without a rule.
14. **The review rule for a person-facing API with no screen is a shipped review block, and applies only to a repo with a web app** (a `package.json` in `apps/web`, `web` or `frontend`, as `doctor.py` checks). Reason: an API-only client has nowhere to put a screen. A screen marked `Build: later` in SCREENS.md does not count as missing. A plan names a machine-only route in its own words; no new marker.
15. **The Forge-only rule goes in `AGENTS.md` under `## Review rules` and has no test or check.** Reason: principle 4; it is about Forge's own templates and no client repo needs it.
16. **The two design skills ship through a new `src/forge/design_skills.py::ships`, shaped like `src/forge/plain_english.py`, to every client repo, with or without a web app (`cfg["repo"] == "client"`; owner, 31 Oct 2026).** Files live under `src/forge/templates/skills/impeccable/` (the upstream `plugin/skills/impeccable` files at one pinned commit, plus the upstream `LICENSE` and `NOTICE.md`) and `src/forge/templates/skills/emil-design-eng/` (`SKILL.md` and the upstream `LICENSE`). Reason: the licences allow redistribution, and a repo's own copy satisfies `forge doctor`. Forge's own repo is not a client, so it gets no copy and keeps its global skills. A newer upstream version reaches clients only with a new Forge release; `forge sync` rewrites a hand-installed copy in a client repo to the pinned one.
17. **The installers install both skills; `forge doctor`'s `INSTALL` text for emil-design-eng becomes a real command.** `scripts/install-mac.sh` and `scripts/install-windows.ps1` run the upstream installer (`npx --yes skills add ...`, one call for each skill, as `doctor.py` already names for impeccable; the builder checks the exact command and flags against upstream before writing it). The rule is stated in the skill and the guide (principle 4). `forge doctor` already reports a missing skill.
