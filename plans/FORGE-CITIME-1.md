# Client pull requests finish CI in about 10 minutes, and Forge shows when they do not

5 parts · Risks: none one-way; nine accepted limits · New moving parts: a test run on the default branch after each merge in repos whose tests run in pull request CI

## What changes for you

- After the checks of a pull request finish, close prints one line: how long CI took from the start of the first job to the end of the last job, how many runner minutes it used, and which job was slowest. It reports the slowest of the pull request's last 5 pushes, so a short rerun after Forge's record commit does not hide the run that tested the code. When a check fails while other jobs still run, the line covers the jobs that ended and says how many were still running. Forge reads these times from GitHub. It stores nothing. (Source: owner, 18 Nov 2026)
- `forge doctor` (Forge's health check) warns when the usual CI time of the last 20 merged pull requests is over 10 minutes. The warning names the slowest job and says that Forge's guide lists the fixes. It only warns. It never stops a close or a merge. The 10 minutes is fixed; there is no setting for it. The board does not change. (Source: owner, 18 Nov 2026)
- In a repo with more than one test group, a pull request that changes 5 or fewer code files, and no lockfile or shared settings file, runs one test group instead of all of them. A larger change runs all groups. The required `tests` check keeps its name and its pass rule. A small change no longer fills every runner while other pull requests wait. (Source: a client team's CI audit of 150 pull requests, and the owner's decision, 18 Nov 2026)
- New apps made from the TypeScript starter run their API test files at the same time, not one after another. (Source: the same CI audit)
- New apps made from either starter run no browser tests on a pull request, also when a change to shared settings selects everything else. The full browser suite, with the rendered check of each screen, runs in the nightly full run. So a broken screen can merge, and the nightly run shows it the next morning. (Source: owner, 18 Nov 2026)
- The testing rules and the guide that Forge gives every repo change. They now say: run browser tests nightly, not in the pull request check (today's text says the opposite); test setup and helpers do not import the whole app, so a change does not select almost every test; each test file owns its data, so files can run at the same time; slow tests that depend on certain files run on a pull request only when those files change, and always nightly; within one CI job, the test picker never selects a test file twice, so when a job runs a project whole it does not run that project's files again as related tests. The guide also gets a list of fixes for a CI over 10 minutes, with what to preinstall on a self-hosted runner. (Source: the same CI audit, and the owner's decision, 18 Nov 2026)
- In a repo whose tests run in pull request CI, a queue of ready changes stops fighting. When the default branch moved after an item's close, and the item's changed files do not overlap the files the default branch gained, Forge merges the item with no new CI run, as repos that test on the laptop already do. When they overlap, the item merges after one combined run of only the tests related to both changes. `forge land --all` already tests up to five ready changes together in one merge train, so overlapping ready items share one run. A repo where GitHub itself requires each pull request to be up to date before it merges keeps today's new run. (Source: owner, 18 Nov 2026)
- In such a repo, each merge to the default branch starts one run of the tests related to what just merged. (Source: owner, 18 Nov 2026)
- While the default branch has a failed test result that no later full test run has cleared, Forge merges nothing: `forge merge` and `forge land` wait and say so in one line. A green result from a later narrow run does not clear it; a green full test run does. For a repo where a person merges, Forge's line that hands over the pull request says the default branch is red and asks the person to wait; Forge cannot stop a merge made on GitHub. To repair, the agent fixes the break in a fix, the owner merges that fix on GitHub, and the agent starts a full test run; merges go ahead when it is green. (Source: owner, 18 Nov 2026)
- Not in this story: test groups balanced by recorded time for Vitest (left out until a repo's slowest group is still twice its fastest); Forge code for runner images or for a table of slow tests and their inputs (guide text only); separate lint, type check and build checks (moved out of the faster-checks story; a later change adds at most one, only if the new time line shows that it helps); changes to how the merge train picks its members; the board; and the extra CI runs that Forge's record commits cause, which a separate fix (issue 1656) solves first.
- What each repo gets. A new repo gets all of this at setup. An existing repo gets the close line, the doctor warning, the one-group rule, the merge rules, the run on the default branch after each merge, and the new rules and guide when it upgrades and Forge refreshes its files (Forge owns the workflow file). A repo that tests on the laptop gets the red-branch wait from its nightly full run's result; it gets no run after each merge. Its own test scripts and test settings do not change. To take the starters' browser and parallel changes, the agent asks the owner and makes the change through a fix.
- Cost. No model call is added. Close and doctor each make one more GitHub request. Runner minutes go down for small changes and for pull requests that touch the web app. Each merge in a repo whose tests run in CI starts one run of the tests related to that merge; in exchange, waiting items no longer start a whole new run each time the default branch moves.

Design: none. Nothing on the board changes.

## Why

A client team measured its pull request CI far over 10 minutes. The audit found four causes: Forge's own record commits start most runs again (a separate fix, issue 1656); each small change fans out into every test group, and each group pays about a minute of setup; the whole browser suite runs on every pull request (16 minutes in one group); and test files cannot run at the same time. Nothing in Forge shows the CI time, so nobody sees it grow. And when several changes are ready at once, each merge moves the default branch, and every other waiting change merges it in and waits for a whole new CI run, even when they share no file.

## Done when

1. **After a pull request's checks finish, close prints its CI time, its runner minutes and its slowest job, and the health check warns when the usual CI time of recent merged pull requests is over 10 minutes.**
2. **In a repo with several test groups, a change of 5 or fewer code files with no lockfile or shared settings change runs one test group, a larger change runs all groups, and the required tests check keeps its name and its pass rule.**
3. **A new TypeScript starter app runs its API test files at the same time, and a new app from either starter runs no browser tests on a pull request while its nightly full run runs all of them.**
4. **The testing rules and the guide tell clients to run browser tests nightly instead of in the pull request check, keep test selection small, keep test files independent, never select a test file twice in one job, and list the fixes for a CI over 10 minutes.**
5. **In a repo whose tests run in pull request CI and where GitHub does not require pull requests to be up to date, Forge merges a ready item whose changed files do not overlap what the default branch gained since its close with no new CI run, and an item that overlaps after one combined run of the tests related to both changes.**
6. **In such a repo each merge to the default branch runs the tests related to it, and while the default branch has a failed test result that no later full run has cleared, Forge merges nothing and each waiting merge says so in one line.**

## Risks

Risks: none one-way. Each part reverts with its pull request. An existing repo's own test scripts change only through a fix that its owner agrees to.

Accepted limits, in plain words:
- A pull request can merge a broken screen. The nightly full run finds it the next morning. This is the owner's choice.
- A small change to a file that many tests use can select many tests. They then run in one group, which can be slower than today. The time line shows it.
- Forge's own repo uses the one-group rule too. Its tests reach Forge's code only through the `forge` command, so a one-file change can select much of the suite, and its one group can reach the 45-minute limit and fail. Close's time line and the health check then name that group as the slowest job, marked as timed out. (Source: owner, 18 Nov 2026)
- Forge takes the times from GitHub's check data. Whether that data counts the time a job waits for a free runner is not checked yet.
- The usual time (the median) includes pull requests that changed only documents. Their short runs lower it.
- The 10 minutes is the same for every repo. A setting comes only when a client asks for another number.
- Two changes that share no file can still break each other, for example when one renames a function that the other starts to use. On 28 Oct 2026 two such changes merged one after the other and left the default branch red, and Forge then added a new CI run for every waiting change. This story removes that run when the files do not overlap. Such a break is now found after the merge, by the run on the default branch and the nightly full run, not before. Until a full run is green again, Forge merges nothing. (Source: owner, 18 Nov 2026)
- The repair of a red default branch needs the owner once: Forge does not merge while the branch is red, so the owner merges the repair fix on GitHub. Forge also cannot stop a person who merges another pull request on GitHub while the branch is red; it only says so.
- In a repo where GitHub requires each pull request to be up to date before it merges, every waiting item still gets a new run after each merge, as today.

### Decisions

- **Which runs count (TIME).** Settled (source: owner, 18 Nov 2026): the slowest of the pull request's last 5 pushes. One GraphQL request reads the pull request's last 30 commits with their check runs; the last five commits that have any counted check run are its last five pushes (only a push's head gets runs). Forge reports the one whose CI took longest. `ponytail:` comment: 30 commits bound the request; a push of more than 30 commits shows fewer pushes. Runs that are skipped, neutral or cancelled, and the run named `Review pull request`, are left out.
- **The numbers.** Wall time = latest `completedAt` minus earliest `startedAt` of the counted runs of that push. Runner minutes = the sum of each run's time, rounded up to whole minutes per run as GitHub bills. Slowest job = the run with the longest time; a run with conclusion `timed_out` is marked `timed out`.
- **Close's line.** In `checks.wait`, when `_wait` returns passed or raises a refusal for a red check, print one line before returning or re-raising, for example `CI took 12 min 30 s (first job start to last job end), 41 runner minutes; slowest job: test group 2 of 6 (9 min 10 s).` Runs still in progress are not counted, and the line ends `; 2 jobs were still running` when there are any. When the request fails or nothing counts, print nothing; the time line never changes close's result. Land and merge also print it, because they call the same function. `close.py` does not change.
- **Doctor's warning.** One GraphQL request for the last 20 merged pull requests with the same 30-commit window. Per pull request, its time as above; the median over those with a time is the upper middle one (the 10th slowest of 20), so it is always one real pull request. When it is over 10 minutes (`BUDGET = 600` seconds, with a `ponytail:` comment naming a setting as the upgrade path), print `- Warning: The last <n> merged pull requests took a median of <m> min in CI, over the 10-minute budget. Its slowest job was <job> (<t>). Forge's guide lists the fixes for a slow CI.` No warning at or under 10 minutes, with no merged pull request, without `gh`, or when GitHub does not answer. Doctor's exit code does not change.
- **Where the time code goes.** A new module `src/forge/citime.py`, about 100 to 130 lines. `checks.py` and `doctor.py` get a few lines each. Nothing is stored. TIME changes no command, option, setting or step that an agent uses, so it has no guide text; RULES adds the guide lines.
- **Small change (GROUPS).** In the CI script, after `docs_only` and `tests_only`: list the changed paths with `git diff --name-only -z --no-renames BASE...HEAD -- . <DOCS_ONLY_EXCLUDES>`. First, the change is not small when any path is a lockfile (`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `uv.lock`, `poetry.lock`) or shared settings (`forge.toml`, any `package.json`, `pnpm-workspace.yaml`, `nx.json`, `pyproject.toml`, `setup.cfg`, `pytest.ini`, `conftest.py`, `tsconfig*.json`, `vitest.config.*`, `vitest.workspace.*`, `jest.config.*`, `playwright.config.*`, or anything under `.github/`). Then drop test files (the globs `only_docs` uses) and call it small when 5 or fewer paths remain. A branch that merged the default branch in is never small, as for `test-only`. Fixed in code; no setting. Write a new output `one-group=<tests_only or small>`; `test-only`, `platform-files` and `run-windows` keep their meaning.
- **The workflow (GROUPS).** `docs-check` exposes `one-group`; the matrix, the job name and `FORGE_GROUPS` read it instead of `test-only`; the one-group fold in `ships` matches. The gate does not change.
- **Forge's own repo (GROUPS).** Settled (source: owner, 18 Nov 2026): Forge's own repo uses the one-group rule too, with no exception for `repo = "forge-source"`. The 45-minute risk is an accepted limit; TIME's line and doctor's warning name the timed-out group.
- **The rules and guide (RULES).** `conventions/testing.md`: replace "Keep browser tests in the root test command" with: browser tests, with each screen's rendered check, run in the full test command and the nightly full run, not in `fast_test`; add the four rules (no whole-app imports in test setup and helpers; each test file owns its data; slow file-dependent tests run on a pull request only when those inputs change, always nightly; one CI job never selects a test file twice, so a project that runs whole is not passed again to a related-test runner, while other projects' related files still run). `skill.md`: correct `:1385-1387` and `:1432-1433`; add a section "When CI is over 10 minutes" that explains close's time line and doctor's warning, lists the fixes in order of measured gain (record-commit reruns fixed with #1656; browser tests nightly; selection that does not import the whole app; test files in parallel; one group for a small change, which is automatic; tools preinstalled on a self-hosted runner: git, Python 3.11, uv, Node and the package manager, Docker, and a warm package store, never `node_modules` or Playwright's browsers), and tells the agent to open the slowest job with `gh run view` before choosing one. `brief.md:652`: the rendered check runs with the browser tests, in the full run. The starter-specific lines (`skill.md:1404-1407` and the TypeScript starter's selection lines) change in STARTER.

Then run this checkout's `forge sync` and commit the refreshed `.claude/skills/forge/SKILL.md`, `.codex/skills/forge/SKILL.md` and standards copies with the part, naming them in the handoff. They are left out of every Scope; the parts that change the template are ordered by After, so their copies are too.
- **The starters (STARTER).** TypeScript starter: read why `fileParallelism` is false, make the API test files own their data (unique names and companies per file, no shared rows, no order between files), and remove `fileParallelism: false`; if the sign-up rate limit is the reason, raise it in the test stack only. The `stack` flag and the Docker steps stay as they are. A run without a base keeps the full browser suite. Record before-and-after times of one web change and one API change in the pull request text.
- **Merge with no overlap (MERGE).** In `merge.merge`, a CI-test item whose files do not overlap what the default branch gained, with no guide repair, merges like a laptop-test item without overlap: reset to the checked head, no push, no check wait, and no local test run (CI-test repos leave tests to CI). A guide repair counts only for a skills path whose merged content differs from both the item's head and the gained default branch, so the item's own guide edits do not count. With an overlap, keep today's push of the combined commit and wait; its pull request run of `forge test --change` selects the tests related to both changes (`fasttest.py:358-365`). When `land._up_to_date_rule` is true (imported inside the function, since `land` imports `merge`), keep today's behaviour for every item. The five-move stop stays. The merge train does not change.
- **Run on the default branch (MERGE).** Settled (source: owner, 18 Nov 2026): each push to the default branch runs the tests related to what just merged, and a red result stops merges until the default branch is green. In a CI-test repo the workflow adds `push: branches: [<default>]`. `docs-check`, the group jobs and the gate also run on `push`; on a push, `HEAD_SHA` is `github.sha` and `BASE_SHA` is `github.event.before`. Before the test step on a push, one workflow line points `refs/remotes/origin/<default>` at `github.event.before`, with a comment, so the unchanged `forge test --change` selects only what that merge brought; no new `forge test` option. The gate's name becomes `tests` on `pull_request` and `push` (`tests (other event)` stays for `pull_request_target`, so a skipped gate never passes a pull request's required check); the one-group fold matches. Its concurrency group never cancels a push run. `forge-pr-check` does not run on a push.
- **Red default branch (MERGE).** `merge.red(top) -> str` returns the red line or `""`. It walks up to ten first-parent commits from `origin/<default>`, newest first, and stops at the first commit with a green `forge-full-suite` status. The branch is red when any commit seen before that stop has a `tests` check run that ended `failure` or `timed_out`, or a failed `forge-full-suite` status. A pending run is not red, and a later green narrow run does not clear an earlier failure (`ponytail:` comment: ten commits, as in `fullrun.green`). `merge.merge` checks it before it merges: when red, print once `<default> has a failed test run (<link>). Forge waits for a green full test run before it merges <item>.`, check again every 60 seconds, and merge when it clears. After 90 minutes (shortened in tests by the `FORGE_CHECKS_WAIT` seam), refuse with a new `REFUSALS["red_default"]`: `("<default> has a failed test run, so Forge did not merge <item>.", "fix the break in a fix; the owner merges that fix on GitHub; then <fullrun.next_run(top)>, then forge merge <item>")`. In `land.py` the human hand-off line adds `<default> is red; wait for a green full test run before merging.` when `merge.red(top)` is not empty. Laptop-test repos read only `forge-full-suite`.
- **New and existing repos.** Each rule is tested on a new repo only. No record changes, so the upgrade test does not change. Existing repos get the workflow and CI script on upgrade and sync, the merge rules with the release, and the text with the normal refresh; their scripts change only through a fix.
