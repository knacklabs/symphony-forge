# Client pull requests finish CI in about 10 minutes, and Forge shows when they do not

5 parts · Risks: none one-way; seven accepted limits · New moving parts: a committed test timings file and a test sequencer in the TypeScript starter

## What changes for you

- After the checks of a pull request finish, close prints one line: how long CI took from the start of the first job to the end of the last job, how many runner minutes it used, and which job was slowest. It reports the slowest of the pull request's last 5 pushes, so a short rerun after Forge's record commit does not hide the run that tested the code. The line also splits the time into stages: waiting for a runner, setup, test selection, the tests and reruns, and it names each test group that went over the 10-minute budget, with its stages. When a check fails while other jobs still run, the line covers the jobs that ended and says how many were still running. Forge reads these times from GitHub. It stores nothing. (Source: owner, 18 Nov 2026)
- `forge doctor` (Forge's health check) warns when the usual CI time of the last 20 merged pull requests is over 10 minutes. The warning names the slowest job and says that Forge's guide lists the fixes. It only warns. It never stops a close or a merge. The 10 minutes is fixed; there is no setting for it. The board does not change. (Source: owner, 18 Nov 2026)
- In a repo with more than one test group, a pull request that changes 5 or fewer code files, and no lockfile, shared settings file, CI workflow file or Forge test-selection script, runs one test group instead of all of them. A larger change runs all groups. The required `tests` check keeps its name and its pass rule. A small change no longer fills every runner while other pull requests wait. (Source: a client team's CI audit of 150 pull requests, and the owner's decision, 18 Nov 2026)
- New apps made from the TypeScript starter run their API test files at the same time, not one after another. (Source: the same CI audit)
- In a new app made from the TypeScript starter that uses more than one test group, each group gets its Vitest test files by their recorded test times, not by file count, so the groups take about the same time. The times live in a timings file kept in the repo. A file with no recorded time goes to a fixed group chosen from its path, and never makes a run fail. Each group prints one line with its test time. One documented command refreshes the times on the developer's machine; the agent commits the new file through a fix. No CI job opens pull requests. The Python starter and Python test groups do not change; pytest groups keep their split by recorded time. (Source: owner, 18 Nov 2026, after a client measured its test groups at 1,113 to 2,257 seconds)
- New apps made from either starter run no browser tests on a pull request, also when a change to shared settings selects everything else. The full browser suite, with the rendered check of each screen, runs in the nightly full run. So a broken screen can merge, and the nightly run shows it the next morning. (Source: owner, 18 Nov 2026)
- The testing rules and the guide that Forge gives every repo change. They now say: run browser tests nightly, not in the pull request check (today's text says the opposite); test setup and shared helpers do not import the app's entry, so a change does not select almost every test; test selection follows the real import graph and never drops a changed file to make the selection smaller, so integration tests are still selected; before you split tests into separate runtimes, check whether the test tool already gives each file its own runtime (Cloudflare's Vitest plugin does), and then run files at the same time with a limited number of workers; if shared state forces files to run one by one, fix that shared reset first; each test file owns its data, so files can run at the same time; slow tests that depend on certain files run on a pull request only when those files change, and always nightly, through a table of each slow test and the input paths that trigger it, where excludes use `**/<file>` and a test that starts scripts names its inputs, because it has no import to follow; within one CI job, the test picker never selects a test file twice, so when a job runs a project whole it does not run that project's files again as related tests; a test of test selection runs the whole chain, from the CI step that skips document-only changes to the picker inside it. The guide also gets a list of fixes for a CI over 10 minutes: what to preinstall on a self-hosted runner, how to size runner slots, to set the number of test groups to the number of fast runner slots, and what to do before a runner machine goes away. (Source: the same CI audit, and the owner's decision, 18 Nov 2026)
- Not in this story: Forge code for runner images or for a table of slow tests and their inputs (guide text only); separate lint, type check and build checks (moved out of the faster-checks story; a later change adds at most one, only if the new time line shows that it helps); the merge queue (its own story); the board; and the extra CI runs that Forge's record commits cause, which a separate fix (issue 1656) solves first.
- What each repo gets. A new repo gets all of this at setup. An existing repo gets the close line, the doctor warning, the one-group rule and the new rules and guide when it upgrades and Forge refreshes its files (Forge owns the workflow file). Its own test scripts and test settings do not change. To take the starters' browser, parallel and time-based group changes, the agent asks the owner and makes the change through a fix; the guide says which starter files to copy.
- Cost. No model call is added. Close makes two more GitHub requests (the pull request's recent pushes and the jobs of the measured push), and doctor two or three. Runner minutes go down for small changes and for pull requests that touch the web app.

Design: none. Nothing on the board changes.

## Why

A client team measured its pull request CI far over 10 minutes. The audit found four causes: Forge's own record commits start most runs again (a separate fix, issue 1656); each small change fans out into every test group, and each group pays about a minute of setup; the whole browser suite runs on every pull request (16 minutes in one group); test files cannot run at the same time; and the test groups split files by count, so one group took twice as long as another. Nothing in Forge shows the CI time, so nobody sees it grow.

## Done when

1. **After a pull request's checks finish, close prints its CI time, its runner minutes and its slowest job, and the health check warns when the usual CI time of recent merged pull requests is over 10 minutes.**
2. **In a repo with several test groups, a change of 5 or fewer code files with no lockfile or shared settings change runs one test group, a larger change runs all groups, and the required tests check keeps its name and its pass rule.**
3. **A new TypeScript starter app runs its API test files at the same time, and a new app from either starter runs no browser tests on a pull request while its nightly full run runs all of them.**
4. **The testing rules and the guide tell clients to run browser tests nightly instead of in the pull request check, keep test selection small, keep test files independent, check the test tool's own file isolation before splitting test runtimes, run slow tests only when their input files change, never select a test file twice in one job, test the whole selection chain, and list the fixes for a CI over 10 minutes.**
5. **In a new TypeScript starter app with more than one test group, each group gets its test files by their recorded times, a file with no recorded time still runs, each group prints its test time, and one documented command refreshes the recorded times.**

## Risks

Risks: none one-way. Each part reverts with its pull request. An existing repo's own test scripts change only through a fix that its owner agrees to.

Accepted limits, in plain words:
- A pull request can merge a broken screen. The nightly full run finds it the next morning. This is the owner's choice.
- A small change to a file that many tests use can select many tests. They then run in one group, which can be slower than today. The time line shows it.
- Forge's own repo uses the one-group rule too. Its tests reach Forge's code only through the `forge` command, so a one-file change can select much of the suite, and its one group can reach the 45-minute limit and fail. Close's time line and the health check then name that group as the slowest job, marked as timed out. (Source: owner, 18 Nov 2026)
- Forge takes the times from GitHub's check data. Whether that data counts the time a job waits for a free runner is not checked yet.
- The usual time (the median) includes pull requests that changed only documents. Their short runs lower it.
- The 10 minutes is the same for every repo. A setting comes only when a client asks for another number.
- Recorded test times come from the machine that ran the refresh command and grow old as tests change. The groups are then less even until someone refreshes them. Nothing refreshes them automatically. (Source: owner, 18 Nov 2026)

### Decisions

- **Which runs count (TIME).** Settled (source: owner, 18 Nov 2026): the slowest of the pull request's last 5 pushes. One GraphQL request reads the pull request's last 30 commits with their check runs; the last five commits that have any counted check run are its last five pushes (only a push's head gets runs). Forge reports the one whose CI took longest. `ponytail:` comment: 30 commits bound the request; a push of more than 30 commits shows fewer pushes. Runs that are skipped, neutral or cancelled, and the run named `Review pull request`, are left out, except a cancelled test job that ran to its time limit: it counts, marked `timed out`, by the same reading of the job's `timeout-minutes` that `checks._tests_timeout` (`src/forge/checks.py:287-300`) already uses; reuse that rule rather than a second one.
- **The numbers.** Wall time = latest `completedAt` minus earliest `startedAt` of the counted runs of that push. Runner minutes = the sum of each run's time, rounded up to whole minutes per run as GitHub bills. Slowest job = the run with the longest time; a run with conclusion `timed_out`, or a cancelled test job at its time limit, is marked `timed out`.
- **Stages against the budget (TIME).** The line splits the measured push's time into stages and shows them against the fixed 10-minute budget. Forge reads the jobs of that push's `forge` workflow run with one request (`repos/{owner}/{repo}/actions/runs/<id>/jobs?filter=all&per_page=100`, which also lists earlier attempts, read with `gh api --paginate` so a large rerun is not cut at one page), and measures the slowest test group's path: queue = its job's `started_at` minus `created_at`; setup = all its steps except `parent-tests` and the test step (checkout, setup actions, cache, Node, installs, also those after `parent-tests`); selection = the `docs-check` job's time plus the `parent-tests` step; run = the test step, which also holds any picking that the test command itself does, and the line calls it `tests (with in-step selection)`; retries = the time of earlier attempts of the run (`run_attempt` above 1). The same jobs give every test group's own stages; each group whose path (queue, setup, selection, run, retries) is over the 10-minute budget gets one extra line, for example `test group 3 of 6 over budget: queue 4 min, setup 2 min, selection 1 min, tests 9 min.` Doctor reads the jobs only for the median pull request (one or two more requests). The 50% time-limit warning is dropped: it needed a second reading of the workflow, and the stage budget covers it.
- **Close's line.** In `checks.wait`, when `_wait` returns passed or raises a refusal for a red check, print one line before returning or re-raising, for example `CI took 14 min against a 10-minute budget: queue 3 min, setup 2 min, selection 1 min, tests 7 min, retries 1 min; 41 runner minutes; slowest job: test group 2 of 6 (9 min 10 s).` A stage that cannot be read is left out of the line. Runs still in progress are not counted, and the line ends `; 2 jobs were still running` when there are any. When the request fails or nothing counts, print nothing; the time line never changes close's result. Land and merge also print it, because they call the same function. `close.py` does not change.
- **Doctor's warning.** One GraphQL request for the last 20 merged pull requests with the same 30-commit window. Per pull request, its time as above; the median over those with a time is the upper middle one (the 10th slowest of 20), so it is always one real pull request. When it is over 10 minutes (`BUDGET = 600` seconds, with a `ponytail:` comment naming a setting as the upgrade path), print `- Warning: The last <n> merged pull requests took a median of <m> min in CI, over the 10-minute budget. Its slowest job was <job> (<t>). Forge's guide lists the fixes for a slow CI.` No warning at or under 10 minutes, with no merged pull request, without `gh`, or when GitHub does not answer. Doctor's exit code does not change.

- **Time-based groups (TIMEGROUPS).** Settled (source: owner, 18 Nov 2026), TypeScript starter and Vitest only:
  - `scripts/test-groups.mjs` (new, plain Node, no Vitest import): `place(files, timings, index, count)` returns the files of group `index`. `count` is already capped by the group rule below. Timed files go longest first to the group with the least time so far. Files with no time go, in the order of a stable hash of their repo-relative paths, first to any group in use that is still empty, then to group `hash(path) % count`, so no group in use is empty. Every group computes the same placement, so each file runs in exactly one group. A missing or unreadable timings file means every file is untimed; it never throws.
  - `scripts/timed-sequencer.mjs` (new): a `BaseSequencer` subclass whose `shard(files)` calls `place` with Vitest's shard index and count. The Vitest configs that the TypeScript starter shards (`apps/web/vitest.config.ts`, `apps/api/vitest.config.ts`) set `sequence: { sequencer }`. The Python starter copies the TypeScript starter's `apps/web` files (`init._starter_files`, `src/forge/init.py:202-219`), and files under `starter-python` override them; so add `src/forge/templates/starter-python/apps/web/vitest.config.ts` as an unchanged copy of today's web config, and the Python starter's web tests keep Vitest's own split.
  - `test-timings.json` (new, committed at the starter root): repo-relative path to seconds, seeded by the builder's own refresh.
  - The one refresh command is `node scripts/test.mjs --timings`: the starter's own full run (no base), with its installs and Docker stack, where each Vitest run also writes Vitest's JSON report, and the script then writes each file's duration into `test-timings.json`. No separate script. The guide documents it; the agent runs it and commits the file through a fix. No CI job writes or uploads timings, and none opens a pull request.
  - `scripts/test.mjs` takes `--group <i>/<n>`. When `n` is above 1, before each Vitest run it counts that run's files (`vitest list --filesOnly` with the same config and filters), because Vitest refuses `--shard` with more groups than files. The group rule (owner, 18 Nov 2026): a run uses as many groups as it has files, never more; a job whose group number is above that count passes with nothing to do; a run that discovers zero files fails with one clear line (`No test files found for <config>; check its include pattern.`); and files are placed only across the groups in use, so no group in use is empty. So the run gets `--shard=<i>/<min(n, files)>`, a group above the file count skips that run and passes, and zero files fail the job. All groups count the same files, so the placement stays the same in every group. It runs its own setup in every group, because each group is a separate runner (install, Prisma generate, the Docker stack and its company setup), and runs lint, type check, build and the health check only in group 1, and prints `Test group <i> of <n> time: <s> s` at the end, also on failure. Init writes the starter's settings as `test = "node scripts/test.mjs --group {group}/{groups}"` and `fast_test = "node scripts/test.mjs {base} --group {group}/{groups}"`, so Forge's group warning no longer applies.
  - Tests that start the placement or the starter's test script (the TIMEGROUPS test, and the starter tests that run `scripts/test.mjs`) pass their own `FORGE_GROUP` and `FORGE_GROUPS` (or `--group`) every time, so a CI job's group cannot leak into them.
  - The Python starter is unchanged; its API tests are pytest.
- **More rules (RULES).** In `conventions/testing.md` and the guide's slow-CI section: (a) narrow the fan-out of related-test selection at its source: shared test setup files and helpers must not import the whole app (Vitest selects every project's tests when a setup file's dependency changes); never remove changed source files from `vitest related` or swap them for area names to narrow the selection, because that drops real dependencies, such as a shared test that imports an API through the package index; (b) before adding any launcher that starts one process per runtime, check that the runner's own pool already isolates each file: with Vitest's default `isolate: true`, Cloudflare's Vitest plugin 1.4.4 gives each file its own pool worker, Miniflare and temporary storage, and it was `fileParallelism: false` that forced one worker; so turn file parallelism on with a bounded `maxWorkers` first; bound the total test workers in one job by its cores and by the measured peak memory, including memory-backed temporary storage (a launcher with many processes started about 7 workers on 4 cores);
