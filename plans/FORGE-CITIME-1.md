# Client pull requests finish CI in about 10 minutes, and Forge shows when they do not

5 parts · Risks: none one-way; seven accepted limits · New moving parts: a committed test timings file and a test sequencer in the TypeScript starter

## What changes for you

- After the checks of a pull request finish, close prints one line: how long CI took from the start of the first job to the end of the last job, how many runner minutes it used, and which job was slowest. It reports the slowest of the pull request's last 5 pushes, so a short rerun after Forge's record commit does not hide the run that tested the code. When a check fails while other jobs still run, the line covers the jobs that ended and says how many were still running. Forge reads these times from GitHub. It stores nothing. (Source: owner, 18 Nov 2026)
- `forge doctor` (Forge's health check) warns when the usual CI time of the last 20 merged pull requests is over 10 minutes. The warning names the slowest job and says that Forge's guide lists the fixes. It only warns. It never stops a close or a merge. The 10 minutes is fixed; there is no setting for it. The board does not change. (Source: owner, 18 Nov 2026)
- In a repo with more than one test group, a pull request that changes 5 or fewer code files, and no lockfile or shared settings file, runs one test group instead of all of them. A larger change runs all groups. The required `tests` check keeps its name and its pass rule. A small change no longer fills every runner while other pull requests wait. (Source: a client team's CI audit of 150 pull requests, and the owner's decision, 18 Nov 2026)
- New apps made from the TypeScript starter run their API test files at the same time, not one after another. (Source: the same CI audit)
- In a new app made from the TypeScript starter that uses more than one test group, each group gets its Vitest test files by their recorded test times, not by file count, so the groups take about the same time. The times live in a timings file kept in the repo. A file with no recorded time goes to a fixed group chosen from its path, and never makes a run fail. Each group prints one line with its test time. One documented command refreshes the times on the developer's machine; the agent commits the new file through a fix. No CI job opens pull requests. The Python starter and Python test groups do not change; pytest groups keep their split by recorded time. (Source: owner, 18 Nov 2026, after a client measured its test groups at 1,113 to 2,257 seconds)
- New apps made from either starter run no browser tests on a pull request, also when a change to shared settings selects everything else. The full browser suite, with the rendered check of each screen, runs in the nightly full run. So a broken screen can merge, and the nightly run shows it the next morning. (Source: owner, 18 Nov 2026)
- The testing rules and the guide that Forge gives every repo change. They now say: run browser tests nightly, not in the pull request check (today's text says the opposite); test setup and shared helpers do not import the app's entry, so a change does not select almost every test, and the fix maps tests to the leaf areas they use rather than only cutting the import, so integration tests are still selected; when a test runner keeps one runtime per test project (for example Cloudflare's Vitest plugin), the test files are split across several projects so the runtimes run side by side; each test file owns its data, so files can run at the same time; slow tests that depend on certain files run on a pull request only when those files change, and always nightly, through a table of each slow test and the input paths that trigger it, where excludes use `**/<file>` and a test that starts scripts names its inputs, because it has no import to follow; within one CI job, the test picker never selects a test file twice, so when a job runs a project whole it does not run that project's files again as related tests. The guide also gets a list of fixes for a CI over 10 minutes, with what to preinstall on a self-hosted runner. (Source: the same CI audit, and the owner's decision, 18 Nov 2026)
- Not in this story: Forge code for runner images or for a table of slow tests and their inputs (guide text only); separate lint, type check and build checks (moved out of the faster-checks story; a later change adds at most one, only if the new time line shows that it helps); the merge queue (its own story); the board; and the extra CI runs that Forge's record commits cause, which a separate fix (issue 1656) solves first.
- What each repo gets. A new repo gets all of this at setup. An existing repo gets the close line, the doctor warning, the one-group rule and the new rules and guide when it upgrades and Forge refreshes its files (Forge owns the workflow file). Its own test scripts and test settings do not change. To take the starters' browser, parallel and time-based group changes, the agent asks the owner and makes the change through a fix; the guide says which starter files to copy.
- Cost. No model call is added. Close and doctor each make one more GitHub request. Runner minutes go down for small changes and for pull requests that touch the web app.

Design: none. Nothing on the board changes.

## Why

A client team measured its pull request CI far over 10 minutes. The audit found four causes: Forge's own record commits start most runs again (a separate fix, issue 1656); each small change fans out into every test group, and each group pays about a minute of setup; the whole browser suite runs on every pull request (16 minutes in one group); test files cannot run at the same time; and the test groups split files by count, so one group took twice as long as another. Nothing in Forge shows the CI time, so nobody sees it grow.

## Done when

1. **After a pull request's checks finish, close prints its CI time, its runner minutes and its slowest job, and the health check warns when the usual CI time of recent merged pull requests is over 10 minutes.**
2. **In a repo with several test groups, a change of 5 or fewer code files with no lockfile or shared settings change runs one test group, a larger change runs all groups, and the required tests check keeps its name and its pass rule.**
3. **A new TypeScript starter app runs its API test files at the same time, and a new app from either starter runs no browser tests on a pull request while its nightly full run runs all of them.**
4. **The testing rules and the guide tell clients to run browser tests nightly instead of in the pull request check, keep test selection small, keep test files independent, run separate test runtimes side by side, run slow tests only when their input files change, never select a test file twice in one job, and list the fixes for a CI over 10 minutes.**
5. **In a new TypeScript starter app with more than one test group, each group gets its test files by their recorded times, a file with no recorded time still runs, each group prints its test time, and one documented command refreshes the recorded times.**

## Risks

Risks: none one-way. Each part reverts with its pull request. An existing repo's own test scripts change only through a fix that its owner agrees to.

Accepted limits, in plain words:
- A pull request can merge a broken screen. The nightly full run finds it the next morning. This is the owner's choice.
- A small change to a file that many tests use can select many tests. They then run in one group, which can be slower than today. The time line shows it.
- Forge's own repo uses the one-group rule too. Its tests reach Forge's code only through the `forge` command, so a one-file change can select much of the suite, and its one group can reach the 45-minute limit and fail. Close's time line and the health check then name that group as the slowest job, marked as timed out. (Source: owner, 18 Nov 2026)
- Forge takes the times from GitHub's check data. Whether that data counts the time a job waits for a free runner is not checked yet.
- The usual time (the median) includes pull requests that changed only documents. Their short runs lower it.
- The 10 minutes is the same for every repo. A setting comes only when a client asks for another number.
- Recorded test times come from the machine that ran the refresh command and grow old as tests change. The groups are then less even until someone refreshes them. Nothing refreshes them automatically. (Source: owner, 18 Nov 2026)

### Decisions

- **Which runs count (TIME).** Settled (source: owner, 18 Nov 2026): the slowest of the pull request's last 5 pushes. One GraphQL request reads the pull request's last 30 commits with their check runs; the last five commits that have any counted check run are its last five pushes (only a push's head gets runs). Forge reports the one whose CI took longest. `ponytail:` comment: 30 commits bound the request; a push of more than 30 commits shows fewer pushes. Runs that are skipped, neutral or cancelled, and the run named `Review pull request`, are left out, except a cancelled test job that ran to its time limit: it counts, marked `timed out`, by the same reading of the job's `timeout-minutes` that `checks._tests_timeout` (`src/forge/checks.py:287-300`) already uses; reuse that rule rather than a second one.
- **The numbers.** Wall time = latest `completedAt` minus earliest `startedAt` of the counted runs of that push. Runner minutes = the sum of each run's time, rounded up to whole minutes per run as GitHub bills. Slowest job = the run with the longest time; a run with conclusion `timed_out`, or a cancelled test job at its time limit, is marked `timed out`.
- **Close's line.** In `checks.wait`, when `_wait` returns passed or raises a refusal for a red check, print one line before returning or re-raising, for example `CI took 12 min 30 s (first job start to last job end), 41 runner minutes; slowest job: test group 2 of 6 (9 min 10 s).` Runs still in progress are not counted, and the line ends `; 2 jobs were still running` when there are any. When the request fails or nothing counts, print nothing; the time line never changes close's result. Land and merge also print it, because they call the same function. `close.py` does not change.
- **Doctor's warning.** One GraphQL request for the last 20 merged pull requests with the same 30-commit window. Per pull request, its time as above; the median over those with a time is the upper middle one (the 10th slowest of 20), so it is always one real pull request. When it is over 10 minutes (`BUDGET = 600` seconds, with a `ponytail:` comment naming a setting as the upgrade path), print `- Warning: The last <n> merged pull requests took a median of <m> min in CI, over the 10-minute budget. Its slowest job was <job> (<t>). Forge's guide lists the fixes for a slow CI.` No warning at or under 10 minutes, with no merged pull request, without `gh`, or when GitHub does not answer. Doctor's exit code does not change.
- **Where the time code goes.** A new module `src/forge/citime.py`, about 100 to 130 lines. `checks.py` and `doctor.py` get a few lines each. Nothing is stored. TIME changes no command, option, setting or step that an agent uses, so it has no guide text; RULES adds the guide lines.
- **Small change (GROUPS).** In the CI script, after `docs_only` and `tests_only`: list the changed paths with `git diff --name-only -z --no-renames BASE...HEAD -- . <DOCS_ONLY_EXCLUDES>`. First, the change is not small when any path is a lockfile (`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `uv.lock`, `poetry.lock`) or shared settings (`forge.toml`, any `package.json`, `pnpm-workspace.yaml`, `nx.json`, `pyproject.toml`, `setup.cfg`, `pytest.ini`, `conftest.py`, `tsconfig*.json`, `vitest.config.*`, `vitest.workspace.*`, `jest.config.*`, `playwright.config.*`, or anything under `.github/`). Then drop test files (the globs `only_docs` uses) and call it small when 5 or fewer paths remain. A branch that merged the default branch in is never small, as for `test-only`. Fixed in code; no setting. Write a new output `one-group=<tests_only or small>`; `test-only`, `platform-files` and `run-windows` keep their meaning.
- **The workflow (GROUPS).** `docs-check` exposes `one-group`; the matrix, the job name and `FORGE_GROUPS` read it instead of `test-only`; the one-group fold in `ships` matches. The gate does not change.
- **Forge's own repo (GROUPS).** Settled (source: owner, 18 Nov 2026): Forge's own repo uses the one-group rule too, with no exception for `repo = "forge-source"`. The 45-minute risk is an accepted limit; TIME's line and doctor's warning name the timed-out group.
- **The rules and guide (RULES).** `conventions/testing.md`: replace "Keep browser tests in the root test command" with: browser tests, with each screen's rendered check, run in the full test command and the nightly full run, not in `fast_test`; add the rules (no whole-app imports in test setup and helpers, with (a) below; separate runtimes side by side, (b) below; the slow-test input table, (c) below; each test file owns its data; slow file-dependent tests run on a pull request only when those inputs change, always nightly; one CI job never selects a test file twice, so a project that runs whole is not passed again to a related-test runner, while other projects' related files still run). `skill.md`: correct `:1385-1387` and `:1432-1433`; add a section "When CI is over 10 minutes" that explains close's time line and doctor's warning, lists the fixes in order of measured gain (record-commit reruns fixed with #1656; browser tests nightly; selection that does not import the whole app; test files in parallel; one group for a small change, which is automatic; tools preinstalled on a self-hosted runner: git, Python 3.11, uv, Node and the package manager, Docker, and a warm package store, never `node_modules` or Playwright's browsers; and a warning against burstable cloud instance types such as AWS t2 and t3, which run out of CPU credits and then run the same tests several times slower (a client measured steal time above user time and about 4 times slower tests, which pushed one test group past 60 minutes); recommend fixed-performance instance types, and say how to spot the problem: a high `st` (steal) value in `top` or `vmstat` while tests run), and tells the agent to open the slowest job with `gh run view` before choosing one. `brief.md:652`: the rendered check runs with the browser tests, in the full run. - **Time-based groups (TIMEGROUPS).** Settled (source: owner, 18 Nov 2026), TypeScript starter and Vitest only:
  - `scripts/test-groups.mjs` (new, plain Node, no Vitest import): `place(files, timings, index, count)` returns the files of group `index`. Timed files go longest first to the group with the least time so far; a file with no time goes to group `hash(path) % count`, using a stable hash of its repo-relative path. Every group computes the same placement, so each file runs in exactly one group. A missing or unreadable timings file means every file is untimed; it never throws.
  - `scripts/timed-sequencer.mjs` (new): a `BaseSequencer` subclass whose `shard(files)` calls `place` with Vitest's shard index and count. The Vitest configs that the starter shards (`apps/web/vitest.config.ts`, `apps/api/vitest.config.ts`) set `sequence: { sequencer }`.
  - `test-timings.json` (new, committed at the starter root): repo-relative path to seconds, seeded by the builder's own refresh.
  - `scripts/test-timings.mjs` (new): the one refresh command, `node scripts/test-timings.mjs`. It runs the full Vitest suites with Vitest's JSON reporter and writes each file's duration into `test-timings.json`. The guide documents it; the agent runs it and commits the file through a fix. No CI job writes or uploads timings, and none opens a pull request.
  - `scripts/test.mjs` takes `--group <i>/<n>`. When `n` is above 1, it adds `--shard=<i>/<n>` to each Vitest run, runs the steps that are not Vitest (install, lint, type check, build, Docker stack, health check) only in group 1, and prints `Test group <i> of <n> time: <s> s` at the end, also on failure. Init writes the starter's settings as `test = "node scripts/test.mjs --group {group}/{groups}"` and `fast_test = "node scripts/test.mjs {base} --group {group}/{groups}"`, so Forge's group warning no longer applies.
  - The Python starter is unchanged; its API tests are pytest.
- **More rules (RULES).** In `conventions/testing.md` and the guide's slow-CI section: (a) shared test setup and helpers must not import the app's entry; to fix a selection that picks almost every test, map tests to the leaf areas they use, and do not only cut the import, because integration tests then stop being selected; (b) when a test runner keeps one runtime per test project (such as Cloudflare's Vitest plugin), split the files that share one runtime across several projects (round robin), so the runtimes run side by side, and note that files inside one runtime still share state; (c) gate slow tests (harness, build, bundle checks) with a table of each test and the input paths that trigger it: they run on a pull request only when an input changes, and always nightly; excludes use `**/<file>`, because each Vitest project collects paths from its own root; a test that starts scripts has no import to follow, so a changed input must add it explicitly.
