# Client apps feel finished without anyone asking for polish

2 parts · Risks: none one-way · New moving parts: none

## What changes for you

- In a new client app, the shared buttons, switches and checkboxes shrink a little while they are pressed, so the screen answers a click at once. The link style of button stays as it is. (Source: your request, 10 Nov 2026)
- The app's theme file holds one motion curve and two shared speeds: a quick one for hover and press, and a slightly slower one for dialogs, side panels and the sidebar. Every shared control takes them, and no shared part animates every property at once. Two things stay as they are on purpose: the check mark inside a checkbox appears at once, and notifications keep their own motion. (Source: your request, 10 Nov 2026)
- When a person's device asks for reduced motion, the loading placeholder stops pulsing and panels no longer slide or zoom. One rule in the theme file does this for every animation and every fade written in style sheets, including screens built later. Spinners keep turning, because they show that work is in progress. The rule cannot reach motion that a script starts. For that, the written rules tell the agent to read the device setting, and the review checks it. (Source: your request, 10 Nov 2026)
- A new app gets three small shared parts for the loading, empty and error states of a screen, with tests that show each one draws its text and keeps its accessible role. The written rules tell the agent to use them wherever an app has them. (Source: your request, 10 Nov 2026)
- Close refuses a changed UI file that animates all properties at once. This is the only motion check that code can prove exactly. It names the file, the line and the rule, and shows the one comment that sets the rule aside with a reason. It also runs on design drafts, as the other design checks do, and when Node is not installed it prints one line and skips, as they do. (Source: your request, 10 Nov 2026; the narrow check is the planner's choice, see Notes)
- Whether a button-like part has a pressed state, and whether a new animation or transition respects reduced motion, are review rules, not close checks. A text pattern cannot tell a missing pressed state from one written in a style sheet, or a harmless transition from a sliding panel, without refusing correct work. The review reports these as findings. (Source: your request, 10 Nov 2026; planner's choice)
- An existing client app keeps every app file as it is. When it upgrades and refreshes its Forge files, it gets the new check and the new written rules. The agent changes the app's shared parts in a normal change, when the check reports a problem in a file the change touches or when the person asks. For the three state parts and the motion section of the theme file, the written rules point the agent to the finished files that Forge ships, to copy. Forge never rewrites the app's own files. (Source: your request, 10 Nov 2026; the existing-app path is the planner's recommendation, see Notes)
- Colours, fonts, corner size, spacing and shadows are not part of this plan. They belong to the theme story. (Source: your request, 10 Nov 2026)

Design: none (this story adds no screen and changes none; it changes shared parts and the theme file of the starter, and Forge ships parts, rules and checks, not screens; owner rule, 31 Oct 2026)

## Why

People who use Forge do not know what to ask for to make an app look finished, and they must not need to. Today the polish rules are written text that the agent may or may not follow. The starter's shared parts have no pressed state, animate every property, share no motion speed or curve, and ignore the reduced-motion setting. This plan puts the polish inside the shared parts that every new app starts with, so each screen built from them has it with no instruction and no model cost.

## Done when

1. **In a new client app, shared buttons, switches and checkboxes show a pressed state, no shared part animates all properties, and every shared control takes its curve and speed from the theme file, except the named ones.**
2. **In a new client app, a device that asks for reduced motion sees the loading placeholder stop pulsing and panels stop sliding and zooming, and a browser test that ships with the app proves it. Motion that a script starts is covered by a written rule and the review, not by this one rule.**
3. **A new client app has shared loading, empty and error parts, a test that shows each draws its text and role, and a written rule to use them wherever an app has them.**
4. **Close refuses a changed UI file that animates all properties, and names the file, the line and the rule; a comment with a reason sets it aside. The review reports a button-like part with no pressed state, and a new animation or transition that ignores reduced motion.**
5. **After an upgrade and a refresh of Forge files, an existing client app has every app file unchanged and gets the check and the written rules. The agent copies the finished parts from Forge's files when a change needs them or the person asks.**

## Risks

Risks: none one-way. Each part reverts with its pull request. Nothing is deleted and no data changes.

Trade-off: a file is checked whole. In an existing app, the first change that touches an old shared part that animates all properties (for example a switch) is refused until the part is fixed or the rule is set aside with a reason. The refusal shows the fix. This is how the existing design checks work.

Trade-off: the pressed-state and reduced-motion rules depend on the review, not on a check. The review can miss one. The parts and the theme file carry both for every new app, so the miss can only come from a hand-written control or animation.

Trade-off: the one reduced-motion rule changes style sheet animations and transitions. It does not change an animation that a script starts (for example with the Web Animations API or the Motion library). The written rule says such code must read the device setting, and the review checks it. Nothing proves it by code.

Trade-off: the proof that the three state parts draw their text and role is a test inside the starter, which runs with the app's own web tests and in the nightly full starter run. Forge's own per-pull-request tests only check that the files and the test exist, because they do not install the app's packages. The nightly run was not run for this plan.

Trade-off: the new check shares Forge's existing design script, so it also applies to design drafts and is skipped with one line on a computer without Node. A draft that uses `transition-all` is refused when the plan is read. The waiver comment works there too.

Model cost: none. The check is a text pattern in the design script that close already runs, and the parts and tests are static code. Nothing is measured; the extra close time is an estimate of well under a second.
