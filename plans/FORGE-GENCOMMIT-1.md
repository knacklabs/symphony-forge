# Stop committing generated API types in Python apps

2 parts · Risks: none one-way · New moving parts: none

## What changes for you

- A new Python client app no longer keeps two files in git: the API contract file (the file that lists every server call of the app) and the TypeScript types that a script makes from it. Git ignores both files. The type check and the tests make them first, so a fresh copy of the app works without them. (Source: your decision, 11 Nov 2026: "Stop committing them")
- Parts that change the API no longer list these two files, so these two files no longer make parts wait for each other. Parts that share other files still wait. For example, every part that adds a module changes the file where each module is registered.
- The web build does not make the two files. It does not need them, and the step that builds the web app inside the container has no Python. (Source: the planner's choice; see the open question in Notes)
- A fast test of a change to the API's code still makes the types and runs the web type check and the browser tests, as it does today when the committed types change. It now does this for every change to the API's code, also one that leaves the contract the same, so those fast tests take a few minutes longer (estimate, not measured). A change to the API's tests only runs only the API checks, as today.
- Forge's stack guidance gets one rule for both stacks: a file that a script makes from the app's own code every time stays out of git. Database migrations and lock files are records, so they stay in git. The TypeScript starter already follows this rule, so nothing in it changes.
- An existing Python client app keeps its committed files when it upgrades and syncs. Forge changes no app file, and the app works as today. The guide gives the agent the steps to move the app over in one small fix, and says when to start it. The steps take only these two files out of git. Then they delete the two files on disk and run the tests, which must make them again. This is safe because a script makes both files from the app's code each time.
- The change adds no model call. Model cost: none. Each type check takes a few seconds more, because it makes the two files first (estimate, not measured).

## Why

In a client repo with several developers, every API part of two stories listed the same two files in its scope: the API contract file and the types made from it. Both files were kept in git. Forge does not start two parts that change the same file, so parts of different stories waited for each other. Forge's own guidance caused this: the Python guidance says to commit both files after each API change, and the Python starter ships both files in git.

You decided on 11 Nov 2026 to stop committing them. Not chosen: letting files marked as generated stop counting as shared between parts.

## Done when

1. **A new Python client app does not keep the API contract file or its generated types in git, and Git ignores both. The type check and the tests make them first, and the full tests pass on a fresh copy of the app without them. The tests that check the API contract still check it, on the contract that the tests make.**
2. **A fast test of a change to the API's code makes the types and runs the web type check and the browser tests, and it fails when the change breaks a web type. A fast test of a web change makes the types before its type check. A change to the API's tests only still runs only the API checks.**
3. **Forge's stack guidance says, for both stacks, that a file a script makes from the app's code every time stays out of git, and that migrations and lock files stay in git. The TypeScript starter is checked against this rule and keeps no such file in git.**
4. **An existing Python client app that upgrades and syncs keeps its two committed files, and Forge changes no app file.**
5. **The guide gives the agent the steps to move an existing Python app over in one small fix, and says when to start it. The steps take only the two files out of git, then delete only those two files on disk and run the tests, which make them again. A new repo gets the steps at setup, and an existing repo gets them on sync.**

## Risks

Risks: none one-way. Each part reverts with its pull request. No data changes. The move-over steps delete only the two generated files on disk, and the tests make them again from the app's code.

Trade-offs, in plain words:
- A reviewer no longer sees an API change as a change in the contract file. The review still sees the route and schema code that makes the contract, and the type check still fails when a web type no longer matches the API. Nothing new keeps a copy of the contract to compare against.
- On a fresh copy of the app, the code editor shows the shared API types as missing until someone runs the type check, the tests, or the script that makes the two files. The starter's README says to run that script once after a clone.
- A fast test of a change to the API's code that leaves the contract the same now also runs the web type check and the browser tests. Today it runs only the API checks.
- In an existing app, a branch that changed either file gets a merge conflict once the move-over fix merges. The guide says how to settle it: keep the removal from git and run the tests.

### Decisions

- Where the files are made. `typecheck` starts with `corepack pnpm run api-types && `. `test` does not change: it still runs `api-types` first, so the full run makes the files twice, a few seconds (estimate). `build` does not change (see the container above). No `pre` scripts, no `postinstall`.
- Setup and generation order. Setup writes and commits only the template's own files, and the template holds neither generated file, so setup never names them. They are first made later, inside the app, by its type check or tests, and the app's `.gitignore` ignores them. A second setup run in that app does not name them either, so it neither adds nor overwrites them. Inside Forge's own template tree nothing makes them: the live run copies the tree to a temporary folder and makes them there, and its copy now also skips the names `openapi.json` and `api-types.ts`, so each live run starts from a copy without them. Making them inside the template tree by hand needs `pnpm install` and `uv sync` there first, which put ignored `node_modules` and `.venv` folders in the tree; setup already copies those and git already refuses them today, so the two files add no new failure. Setup gets no new filter.
- The fast test. `scripts/affected.mjs`: a change under `apps/api/app/` (the code that makes the contract) selects both `api` and `web`; other changes under `apps/api/` (tests, migrations, config) select only `api`, as today. `scripts/test.mjs`: when `api || web`, run `api-types` once before either branch (moved out of the `api` branch); the `web` branch does not change: ESLint, `tsc --build`, `vitest run --changed <base> --passWithNoTests`, and the browser tests. So for a change to the API's code the web side always runs the type check and the browser tests. Vitest stays changed-only: an API-only change leaves every web source file the same, and the generated types are type-only imports that Vitest removes before it runs, so a web unit test cannot see the change. Vitest therefore usually selects no test there, at almost no cost, as today (with committed types, Vitest's import graph also skipped the type-only file). This keeps today's protection for an API change that changes the contract (type check and browser tests), and adds it for a change to the API's code that does not. Cost: one stack start and the browser tests on such fast tests, a few minutes (estimate). Score: F 2, H 2 (a broken request found late), C 1. 4 >= 2.
- Git. Add `libs/shared/api-types/openapi.json` and `libs/shared/api-types/src/api-types.ts` to the starter's `.gitignore`.
- Lost protection. The contract no longer shows as a diff. The review still reads the route and schema code, `tsc` still fails on a type mismatch, and the browser tests still run for every change to the API's code. No snapshot, no drift check.
- Windows. The new prefix is the same `&&` chain that `test` already runs through pnpm, and `test.mjs` already spawns with `shell: true` on Windows. No new shell syntax. The live run skips Windows, so Windows stays proven only as much as it is today.
- Existing repos. Forge changes no app file. `forge sync` and `forge doctor` say nothing new: the shared-file note from FORGE-GENFILE-1 already names a file that three or more parts share. Score for a doctor line: F 1, H 2, C 1. 2 >= 2, but it would repeat that note, so it is left out.
- What parts still share. After the two files leave the scopes, API parts that add a module still share the files `forge feature` edits (above), and parts that change one module share that module's files. Neither this story nor the guide step promises that such parts stop waiting, and the guide step does not change `After` links.
- FORGE-GENFILE-1 (approved 11 Nov 2026) advises, at plan read, to make a generated file at build time. This story makes Forge's own Python starter follow that advice. Nothing in FORGE-GENFILE-1 changes.
