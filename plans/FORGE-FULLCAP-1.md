# Waiting parts start and merge on their own once the part before them is done

3 parts · Risks: none one-way · New moving parts: one Claude Code Stop hook that `forge sync` and `forge init` write into `.claude/settings.json` and that runs a new local-only command, `forge hook stop`

## What changes for you

- After a part merges, its stacked parts that already have a clean review also merge, and each part that can now start gets one line.
- The coordinator cannot end its turn while Forge lists a part that can start and none is running. A part that waits on a person does not count.
- After every merge, the coordinator starts each listed part in the background before it replies, on Claude and on Codex.
- Forge lists a part as able to start only when starting it would succeed.
- New client repos get all of this at init. Existing client repos get it on upgrade.

## Why

After a part merges, nothing starts the parts that waited for it unless the coordinator reads the next-step list and starts them by hand. The merge output for a stacked part names a close step, not a merge, and nothing calls the merge again. Forge already has a run that merges stacked parts base-first (forge land --all, in the land module), but nothing calls it after a merge. A stacked part still needs its own close step to move onto the default branch and wait for checks, so merging it inside the base merge is a longer run, not one quick step. The turn stop check is a gate on every turn end, so it needs a loop guard and a cost check against the speed rules.

## Done when

1. **After a base part merges, its clean stacked part merges, or its line says it can now start, with no extra step from a person.**
2. **A test shows that a part listed as able to start is one that task start accepts, including the case where the base lacks the default branch's merge.**
3. **A test shows the stop check holds a turn while a startable part is idle, and lets it end when only waits on a person remain.**
4. **Tests cover one new client repo and one existing repo adopted on an earlier release.**

## Risks

Risks: none one-way. Each part reverts with its pull request. Nothing is deleted, no data changes and no new vendor is added.

Trade-off: the turn stop check can hold a turn that should end. It holds only when `forge next` would list a part that can start. It holds a turn once: on the second try the turn ends, even when nothing was started. The worst case is one extra reply from the coordinator. The check reads only local git, so when the computer's copy of the remote branches is older than GitHub, it can list a part that is not startable yet, or miss one that is. A miss costs the same as today. The coordinator's own `forge task start` still says no, with the reason.

Trade-off: if `forge` is not on the path, or the check fails for any reason, the turn ends as it does today. The hook writes nothing to block in that case. A broken Forge never traps a session.

Trade-off: Codex gets no stop hook, so on Codex only the written rule (start every listed part after each merge) keeps capacity in use. A Codex coordinator that ignores the rule leaves parts idle, as it does today.

Trade-off: `forge merge` now also closes and merges the stacked parts that already have a clean review, so one `forge merge` can run for as long as the checks of those parts take. A stacked part whose review is not clean, or whose tests fail, is not merged: Forge prints its next step as it does today, and the base stays merged. Run `forge merge` in the background, as for `forge land`.

Trade-off: after a merge, the listed parts are computed from the computer's local git, which `forge merge` has just refreshed. A part that waits on a pull request merged outside Forge is not listed until `forge next` runs with a fresh GitHub read.

### Done-when details

1. After a base part merges, its clean stacked part merges, or its line says it can now start.
   - Behaviour. At the end of `merge.merge`, after the worktree cleanup and with the current directory back in the main checkout, `forge merge <item>` takes the child pull requests it just retargeted (the `found` items at `merge.py:238-260`) and keeps those whose recorded review is clean and whose state is in `IN_CLOSE`. For those, it calls the land queue with that list only: `land._queue(top, only=<items>)`, a new optional argument that drops every other change before the sort. `_queue` already orders bases first, runs each child as `forge land <child>` (close, one fix round, merge) and prints its summary. The queue's lock is taken the way `_land_all` takes it. Reuse that wrapper with the list as a parameter; write no new loop.
   - Children built on another machine. `merge` decides which children are clean without a checkout: it reads each child's state the way `land._queue` does at `land.py:307`, through `nextstep.at_ref(top, item, state, pr)` (which picks the newer of the local branch and `origin/<branch>` with `nextstep.review_ref`), so a stale local blocked review never hides a clean published one, and keeps those whose `review.status` is `clean`. `_queue(top, only=...)` then makes a checkout for each kept item that has no worktree, with `close._worktree(item)`, before it builds `changes`, so a remote-only child enters the queue the same way a local one does. ### New and existing repos

- **New repos** (`forge init`, `forge init --starter`, adoption): the Stop hook is written into `.claude/settings.json` at init; `forge merge`, `forge next` and the guide text work as written from the first merge.
- **Existing repos** (on upgrade, after `forge sync` or `forge doctor --fix`): the same hook entry and the same guide and brief text. `forge merge` and `forge next` behave the new way as soon as the installed Forge is the new release. Nothing in the app's code changes and nothing blocks the upgrade. A repo with `stack = "off"` has no stacked parts, so the merge step finds none; its stop hook and `forge next` list work the same.
