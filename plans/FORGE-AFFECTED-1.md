# Tests run once, and only for the parts a change touches

4 parts · Risks: none one-way · New moving parts: one small Node script in each starter (`scripts/affected.mjs`) and one small Python script in Forge's own repo (`scripts/smoke_select.py`); no new command, service, setting or model call

## What changes for you

- The pull request check of a client app runs lint, typecheck and tests only for the parts a change touches, compared with the merge base, and its log names them. Close does not run them again on the laptop; it waits for that one check.
- Forge picks the touched parts in this order: Nx affected projects where the workspace defines its targets; else each runner's own selection (Forge's related pytest picker, vitest changed, jest changed since, Playwright only-changed); a chained command is split and each step gets its own selection; only a step with no selection runs whole.
- A Python app without Nx gets its related pytest tests, plus ruff and mypy on the changed files.
- The full suite runs nightly and before sign-off, as it already does when tests run in CI.
- Forge's own repo is checked first: its related tests run once, in the pull request check (close already waits for that check and runs none itself), and the starter app smoke runs are chosen by the area a change touches.
- New client repos get it at init. Existing client repos get it with the Forge release their CI file pins, after upgrade and sync; their app scripts and `forge.toml` stay theirs, and the agent asks before it changes `forge.toml`.

## Why

Client developers wait about 40 minutes at close. With the default setup close does not run tests on the laptop; it waits for the pull request check, and that check runs the starter's whole test script (lint, typecheck, API, hooks and Docker browser tests) for every change, because the script is one Node program that Forge cannot select from. The starters' Nx setup cannot select yet: only the two app projects define targets, and the Python starter has no Nx. In Forge's own repo the related tests already run once, in the pull request check, but any template change starts every app smoke run, each of which takes up to 45 minutes.

## Done when

1. **A change to a client app runs lint, typecheck and tests only for the parts it touches, once, in the pull request check, and the log names those parts.**
2. **A Python app without Nx runs only its related pytest tests and checks the changed files.**
3. **The full suite runs nightly and before sign-off.**
4. **Forge's own repo runs a change's related tests once and picks app smoke runs by the changed area.**
5. **New client repos get it at init; existing client repos get it after upgrade and sync, and the agent asks before forge.toml changes.**

## Risks

<!-- Each one-way step: deleting data, a destructive migration, a new vendor. -->

Risks: none one-way. Each part reverts with its pull request. Nothing is deleted and no data changes.

Trade-off: a selection can miss a test that a change reaches through a dependency the selection does not see (an import through a config file, a shared fixture, a service the test calls over HTTP). The nightly full run and the full run before sign-off are the guard, as they are for the pytest picker today. A miss is found in one day, not before the merge.

Trade-off: Nx finds affected projects from imports and package dependencies. In the starter, the browser tests call the running app over HTTP and import no app code, so Playwright's own changed-file selection would pick none of them for an app change. Where Nx defines the targets, a changed web project runs its whole browser suite. Playwright's changed-file selection is used only for steps that Nx does not cover.

Trade-off: the Python starter's API tests call the app over HTTP and name no module, so Forge's related picker finds none for a source change (its "No local test names ..." lines). The plan runs all the API tests when API code changes, and the related picker alone elsewhere. This is open for the owner (see Notes).

Trade-off: Nx targets added to the starter's libraries change only new repos. An existing app keeps its own `project.json` files and scripts. The agent adds the same targets to an existing app after the owner agrees; the guide gives the recipe.

Trade-off: Forge's own smoke areas are a table in one script. A template path that the table does not name runs every smoke job, as today, so a wrong or missing row costs time and never hides a failure.

### How a change picks its tests

- Order, as the owner decided. (1) Nx affected, where the workspace defines the targets. (2) Else each runner's own selection. (3) A chain joined by `&&` is split, and each step gets its own selection by this order. (4) A step with no selection runs whole.
- Forge's side (SPLIT). `close_tests` rewrites an `&&` chain in place and runs it once in the same shell. Kinds and what each gets: an Nx step gets Nx affected (next paragraph), vitest `--changed <base>` and jest `--changedSince <base>` (as today), Playwright `--only-changed=<base>`, a pytest step through the existing picker (`narrow_command`), and `ruff` or `mypy` steps with their path arguments replaced by the changed `.py` files that sit under them (a step with none becomes `true`). Every other step runs whole. A step run through `pnpm` or `npm` keeps today's rule: a package script that is itself compound runs whole, because arguments go to its last command. A command with `;` or `|` runs whole, as today. Before the chain runs, `close_tests` prints one line per step, such as `Test selection: vitest run -> changed since abc1234` or `Test selection: eslint . -> runs whole (no selection)`; that is the log that names the parts. An existing repo gets this with no `forge.toml` change when it has no `fast_test`, because `close_test` then calls `close_tests`. A repo with a `fast_test` keeps its own command. `quicktest.suggest` also knows Playwright and prints its `--only-changed={base}` line.
- Nx in an existing workspace (SPLIT). `quicktest.test_parts` gets a kind `nx` for a step that runs `nx run-many -t <target>`, `nx affected -t <target>` or `nx run-many --targets=<target>`, with or without a `npx`, `pnpm exec`, `pnpm nx` or `corepack pnpm` prefix. Forge uses Nx on that step when the repo has `nx.json` and `nx show projects --with-target <target>` names at least one project (any failure of that command means no Nx): it replaces `run-many` with `affected` and adds `--base=<merge base>`. A step that names `--projects`, `--all` or a target no project defines runs whole. This is the only place Forge looks at Nx. A step that calls a runner directly (`vitest run`, `pytest`) in an Nx workspace is not mapped to an Nx target: it keeps its own runner's selection, which is step (2) of the order. So "Nx affected where the workspace defines its targets" means the steps that already invoke those targets.
- The starters' side (the two starter parts). In each starter `scripts/affected.mjs` takes the merge base and returns the parts to run and the exact commands for them. `scripts/test.mjs` takes the base as an optional first argument, builds its command list from `affected.mjs`, runs the Docker set-up only when a selected part needs it, and runs only the selected commands. With no argument it runs everything as today, so `test = "node scripts/test.mjs"` stays the full run. `node scripts/test.mjs --list <base>` prints the command list it would run, in order, and exits 0 without running any; it uses the same code as a real run and is how the tests see the selected path. A changed path outside every project root (`package.json`, a lock file, `eslint.config.mjs`, `Dockerfile`, `compose.test.yml`, `scripts/`) selects everything. Both scripts print `Affected parts: ...` before they run; that is the log line. Init writes `fast_test = "node scripts/test.mjs {base}"` for a starter that ships `scripts/affected.mjs` (a file check, so each starter part ships its own file and init needs one change, made by STARTERS-TS), so close, the pull request check and a worker's `forge test` all select, and `forge test --full` (nightly, before sign-off) does not.
- TypeScript starter. `affected.mjs` asks Nx for the affected projects (`nx show projects --affected --base=<base> --json`) and runs `nx affected -t lint typecheck test --base=<base>`; Docker and the browser suite start only when `api` or `web` is affected. `nx.json` gets `defaultBase`. Every library `project.json` gets a `lint` target (ESLint on its folder). Test targets are disjoint: the two apps' `test` targets run their own tests (`vitest run --config apps/api/vitest.config.ts`; `vitest run --config apps/web/vitest.config.ts apps/web/src`), and each of the three libraries with tests (`shared/util`, `history/server`, `core/server`) gets a `test` target that runs `vitest run --config apps/web/vitest.config.ts libs/<group>/<name>`. The web config's library glob (`apps/web/vitest.config.ts`) stays, so the full run (`test:hooks`, no base) still runs every test once. A library change then runs that library's tests once and, because `web` depends on it, the web project's own tests; no test file is named by two targets. The web `e2e` target wraps `playwright test --config apps/web/playwright.config.ts`.
- Python starter, with no Nx. `affected.mjs` maps the changed paths to parts by folder and lists, per part, the checks the starter's `test` script runs today. API part (a change under `apps/api`): `api-types` (it regenerates `libs/shared/api-types`, which the web type check reads), `ruff check`, `ruff format --check` and `mypy` on the changed `.py` files (paths made relative for `uv --directory apps/api`), `test:imports` (import-linter, whole, it is fast), and the API tests: all of them when a file under `apps/api/app` or `apps/api/migrations` changes (open choice 1), else only the changed test files.
