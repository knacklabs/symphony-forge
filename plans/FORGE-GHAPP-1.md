# Give each developer their own GitHub app for Forge's GitHub work

2 parts · Risks: none one-way; eight accepted limits · New moving parts: one private GitHub app for each developer, owned by the client's organization, its private key in a file in Forge's folder on that developer's laptop, and a small local web page during setup

## What changes for you

- Each developer gets a GitHub app of their own, named after them, for example "Forge (octocat)". Nothing is shared between developers: each one has their own app, their own key and their own hourly budget. The app belongs to the client's organization and is private, so only that organization can install it. During setup, Forge prepares the app's settings and opens GitHub in the browser. The developer clicks once on GitHub to create the app in the organization. Then an owner of the organization installs it once. Setup and the guide tell the owner to choose "Only select repositories" and pick only the repos that this developer works on. When the developer is an owner, they do both. A new repo does this with `forge init --actions yes --github-app` (or `--actions no`). An existing repo runs `forge init --github-app` once after it upgrades. (Source: owner, 19 Nov 2026)
- To create an app in the organization, the developer must be an owner of the organization or have its App Manager role. When GitHub does not let the developer create it, setup stops with one line: an owner of the organization must give the developer the App Manager role once. There is no other way. (Source: owner, 19 Nov 2026)
- When the repo is in the developer's own GitHub account, not in an organization, setup makes a private app in that account, and the developer installs it there. No one else is needed. (Source: owner, 19 Nov 2026)
- After that, close, merge and land act on GitHub as the developer's app, with that app's own hourly budget of requests: reviews, checks, waits for CI, CI reruns and merges. The pull requests that close and land open stay in the developer's name: Forge opens them, and writes their description, with the developer's own GitHub sign-in. That sign-in keeps its budget for agents and other tools. Pushes still use the developer's own git sign-in. Each token that Forge gets from the app works only for the repo the command works in, even when the app is installed on more repos. Forge uses the app that belongs to the GitHub account that `gh` is signed in to now. Until the app is set up and installed, or when GitHub refuses it, these commands use the developer's sign-in as today. When GitHub refuses it, Forge says why in one line. (Source: owner, 19 Nov 2026)
- The app's private key stays on the developer's laptop. Forge keeps it in its own folder for that user, outside every repo: `~/.config/forge/github-apps/` on macOS and Linux, and `%LOCALAPPDATA%\forge\github-apps\` on Windows (the local folder, which Windows does not copy to other computers). Only that user's account can read the file. Setup refuses to save a key in a folder that is inside a git repo. Forge never writes the key into a repo file, never copies it to another laptop, never puts the key or a token in a command line, and keeps no other secret that GitHub gives it. (Source: owner, 19 Nov 2026)
- `forge doctor` (Forge's health check) shows, for the repo, who close, merge and land act as on GitHub (the developer's own app, or the developer's sign-in) and how many GitHub requests are left in the current hour. While an owner has not yet installed the app, it says so. It warns when an owner installed the developer's app on all repos of the organization instead of selected repos. It only warns; it does not stop anything.
- Not in this story: keeping CI runners up to date and running. A later story uses GitHub's standard runner tools for that (Actions Runner Controller, short-lived runners that scale by themselves, or plain runners); Forge builds no runner manager. Also not in this story: the board, `forge next` and the other commands, which keep the developer's sign-in; keeping the key in the operating system's keychain; Mainline.
- What each repo gets. A new repo gets the developer's app when its setup runs `forge init` with `--github-app`; plain `forge init` names that step. An existing repo gets it after it upgrades, through `forge init --github-app`; `forge doctor` names the step until the developer's laptop has an app. A repo that Forge is adopting runs the step after the adoption's pull request merges. Nothing in any repo changes: no setting, no file. Only the developer's laptop gets a key file. Another repo of the same organization uses the same app with no new step when the install covers it; otherwise the step asks an owner to add that repo.
- Cost. No model call is added. Each close, merge or land run makes four more GitHub requests when it starts (two with the developer's sign-in: who is signed in and which repo this is; two with the app's key: find the install and make a token), and one more about once an hour after that. `forge doctor` makes the same few.

Design: one small local page that setup opens in the browser. It says one sentence and sends the app's settings to GitHub. Nothing on the board changes.

## Why

Close, merge and land use the developer's own GitHub sign-in. It allows 5,000 requests an hour, and agents and runner tools use the same budget. At one client it ran out several times an hour on 18 and 19 November 2026, and close then stopped to wait. Waits for CI checks used most of it. The next release asks GitHub once a minute and limits waits by the budget that is left, but the budget is still shared. Each install of a GitHub app gets a budget of its own: 5,000 requests an hour, plus 50 for each repo above 20 and 50 for each organization member above 20, up to 12,500 (15,000 on GitHub Enterprise Cloud). With one app for each developer, each developer gets this budget for themselves. (Source: GitHub's documentation on REST API rate limits, read on 19 Nov 2026.)

## Done when

1. **forge doctor shows which identity close, merge and land use for a repo, the developer's own app or their gh sign-in, and how much of its hourly budget is left, and it warns when the developer's app is installed on all repos of the organization.**
2. **Each developer gets their own private app, owned by the client's organization (or by their own account for a repo outside an organization), at init of a new repo or through one setup step in an existing repo after upgrading; an organization owner installs each developer's app once, and a developer who may not create organization apps gets one line that names the App Manager role.**
3. **Each developer's app key stays on that developer's laptop, Forge never writes it into a tracked repo file, and the plan says where the laptop reads it from.**
4. **Close, merge and land use the developer's app token, limited to the repo they work in, for their GitHub calls when the app is set up, and use the developer's gh sign-in as today when it is not.**

## Risks

Risks: none one-way. Each part reverts with its pull request. An owner of the organization can delete or uninstall a developer's app on GitHub at any time; Forge then uses that developer's sign-in again.

Accepted limits, in plain words:
- A copied key acts as that developer's app. Anyone who reads the key file can make tokens for every repo where the app is installed, until an owner or the developer deletes that key on GitHub: open and merge pull requests, run CI again, and push to branches that have no protection. Forge's own tokens reach only one repo, but a copied key is not bound by that; only the install's repo list limits it. That is why owners choose "Only select repositories", and why doctor warns about an install on all repos. Doctor does not check selected repos one by one. The default branch keeps its protection. Only the developer's own account can read the file, the same protection that ssh keys have.
- The app asks for these permissions: write access to code (to merge), to pull requests, and to Actions runs (to run CI again and to cancel it); read access to checks, commit statuses and the repo's settings (to read the branch rules). It gets no permission to change workflow files.
- The organization owns every developer's app. Its owners, and people with the App Manager role, can change each app's settings and make new keys for it. A developer who is given the App Manager role can do the same for every app of the organization. (GitHub: owners grant "access for a user to manage some or all of the GitHub Apps owned by the organization", and creating an app in the organization needs permission "to manage all its apps".)
- One app for each developer means many apps. An organization can have at most 100 apps of its own. An owner installs each one once. Branch rules that let only named people merge, or let named people skip rules, must allow each developer's app; until an owner adds it, Forge's merge stops with GitHub's message, as today. The merges that Forge makes show the developer's app on GitHub, not the developer; the pull requests keep the developer as their author. Whose name GitHub puts on the merged commit is not checked yet; the builder checks it on a trial repo.
- GitHub app names are unique across all of GitHub. When "Forge (octocat)" is taken, for example because the developer already has an app for another client, the developer changes the name on GitHub's page before creating it. Forge uses whatever name GitHub gives back.
- A developer's app lives on one laptop. On a new laptop, or when GitHub refuses a key, an owner deletes the old app on GitHub, the developer deletes the two files that doctor names and runs the setup step again, and an owner installs the new app. Until then, that developer's close, merge and land use their own sign-in. A contractor who is not a member of the organization cannot get the App Manager role, so they keep their own sign-in.
- Without an organization, the app is private and installed on the developer's own account. Its budget is 5,000 requests an hour, plus 50 for each repo above 20, and it is separate from the developer's own sign-in.
- A token from the app lasts one hour. Forge makes a new one before a GitHub call when less than 5 minutes are left, so a long close does not fail on an old token. When an owner uninstalls the app while a command runs, that command may stop with GitHub's message; running it again uses the developer's sign-in.

### Decisions

- **One private app for each developer, owned by the organization (owner, 19 Nov 2026).** For a repo whose owner is an organization, the manifest posts to `https://github.com/organizations/<org>/settings/apps/new`, with `public` false, so the organization owns the app and only the organization can install it. For a repo on a personal account, it posts to `https://github.com/settings/apps/new`, with `public` false. The name is `Forge (<login>)`; GitHub may let the developer change it on its page, and Forge keeps the `slug` that the conversion returns. There is no public app, no key import and no shared app.
- **GitHub's app endpoints go through Python, not gh.** The three calls that use the app's key or no sign-in (the installation lookup, the token, and the manifest conversion) use `urllib.request` against `https://api.github.com` inside the Forge process, through one helper `ghapp.api(method, path, auth=None, body=None) -> tuple[int, Any]`. So the JWT never appears in a process argument or a child environment, a developer who signs gh in only through `GH_TOKEN` still works, the conversion runs with no credential (GitHub's conversion endpoint needs only the code), and these calls never enter `github.run` or its quota lock. Tests point the helper at a local server through `FORGE_GITHUB_API` (a test seam, like `FORGE_CHECKS_WAIT`). An installation token reaches gh only as `GH_TOKEN` in that gh child's environment, never in its arguments.
- **Who is signed in, and which repo (Done-when 4).** Once per process, read the active gh login (`task.github_login`) and the repo (`gh repo view --json nameWithOwner --jq .nameWithOwner`), both with the developer's sign-in. While these two reads run, `ghapp.env` returns `{}` (a module flag), so a rate-limit wait inside them, whose quota read runs gh again, never starts a second lookup.
- **Which app a repo uses.** The saved app whose `login` is the active gh login and whose `owner` is the repo's owner. There is at most one: setup never saves a second app for the same login and owner. One installation lookup (`GET /repos/<owner>/<repo>/installation` with the JWT): an `id` means installed; a 404 means not installed on this repo yet. Keep `repository_selection` for doctor.
- **Where the key lives (Done-when 3).** `ghapp.folder()`: `%LOCALAPPDATA%\forge\github-apps` on Windows (local, not roaming), else `$XDG_CONFIG_HOME/forge/github-apps`, else `~/.config/forge/github-apps`. Files `<app id>.pem` and `<app id>.json` with `{"id": <int>, "slug": "<slug>", "owner": "<org or login>", "login": "<developer>"}`. Before saving, setup refuses when the folder, or its nearest existing parent, is inside a git work tree (`git -C <that folder> rev-parse --is-inside-work-tree` prints `true`): problem `Forge keeps app keys outside every repo, but <folder> is inside one.`, next `point XDG_CONFIG_HOME (LOCALAPPDATA on Windows) outside any repo, then forge init --github-app`. Make the folder with mode 0700 and write the key through `os.open(..., os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)` to a temporary name, then `os.replace`. Keep only the key, the id, the slug, the owner and the login; drop `client_id`, `client_secret` and `webhook_secret`. Never print the key. `machine.py` does not change; its repo list keeps `APPDATA`.
- **No forge.toml setting (choice, for the owner).** Each app belongs to one developer, so a repo setting could not name it.
- **The JWT.** RS256 over `{"alg":"RS256","typ":"JWT"}` and `{"iat": now - 60, "exp": now + 540, "iss": <app id>}`, base64url without padding. Sign in Python, since no crypto library is installed and Windows may lack `openssl`: read the PEM (PKCS#1 `RSA PRIVATE KEY`, as GitHub gives it; also unwrap PKCS#8 `PRIVATE KEY`), read `n` and `d` from the DER integers, build the EMSA-PKCS1-v1_5 block `00 01 FF..FF 00` + the SHA-256 DigestInfo prefix `3031300d060960864801650304020105000420` + the digest, and sign with `pow(m, d, n)`. About 25 lines with a `ponytail:` comment: it is not constant-time, which matters only to code that already runs as this user and can read the key file anyway; a crypto library is the upgrade path if one is ever a dependency.
- **The token (one repo; owner, 19 Nov 2026).** `POST /app/installations/<id>/access_tokens` with the JWT and the body `{"repositories": ["<repo name>"]}`, so each token reaches only the repo of the checkout. Doctor's token is the same. Keep the token and its `expires_at` in memory for the process and make a new one when less than 5 minutes are left. Write no token to disk.
- **Use for close, merge and land only (Done-when 4).** In `repo.run`'s `execute`, for `args[0] == "gh"` and a caller that passed no `env`, add `**ghapp.env(args, cwd)`. `ghapp.env` returns `{}` unless `github.wait_for_reset` is true, and `{"GH_TOKEN": <token>}` when the app is usable. Since `execute` runs again on each retry and each rate-limit wait, a retry gets a fresh token. Forge never sets `os.environ["GH_TOKEN"]`, so git, gh's git credential helper and child processes do not get the token: pushes stay with the developer's sign-in, and the app needs no workflows permission. Two kinds of call keep the developer's sign-in so each pull request keeps the developer as author (owner, 19 Nov 2026): `ghapp.env` returns `{}` for `args[1:3] == ("pr", "create")` (close's `_gh` and `_draft` at `close.py:975-977`, land's train at `land.py:735`) and for `args[1:3] == ("pr", "edit")` with `--body-file` in `args` (`close.py:934`, `:999`). `close.py` and `land.py` do not change.
- **Fallback (Done-when 4).** No saved app for this login and owner, or not installed on this repo yet: use the sign-in and print nothing (doctor says it). A key that GitHub refuses, a failed token call, or a key file Forge cannot read: use the sign-in and print once per process on stderr `Your GitHub app <slug> could not be used: <GitHub's first line>. <command> uses your gh sign-in. Next: forge doctor`. Never refuse because of the app.
- **Doctor's line (Done-when 1).** After the gh sign-in check (`doctor.py:366`), when gh is on PATH, print one line, for example `- GitHub: close, merge and land act as your app forge-octocat. 6,500 of 6,750 requests and 6,700 of 6,750 GraphQL points are left this hour; it resets at 14:05 UTC.` or `- GitHub: close, merge and land use your gh sign-in octocat. 120 of 5,000 requests and 4,100 of 5,000 GraphQL points are left this hour; it resets at 14:05 UTC.` followed by ` You have no Forge GitHub app on this laptop for this repo: forge init --github-app.` or ` Your app <slug> is not installed on <owner>/<repo> yet: an owner of <owner> installs it on https://github.com/apps/<slug>/installations/new.` The numbers come from one `gh api rate_limit` (GitHub does not count it), with the app's one-repo token as `GH_TOKEN`, or without. Waiting for an owner is not a row; a key that GitHub refuses is a row (a problem) with the fix `an owner of <owner> deletes the app <slug> on GitHub; delete <folder>/<id>.pem and <folder>/<id>.json; then forge init --github-app`. A laptop with no app adds no row.
- **Doctor's wide-access warning (Done-when 1; owner, 19 Nov 2026).** When the installation lookup's `repository_selection` is `all`, print `- Warning: Your app <slug> is installed on all repos of <owner>. Ask an owner of <owner> to change it to "Only select repositories" with only the repos you work on.` plus the settings page (`https://github.com/organizations/<owner>/settings/installations` for an organization, `https://github.com/settings/installations` for a personal account). No more requests. It is a warning, not a row. Doctor does not list selected repos: that needs a token for the whole install, which the one-repo rule forbids.
- **Select repos (SETUP; owner, 19 Nov 2026).** The step's owner-installs line, the local page's text and the guide say: choose "Only select repositories", and pick only the repos that this developer works on.
- **The setup step (Done-when 2 and 3).** `forge init --github-app`, a new option of init (a flag, no value).
  - A repo with no history: init does today's work (with `--actions` as today), then the app step. A repo whose `forge.toml` exists: only the app step, so an existing repo after upgrading runs one step. A repo with history and no `forge.toml` (adoption): refuse with `run forge init --github-app after the adoption's pull request merges`; adoption is unchanged. Plain `forge init` on a new repo prints, before `Next: forge next`, either `close, merge and land act as your GitHub app <slug>.` or `To give close, merge and land their own GitHub budget, run forge init --github-app with the developer at the browser.`
