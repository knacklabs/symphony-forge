# Give each client its own GitHub app for Forge's GitHub work

2 parts · Risks: none one-way; seven accepted limits · New moving parts: a GitHub app in each client's own GitHub account, and its private key in a file in Forge's folder on each laptop

## What changes for you

- During setup, the person makes Forge's GitHub app in the client's own GitHub organization. Forge prepares the app's settings and opens GitHub in the browser. The person clicks two times on GitHub: once to create the app, and once to install it on the repos. A new repo does this with `forge init --github-app`. An existing repo runs the same one step after it upgrades. A client without an organization makes the app in the person's own GitHub account in the same way. (Source: owner, 19 Nov 2026)
- After that, close, merge and land act on GitHub as the app, with the app's own hourly budget of requests: reviews, checks, waits for CI, CI reruns and merges. The pull requests that close and land open stay in the person's name: Forge opens them, and writes their description, with the person's own GitHub sign-in. The person's own GitHub sign-in keeps its budget for agents and other tools. Pushes still use the person's own git sign-in. When the app is not set up on a laptop, or GitHub refuses it, these commands use the person's sign-in as today. When GitHub refuses it, Forge says why in one line. (Source: owner, 19 Nov 2026)
- The app's private key stays on the laptop. Forge keeps it in its own folder for that user, outside every repo: `~/.config/forge/github-apps/` on macOS and Linux, and `%APPDATA%\forge\github-apps\` on Windows. Only that user's account can read the file. Forge never writes the key into a repo file, and it keeps no other secret that GitHub gives it. Another developer gets a key of their own: an owner of the organization makes it on the app's page on GitHub, and the developer runs the same setup step with that file. (Source: owner, 19 Nov 2026)
- `forge doctor` (Forge's health check) shows, for the repo, who close, merge and land act as on GitHub (the app, or the person's sign-in) and how many GitHub requests are left in the current hour.
- Not in this story: keeping CI runners up to date and running. A later story uses GitHub's standard runner tools for that (Actions Runner Controller, short-lived runners that scale by themselves, or plain runners); Forge builds no runner manager. Also not in this story: the board, `forge next` and the other commands, which keep the person's sign-in; keeping the key in the operating system's keychain; Mainline.
- What each repo gets. A new repo gets the app when its setup runs `forge init --github-app`; plain `forge init` names that step. An existing repo gets it after it upgrades, through the same step; `forge doctor` names the step until the laptop has a key. Nothing in either repo changes: no setting, no file. Only the laptop gets a key file. A second repo of the same organization on the same laptop uses the app with no step, when the app is installed on it.
- Cost. No model call is added. Each close, merge or land run makes two more GitHub requests when it starts and about once an hour after that (find the app's installation, make a token). `forge doctor` makes one or two more.

Design: none. Nothing on the board changes.

## Why

Close, merge and land use the person's own GitHub sign-in. It allows 5,000 requests an hour, and agents and runner tools use the same budget. At one client it ran out several times an hour on 18 and 19 November 2026, and close then stopped to wait. Waits for CI checks used most of it. The next release asks GitHub once a minute and limits waits by the budget that is left, but the budget is still shared. A GitHub app installed in an organization gets a budget of its own: 5,000 requests an hour, plus 50 for each repo above 20 and 50 for each organization member above 20, up to 12,500 (15,000 on GitHub Enterprise Cloud). (Source: GitHub's documentation on REST API rate limits, read on 19 Nov 2026.)

## Done when

1. **forge doctor shows which identity close, merge and land use for a repo, and how much of its hourly budget is left.**
2. **A new repo gets its app at init, and an existing repo gets it through one setup step after upgrading.**
3. **The app's keys stay with the client, Forge never writes them into a tracked repo file, and the plan says where the laptop reads them from.**
4. **Close, merge and land use the app's token for their GitHub calls when the app is set up, and use the person's gh sign-in as today when it is not.**

## Risks

Risks: none one-way. Each part reverts with its pull request. An owner of the organization can delete the app on GitHub at any time; Forge then uses the person's sign-in again.

Accepted limits, in plain words:
- A copied key acts as the app. Anyone who reads the key file can act as the app on the repos where it is installed, until an organization owner deletes that key on GitHub: open and merge pull requests, run CI again, and push to branches that have no protection. The default branch keeps its protection. Only the person's own account can read the file, the same protection that ssh keys have.
- The app asks for these permissions: write access to code (to merge), to pull requests, and to Actions runs (to run CI again and to cancel it); read access to checks, commit statuses and the repo's settings (to read the branch rules). It gets no permission to change workflow files.
- One budget for the whole organization. Everyone in the organization who uses the app shares its budget. For a large team, this can be less than the budgets of everyone's own sign-ins together. `forge doctor` shows what is left.
- The merges that Forge makes show the app on GitHub, not the person. The pull requests themselves keep the person as their author. Branch rules that let only named people merge, or let named people skip rules, do not include the app until an owner adds it. Until then, Forge's merge stops with GitHub's message, as today. Whose name GitHub puts on the merged commit is not checked yet; the builder checks it on a trial repo.
- Each laptop needs its own key. Until a developer adds one, their close, merge and land use their own sign-in.
- Without an organization, the app belongs to the person. Its budget is 5,000 requests an hour, plus 50 for each repo above 20, and it is separate from the person's own sign-in.
- A token from the app lasts one hour. Forge makes a new one before a GitHub call when less than 5 minutes are left, so a long close does not fail on an old token.

### Decisions

- **Where the key lives (Done-when 3).** `<config>/forge/github-apps/<app id>.pem` and `<app id>.json` with `{"id": <int>, "slug": "<slug>", "owner": "<login>"}`, where `<config>/forge` is the folder `machine._repos_file` already uses; move that expression into one small function both call. Make the folder with mode 0700 and write the key through `os.open(..., os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)` to a temporary name, then `os.replace`. On Windows the user profile's own permissions apply. Keep only the key, the id, the slug and the owner; drop `client_id`, `client_secret` and `webhook_secret` from the conversion answer. Never print the key.
- **No forge.toml setting (choice, for the owner).** The owner's likely shape had each repo's forge.toml name the app id. Cut: in an existing repo a forge.toml change needs a fix, so setup would take two steps, and the laptop can find the app without it by asking GitHub which saved app is installed on the repo (below). The setup step learns that an organization already has the app from GitHub's public `GET /apps/forge-<owner>`, so a second developer is not led to make a second app. The id stays in the laptop file. If a client later wants the app named in the repo, it is one setting.
- **Which app a repo uses.** For each saved app (usually one), make a JWT and run `gh api repos/{owner}/{repo}/installation -H "Authorization: Bearer <jwt>"` (gh fills the placeholders from the checkout's origin, as `init.protect` relies on). The first answer with an `id` wins; a 404 means not installed on this repo. Once per process.
- **The JWT.** RS256 over `{"alg":"RS256","typ":"JWT"}` and `{"iat": now - 60, "exp": now + 540, "iss": <app id>}`, base64url without padding. Sign in Python, since no crypto library is installed and Windows may lack `openssl`: read the PEM (PKCS#1 `RSA PRIVATE KEY`, as GitHub gives it; also unwrap PKCS#8 `PRIVATE KEY`), read `n` and `d` from the DER integers, build the EMSA-PKCS1-v1_5 block `00 01 FF..FF 00` + the SHA-256 DigestInfo prefix `3031300d060960864801650304020105000420` + the digest, and sign with `pow(m, d, n)`. About 25 lines with a `ponytail:` comment: it is not constant-time, which matters only to code that already runs as this user and can read the key file anyway; a crypto library is the upgrade path if one is ever a dependency. The test checks the signature with the `openssl` program.
- **The token.** `gh api --method POST app/installations/<id>/access_tokens -H "Authorization: Bearer <jwt>"`. gh keeps a given Authorization header; GH_TOKEN alone would send `token <jwt>`, which GitHub refuses for a JWT. Both app calls run through `repo.run(..., env=<os.environ without GH_TOKEN>)`, so the hook below skips them. Keep the token and its `expires_at` in memory for the process and make a new one when less than 5 minutes are left. Write no token to disk. The JWT is a gh argument for under a second and is valid for at most 10 minutes; that is accepted.
- **Use for close, merge and land only (Done-when 4).** In `repo.run`'s `execute`, for `args[0] == "gh"` and a caller that passed no `env`, add `**ghapp.env(cwd)`. `ghapp.env` returns `{}` unless `github.wait_for_reset` is true, and `{"GH_TOKEN": <token>}` when an app is usable. Since `execute` runs again on each retry and each rate-limit wait, a retry gets a fresh token. Forge never sets `os.environ["GH_TOKEN"]`, so git, gh's git credential helper and child processes do not get the token: pushes stay with the person's sign-in, and the app needs no workflows permission. Every gh call of close, merge and land uses the app except two, which keep the person's sign-in so each pull request keeps the person as author (source: owner, 19 Nov 2026): `gh pr create` (close's `_gh` and `_draft` at `close.py:975-977`, and land's train at `land.py:735`) and `gh pr edit ... --body-file` (close's body writes at `close.py:934` and `:999`). `ghapp.env` returns `{}` for `args[1:3] == ("pr", "create")`, and for `args[1:3] == ("pr", "edit")` with `--body-file` in `args`; both go through `repo.run`, so `close.py` and `land.py` do not change. `pr ready`, `pr edit --base`, `pr merge`, `pr close`, reads, reruns and cancels use the app.
- **Fallback (Done-when 4).** No saved app, or no saved app installed on this repo: use the sign-in and print nothing (doctor says it). A key that GitHub refuses, a failed token call, or a key file Forge cannot read: use the sign-in and print once per process on stderr `Forge's GitHub app <slug> could not be used: <GitHub's first line>. <command> uses your gh sign-in. Next: forge doctor`. Never refuse because of the app.
- **Doctor's line (Done-when 1).** After the gh sign-in check (`doctor.py:366`), when gh is on PATH, print one line, for example `- GitHub: close, merge and land act as the app forge-acme. 6,500 of 6,750 requests and 6,700 of 6,750 GraphQL points are left this hour; it resets at 14:05 UTC.` or `- GitHub: close, merge and land use your gh sign-in octocat. 120 of 5,000 requests and 4,100 of 5,000 GraphQL points are left this hour; it resets at 14:05 UTC. Forge's GitHub app is not set up on this laptop: forge init --github-app.` The numbers come from one `gh api rate_limit` (GitHub does not count it) with the app's GH_TOKEN, or without. The login comes from `task.github_login`. A saved app whose key GitHub refuses, or that is not installed on this repo, adds a row (a problem) with its fix: run `forge init --github-app` again, or add the repo on `https://github.com/apps/<slug>/installations/new`. A laptop with no app adds no row; the app is optional.
- **The setup step (Done-when 2 and 3).** `forge init --github-app [KEY_FILE]`, a new option of init (`nargs="?"`).
  - A repo with no history: init does today's work, then the app step. A repo whose `forge.toml` exists: only the app step, so an existing repo after upgrading runs one step; `_adopt` is not called. A repo with history and no `forge.toml`: `_adopt` as today, then the app step. (3) A saved app for that owner that is not installed on this repo: refuse with `add <owner>/<repo> to it on https://github.com/apps/<slug>/installations/new, then forge init --github-app`. (4) With `KEY_FILE`: take the slug from GitHub's file name `<slug>.<YYYY-MM-DD>.private-key.pem` (another name refuses with "keep the file name that GitHub gave the key"); `gh api apps/<slug>` (public) gives the id and the owner; check the key with the installation call; save it; say that Forge keeps its own copy and the downloaded file can be deleted. (6) Otherwise the manifest flow below.
  - The manifest flow: a local web server on 127.0.0.1 at a free port (stdlib `http.server`) and a random `state` (`secrets.token_urlsafe`). `/` serves a page whose form posts the `manifest` field, on load, to `https://github.com/organizations/<owner>/settings/apps/new?state=<state>` (owner type `Organization`) or `https://github.com/settings/apps/new?state=<state>` (type `User`). Print the local address and open it with `webbrowser.open`. `/created`: a wrong `state` answers 400 and the step keeps waiting; the right one calls `gh api --method POST app-manifests/<code>/conversions`, saves the key, and redirects to `https://github.com/apps/<slug>/installations/new`. `/installed`: ignore its `installation_id` and check with the installation call. Installed on this repo: the page says done, the step prints `Forge's GitHub app <slug> is set up: close, merge and land act as it on <owner>/<repo>.` and exits 0. Not on this repo: refuse as in (3). The step waits at most 15 minutes in total, then refuses with `forge init --github-app`. It never writes inside the checkout.

The installation call's `-H` argument is `Authorization: Bearer <jwt>`; the JWT's header says RS256, its claims have `iss` 123 and `exp - iat` at most 600, and `openssl dgst -sha256 -verify` accepts its signature with the key's public half. Close's `pr create` call and its `pr edit --body-file` calls carry no token (the person's sign-in), while its `pr view` and check reads carry one. `forge merge <item>`'s `pr merge` call carries a token, and so does one `forge land` call; a train's `pr create --draft` carries none. No call carries the token unless close, merge or land made it (the app calls carry none). Fallback: with no saved app, the same calls carry no token and nothing is printed; with the token call answering HTTP 401, they carry no token and stderr has the could-not-be-used line once.
   - Live check, not a test: the builder of SETUP runs the setup step on a trial repo owned by the Forge team, then close, merge and land through the app once there, and puts in the pull request text: whether `gh pr merge`, `gh pr ready` and `gh run rerun` work with an installation token, whose name GitHub puts on the merged commit, and the `rate_limit` numbers.

Before each round ends, run the two cheap checks from AGENTS.md (`test_4_one_test_per_rule`, `test_5_forge_stays_small`).
