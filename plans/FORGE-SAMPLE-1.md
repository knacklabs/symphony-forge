# Sample-data prototypes get a light sign-off

5 parts · Risks: none one-way · New moving parts: none

## What changes for you

- A prototype that holds only made-up data and has no back end can be marked as a sample-data prototype. The agent writes one line, `sample_data = true`, in `forge.toml` after it asks the person, as it does for other settings. A worker cannot change that file. Today the same switch exists as a line in the sign-off record; that record may not exist early in the prototype, so the line moves to `forge.toml`. A repo that already wrote it in the sign-off record keeps working. (Source: your decisions, 2 Nov 2026)
- Before sign-off, a sample-data prototype has no tests and no CI (GitHub's automatic checks). The agent walks the demo steps in a browser before it shows the client. Tests begin with the first build story, and Forge shows that as a visible first step after sign-off. A prototype with real data or a back end keeps tests from day one. A full green run still comes before any real-data or production release. (Source: your decision, 2 Nov 2026)
- A sample-data prototype signs off with no full test run and no whole-source review. One small gap check, one model call, runs once before the demo, with no rounds. It reads the brief, the client's answers, the design, and the app's routes, and reports what is missing. The demo steps and the signer's record stay. Every other finding goes to the Known issues list (the list of known problems that the board shows beside the item), with no repair round unless you ask for one. If the check finds the most serious kind of problem (a security hole, a data leak or data loss in normal use), or any finding scored Gain 5 or Harm 4 or more (for example a missing main demo route), it comes to you at once, and you may accept it with a reason, as you can today. A prototype without the line, or with real data or a back end, keeps today's sign-off rules. (Source: your decision, 2 Nov 2026)
- The sign-off record reaches the main branch in a pull request that holds only that record. The agent merges it at once, with no second review and no tests. GitHub's branch protection, which Forge turns on, requires a pull request and also binds admins, so a direct push to main is impossible there; Forge's own hooks refuse it as well. This plan therefore asks for no exception to "main changes only by pull request". (Source: your decision, 2 Nov 2026, adjusted because a direct push cannot work; see Notes)
- The brief informs and never blocks. No answer in the brief and no open client question stops planning, review, close, merge or sign-off. "Not known yet" is an accepted answer and is not a review finding. The brief's Answers section is the one running list, written during the talks. Forge writes its quote into the sign-off record, so nobody copies it by hand. Sign-off needs only the signer's name. The checks on the customer's name format, the demo address and the list of ways the client replied go. Forge keeps the record of the client's reply. (Source: your decision, 2 Nov 2026)
- An open personal-data answer never stops a sample-data prototype from signing off, approving its rules page or starting a story. The refusal comes when the fix that turns `sample_data` off is closed, because turning it off means real data is coming. That fix is the visible first step after sign-off. Forge counts removing the line, or writing `sample_data = false`, as turning it off. The first-release how-to also lists the answer. A repo that never declared sample data keeps today's refusal, at the approval of the app's rules page. Forge has no release step today (see Notes). (Source: your decision, 2 Nov 2026)
- The design can be made through Forge or separately, and both work. Forge requires no way of making it and does not require it to be saved in the repo. The brief holds one link to the design, in a new `## Design` section. The gap check and the step before the demo read the design from that link when the host can. When it cannot be read (a Codex-only host, or no access), they use the design pages saved in the repo if there are any, or ask the person for the screen list, and say plainly that the design was not read. They never refuse for this. A UI fix in a prototype no longer waits for saved design images. (Source: your decision, 2 Nov 2026)
- `forge next` and the board show one status line, for example "Sign-off: 2 open questions, 5 of 7 demo steps done, signer Sam Lee". Forge leaves out a part that is zero or unknown. Under it, when nothing else is in progress, `forge next` lists the open items as a short checklist; the board lists them too. Each item has the phrase that fixes it. There is no `forge brief` command: the agent asks in chat and edits the file in a normal fix. (Source: your decisions, 2 Nov 2026; the status line is the coordinator's recommendation)
- A new client repo gets all of this from `forge init` and the guide. An existing client repo gets the same sign-off behaviour once the agent writes `sample_data = true` after asking (the repo must first move to a Forge release that knows the line), and keeps today's sign-off rules, personal-data refusal and CI until then. It gets the brief rules, the checklist and the design-link rule at once, because they are Forge's own behaviour; no migration, no app file changes, and an accepted sign-off stays accepted. It gets the new guide text with `forge sync`. (Source: the Forge review rules; this corrects the intake text, which said that every existing repo sees no change)

Design: none (adds one short list and one line to the board's existing Now screen, in its existing style; no new screen or flow)

## Why

A prototype that holds only made-up data is judged today like a real build. It runs tests and CI from the start, sign-off waits for a full green run and a whole-source review in rounds, and sign-off refuses while brief topics are open. The owner chose on 2 November 2026 to judge such a prototype by one small gap check, to start tests with the first build story, and to stop the brief from blocking work.

## Done when

1. **A prototype marked as sample-data signs off with no full test run and no whole-source review. One gap check runs once before the demo, with no rounds. The demo steps and the signer's record decide. Findings below that bar go to Known issues with no repair round. A most-serious finding, or one scored Gain 5 or Harm 4 or more, comes to the owner at once, who may accept it with a reason. A prototype without the mark keeps today's rules.**
2. **The agent writes `sample_data = true` in `forge.toml` after asking the person; a worker cannot. With it, a prototype runs no tests and no CI before sign-off, and close, land and merge work without them. After sign-off, `forge next` shows setting up tests as a visible first step. Real data or a back end keeps tests from day one.**
3. **The sign-off record reaches main in a pull request that holds only the record. Close and merge need no review and no tests for it, and the agent merges it. No hook, rule or branch protection is loosened.**
4. **No brief answer and no open client question blocks planning, review, close, merge or sign-off. "Not known yet" is accepted. Forge writes the Answers quote, and sign-off needs only the signer's name. A repo marked sample-data is never refused on an open personal-data answer, at sign-off, at the rules page or at a story start. Closing the fix that turns `sample_data` off is refused while the answer is open, and the first-release how-to lists it. A repo that never declared sample data keeps today's refusal.**
5. **The brief holds one design link. The gap check and the pre-demo step read the design from it when they can. Otherwise they use design pages saved in the repo, or ask for the screen list, and say plainly that the design was not read. They never refuse for this, and a UI fix needs no saved design images.**
6. **`forge next` and the board show one sign-off status line, and `forge next` lists the open items as a checklist when nothing else is in progress. Each item has the phrase that fixes it.**

## Risks

Risks: none one-way. Each part reverts with its pull request. No migration, no data change, no app file changes.

Trade-offs, in plain words:
- A sample-data prototype has no tests, no CI, no full run and no whole-source review before sign-off. A hole that only those would find reaches the client's demo. The light review of each fix and the gap check still run, and you chose this (2 Nov 2026).
- The agent writes `sample_data = true` after asking the person. Forge cannot check that the prototype really has no back end. The gap check and the line's own meaning are the only guards.
- A sample-data prototype can sign off, approve its rules page and start stories with the personal-data answer still open. The refusal comes only when the switch is turned off. If real data arrives while the switch stays on, nothing refuses, because Forge cannot see real data; the guide and the first-release how-to are then the only guards. A person can also turn the switch off outside close, but main changes only through a pull request, and close sees every one.
- A repo that already has CI keeps it. Forge does not remove checks from `forge.toml` or from GitHub's branch protection; a person does.
- The status line's demo-step count needs the demo-step list that FORGE-ONEPLAN-1 adds. Until that story merges, the line leaves that part out.

Model cost: lower overall, not measured. A sample-data prototype pays one small call at sign-off instead of two strict whole-source rounds, repair rounds and a full run, and pays no test or CI time before sign-off. The record pull request, the brief rules, the checklist and the status line use no model call.

### Settled (with the reason)

1. **The switch is `sample_data = true` in `forge.toml`; the sign-off decision's line stays as a fallback.** `repo.sample_data(top, fields)` returns the `forge.toml` value when the key is present (true or false) and otherwise the decision's line. Reason: the sign-off decision may not exist early, `forge.toml` always does, and a worker cannot change it; the agent edits it after asking the person, as for other settings. The review block and the skill text that say "only a person may write" the line change to say that the agent writes it after asking the person. One `or` keeps v1.2.27 repos working with no migration. A bool needs a small branch in `repo._config_problem`.
2. **No tests and no CI is a setting, not new code.** The guide tells the agent to run `forge init --actions no` for a sample-data prototype and to write `test = ""`, `test_place = "local"`, `checks = []` with the switch. `prcheck.ships` writes no workflow while `sample_data` is true; the builder checks what `forge sync` does with a workflow that is already there and reports it. Forge does not edit branch protection; `doctor` already reports a mismatch. Reason: close, land and merge already work this way (see evidence). The worker brief changes too: `src/forge/worker.py` picks a new `<!-- sample-proof -->` block in `templates/brief.md` instead of the `prototype_proof` block while `repo.sample_data` is true (for a fix and for a task). The block says: write and run no tests; walk each demo step in a browser and record how in the commit's Proof list; the light review expects no tests. Workers do not read the coordinator guide, so this block is their only source. The light review's prompt for a sample-data prototype (`review.instructions`) likewise stops asking for test evidence.
3. **The visible first step.** While `sample_data = true` and the fetched default branch holds an accepted sign-off, `forge next` prints `Next: forge fix start "Set up tests and CI" --done "forge.toml names the tests and checks, sample_data is removed, and the tests run on pull requests" --kind mechanical`, and the journey step line says so. Nothing refuses. Reason: the owner asked for a visible step, not a gate (principle 4). Its Done-when names `forge.toml`, so a worker may edit it (`task.settings_allowed`).
4. **The gap check is one `review.run` call with a new `<!-- gapcheck -->` block in `templates/review.md`, on the same engine and `[models.review]` setting.** The prompt names the inputs: the brief's Answers section, the design (Settled 7), and the app's routes, which the model finds itself (route tables, controllers, routers); it reports each missing screen, answer or route as a finding and runs no whole-source review. Reason: `interfaces` in `forge.toml` is empty by default, so Forge cannot list routes with a pattern. The check really limits the files. `review.run` gets one new argument, `only`, a list of path patterns; after the sign-off snapshot is built, every product file that matches none of them is removed from the snapshot before the engine starts (about ten lines in `review.py`). For the gap check `only` is: `docs/product/BRIEF.md`, `docs/design/prototype/**`, and the route files, which are the `interfaces` patterns of `forge.toml` or, when it names none, `init.INTERFACES`. A route file that matches no pattern is not seen; the check then says so in a note and reports no gap for it. Reason: a prompt cannot narrow what the engine receives, and a second call that bypasses `review.run` would copy its clone, model and run-record code.
5. **One check, no rounds.** The accept command with no client reply runs the gap check; a rerun is a new call and never counts as a round. A held finding stops at once with the owner's question; held means a P0, or a finding that `score.holds(finding, "P0")` holds (Harm 4 or more, or Gain 5, whatever its priority), which is the test `_signoff_known` already uses to keep a finding out of Known issues (`review.stop_question`; accept with `--resolve accept --reason` keeps it in Known issues, as in v1.2.27; `more` is the owner asking for a repair round; `split` makes a follow-up fix). Every other finding goes to Known issues through `_signoff_known`. The full-run gate is skipped, and the review prompt's "full run passed" paragraph is left out. The demo steps still need a Proof section; for a sample-data prototype each line says how the step was walked (the browser walk and its date), not a test name.

Reason: a direct push is impossible under GitHub protection and refused by Forge's hooks; this path touches no hook, no `repo._work_branch` rule and no protection. With `checks = []` and no workflow there is nothing to wait for.
