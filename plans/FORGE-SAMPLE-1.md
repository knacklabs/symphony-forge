# Sample-data prototypes get a light sign-off

5 parts · Risks: none one-way · New moving parts: none

## What changes for you

- A prototype that holds only made-up data and has no back end can be marked as a sample-data prototype. A person writes one line, `sample_data = true`, in `forge.toml`. Forge keeps that file out of a worker's hands, so only a person (or the agent on the person's say) writes the line. Today the same switch exists as a line in the sign-off record; that record may not exist early in the prototype, so the line moves to `forge.toml`. A repo that already wrote it in the sign-off record keeps working. (Source: your decision, 2 Nov 2026; the place is a recommendation)
- Before sign-off, a sample-data prototype has no tests and no CI (GitHub's automatic checks). The agent walks the demo steps in a browser before it shows the client. Tests begin with the first build story, and Forge shows that as a visible first step after sign-off. A prototype with real data or a back end keeps tests from day one. A full green run still comes before any real-data or production release. (Source: your decision, 2 Nov 2026)
- A sample-data prototype signs off with no full test run and no whole-source review. One small gap check, one model call, runs once before the demo, with no rounds. It reads the brief, the client's answers, the design, and the app's routes, and reports what is missing. The demo steps and the signer's record stay. Every other finding goes to the Known issues list (the list of known problems that the board shows beside the item), with no repair round unless you ask for one. If the check finds the most serious kind of problem (a security hole, a data leak or data loss in normal use), it comes to you, and you may accept it with a reason, as you can today. A prototype without the line, or with real data or a back end, keeps today's sign-off rules. (Source: your decision, 2 Nov 2026)
- The sign-off record reaches the main branch in a pull request that holds only that record. The agent merges it at once, with no second review and no tests. GitHub's branch protection, which Forge turns on, requires a pull request and also binds admins, so a direct push to main is impossible there; Forge's own hooks refuse it as well. This plan therefore asks for no exception to "main changes only by pull request". (Source: your decision, 2 Nov 2026, adjusted because a direct push cannot work; see Notes)
- The brief informs and never blocks. No answer in the brief and no open client question stops planning, review, close, merge or sign-off. "Not known yet" is an accepted answer and is not a review finding. The brief's Answers section is the one running list, written during the talks. Forge writes its quote into the sign-off record, so nobody copies it by hand. Sign-off needs only the signer's name. The checks on the customer's name format, the demo address and the list of ways the client replied go. Forge keeps the record of the client's reply. (Source: your decision, 2 Nov 2026)
- An open personal-data answer is refused only before the first real-data release. Forge has no release step today (see Notes). The simplest place is the approval of the app's rules page that every new story needs after sign-off, where Forge already refuses an open personal-data answer. The first-release how-to also lists it. This story moves no check there; it only stops asking for the answer earlier. (Source: your decision, 2 Nov 2026; the place is a recommendation)
- The design can be made through Forge or separately, and both work. Forge requires no way of making it and does not require it to be saved in the repo. The brief holds one link to the design, in a new `## Design` section. The gap check and the step before the demo read the design from that link when the host can. When it cannot be read (a Codex-only host, or no access), they use the design pages saved in the repo if there are any, or ask the person for the screen list, and say plainly that the design was not read. They never refuse for this. A UI fix in a prototype no longer waits for saved design images. (Source: your decision, 2 Nov 2026)
- `forge next` and the board show one status line, for example "Sign-off: 2 open questions, 5 of 7 demo steps done, signer Sam Lee". Forge leaves out a part that is zero or unknown. Under it, when nothing else is in progress, `forge next` lists the open items as a short checklist; the board lists them too. Each item has the phrase that fixes it. There is no `forge brief` command: the agent asks in chat and edits the file in a normal fix. (Source: your decisions, 2 Nov 2026; the status line is the coordinator's recommendation)
- A new client repo gets all of this from `forge init` and the guide. An existing client repo gets the same sign-off behaviour once a person writes `sample_data = true` (it must first move to a Forge release that knows the line), and keeps today's sign-off rules and its CI until then. It gets the brief rules, the checklist, the personal-data timing and the design-link rule at once, because they are Forge's own behaviour; no migration, no app file changes, and an accepted sign-off stays accepted. It gets the new guide text with `forge sync`. (Source: the Forge review rules; this corrects the intake text, which said that every existing repo sees no change)

Design: none (adds one short list and one line to the board's existing Now screen, in its existing style; no new screen or flow)

## Why

A prototype that holds only made-up data is judged today like a real build. It runs tests and CI from the start, sign-off waits for a full green run and a whole-source review in rounds, and sign-off refuses while brief topics are open. The owner chose on 2 November 2026 to judge such a prototype by one small gap check, to start tests with the first build story, and to stop the brief from blocking work.

## Done when

1. **A prototype marked as sample-data signs off with no full test run and no whole-source review. One gap check runs once before the demo, with no rounds. The demo steps and the signer's record decide. Findings below the most serious kind go to Known issues with no repair round. A most-serious finding comes to the owner, who may accept it with a reason. A prototype without the mark keeps today's rules.**
2. **A person writes `sample_data = true` in `forge.toml`; a worker cannot. With it, a prototype runs no tests and no CI before sign-off, and close, land and merge work without them. After sign-off, `forge next` shows setting up tests as a visible first step. Real data or a back end keeps tests from day one.**
3. **The sign-off record reaches main in a pull request that holds only the record. Close and merge need no review and no tests for it, and the agent merges it. No hook, rule or branch protection is loosened.**
4. **No brief answer and no open client question blocks planning, review, close, merge or sign-off. "Not known yet" is accepted. Forge writes the Answers quote, and sign-off needs only the signer's name. An open personal-data answer is refused only when the app's rules page is approved for the first story after sign-off, and the first-release how-to lists it.**
5. **The brief holds one design link. The gap check and the pre-demo step read the design from it when they can. Otherwise they use design pages saved in the repo, or ask for the screen list, and say plainly that the design was not read. They never refuse for this, and a UI fix needs no saved design images.**
6. **`forge next` and the board show one sign-off status line, and `forge next` lists the open items as a checklist when nothing else is in progress. Each item has the phrase that fixes it.**

## Risks

Risks: none one-way. Each part reverts with its pull request. No migration, no data change, no app file changes.

Trade-offs, in plain words:
- A sample-data prototype has no tests, no CI, no full run and no whole-source review before sign-off. A hole that only those would find reaches the client's demo. The light review of each fix and the gap check still run, and you chose this (2 Nov 2026).
- A person writes `sample_data = true`. Forge cannot check that the prototype really has no back end. The gap check and the line's own meaning are the only guards.
- The personal-data refusal comes after sign-off, at the first story. A prototype with an open answer reaches sign-off, and the client may sign before the answer exists.
- A repo that already has CI keeps it. Forge does not remove checks from `forge.toml` or from GitHub's branch protection; a person does.
- The status line's demo-step count needs the demo-step list that FORGE-ONEPLAN-1 adds. Until that story merges, the line leaves that part out.

Model cost: lower overall, not measured. A sample-data prototype pays one small call at sign-off instead of two strict whole-source rounds, repair rounds and a full run, and pays no test or CI time before sign-off. The record pull request, the brief rules, the checklist and the status line use no model call.

### Settled (with the reason)

1. **The switch is `sample_data = true` in `forge.toml`; the sign-off decision's line stays as a fallback.** `repo.sample_data(top, fields)` is true when either says so. Reason: the sign-off decision may not exist early, `forge.toml` always does, and a worker cannot change it. One `or` keeps v1.2.27 repos working with no migration. A bool needs a small branch in `repo._config_problem`.
2. **No tests and no CI is a setting, not new code.** The guide tells the agent to run `forge init --actions no` for a sample-data prototype and to write `test = ""`, `test_place = "local"`, `checks = []` with the switch. `prcheck.ships` writes no workflow while `sample_data` is true; the builder checks what `forge sync` does with a workflow that is already there and reports it. Forge does not edit branch protection; `doctor` already reports a mismatch. Reason: close, land and merge already work this way (see evidence).
3. **The visible first step.** While `sample_data = true` and the fetched default branch holds an accepted sign-off, `forge next` prints `Next: forge fix start "Set up tests and CI" --done "forge.toml names the tests and checks, sample_data is removed, and the tests run on pull requests" --kind mechanical`, and the journey step line says so. Nothing refuses. Reason: the owner asked for a visible step, not a gate (principle 4). Its Done-when names `forge.toml`, so a worker may edit it (`task.settings_allowed`).
4. **The gap check is one `review.run` call with a new `<!-- gapcheck -->` block in `templates/review.md`, on the same engine and `[models.review]` setting.** The prompt names the inputs: the brief's Answers section, the design (Settled 7), and the app's routes, which the model finds itself (route tables, controllers, routers); it reports each missing screen, answer or route as a finding and runs no whole-source review. Reason: `interfaces` in `forge.toml` is empty by default, so Forge cannot list routes with a pattern. The builder checks the size of the call on a fixture; if the engine still receives the whole product as an addition, the snapshot is narrowed to the brief and the files that define routes.
5. **One check, no rounds.** The accept command with no client reply runs the gap check; a rerun is a new call and never counts as a round. A P0 stops at once with the owner's question (`review.stop_question`; accept with `--resolve accept --reason` keeps it in Known issues, as in v1.2.27; `more` is the owner asking for a repair round; `split` makes a follow-up fix). Non-P0 findings go to Known issues through `_signoff_known`. The full-run gate is skipped, and the review prompt's "full run passed" paragraph is left out. The demo steps still need a Proof section; for a sample-data prototype each line says how the step was walked (the browser walk and its date), not a test name.
6. **The record reaches main in a pull request that holds only it.** `close.close` counts a change as `records_only` when its paths are under `review.BOOKKEEPING` or are `docs/decisions/` files that end in `client-signoff.md`, and skips the local test run for a `records_only` change. These are line edits in `close.py` with no net lines. It applies to every prototype's sign-off record, because that record's review already ran in the accept command. Reason: a direct push is impossible under GitHub protection and refused by Forge's hooks; this path touches no hook, no `repo._work_branch` rule and no protection. With `checks = []` and no workflow there is nothing to wait for.
7. **The design is one link in the brief.** `templates/skeleton/docs/product/BRIEF.md` gets `## Design` with `- Link: <url>` and an optional `- Screens: <list>`. A new helper `design.source(top)` returns the link, else the saved pages, else the `Screens` line, else none. The gap check prompt names the source and asks for a P3 note titled `Design not read: <why>` when it cannot open the link; Forge prints that note's text and the next step ("say: The screens are <list>, or save pages in docs/design/prototype/") and never refuses. `design.require_prototype` accepts the link as the design; committed images and an accepted `prototype-design` still count where they exist. The pre-demo step is guide text: the host that can read the link reads it, lists the screens, compares them with the app and builds what is missing or tells the person.
8. **The brief rules apply to every prototype, and open client questions stop blocking.** `open_decisions.blocking` leaves the sign-off gap list; `forge decision open` still prints its list. Reason: decisions 4 and C say no brief answer and no open question blocks; deleting checks makes Forge smaller. The checks that go: Answers mismatch, the three pattern checks, the topic checks, the Sign-off person match, `open_decisions.blocking`. `approved_via` and `approved_on` stay as written fields, and the `approved_on` date check stays (not named by the owner).
9. **Forge writes the Answers quote.** At accept, Forge sets the decision's `## Answers` section to the brief's current Answers section and commits it with the checks. `customer` is the signer's name: non-empty, one line.
10. **"Not known yet" parses as an ordinary answer** (`ANSWER_LINE` already accepts any text). `ask the client`, `later`, a missing line and a malformed line stay open. One exception: for `Personal data`, `not known yet` counts as open at the one place that refuses it. Reason: a regulated-data question cannot be waved through with a placeholder.
11. **The personal-data place is the existing constitution approval.** `_constitution_gaps` keeps its line; `deploy.md`'s First production release gets one line that the answer must be settled. The cold read stops reporting `Decide first`. Reason: Forge has no release step and Promote is outside Forge (principle 4).
12. **The status line and the checklist.** The line is built from three counts: open items (open must-answer topics plus complete open client questions), demo steps done of all (from the plan record's `## Demo steps` and the Proof ticks that FORGE-ONEPLAN-1 adds; no part before it merges) and the signer (the Sign-off person answer). A part that is zero or unknown is left out; with no part, no line. The checklist is one line per open item, `- <item>. Say: "The client answered <item>: <answer>"`, printed under the status line in `forge next` only when the run lists nothing else, and always on the board. The board snapshot gets one key, `signoff` (`line` and `open`, empty when the repo is not a prototype); `now.js` shows it as one quiet line and list under "Needs you", no colour, no badge, hidden when empty. The new code sits in `nextstep.py` and `board_facts.py`; `board.py` gets one line and loses one.
13. **Two items moved to a second story.** Milestone review passes and the sign-off repair close apply only to prototypes without the switch and share no file with the parts below except `records.py` and the guide. See Notes.
