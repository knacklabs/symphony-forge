# Merge several ready items in one train

2 parts · Risks: none one-way · New moving parts: none

## What changes for you

- A merge train is a group of ready changes that Forge tests together once and then merges one after the other. When Forge merges all ready changes in one run (`forge land --all`) and two to five changes are ready, it now uses a train. Today each waiting change runs its full check again after each merge. In a train, one combined check replaces these runs. (Source: your decision, 12 Nov 2026: plan the merge train first)
- The train runs only where the agent merges and CI runs the tests. Forge reads these settings from the newest default branch when the train forms. Repos where a human merges and repos that run the tests on the laptop work as today. There is no new command and no new setting. (Source: the planner's choice; confirm)
- Some changes stay out of the train and merge one at a time, as today: a change that clashes with the default branch or with a change already in the train, a change that is built on another change that has not merged, and a change to Forge's settings file. Two changes that both edit a file that Forge merges with its own rule, such as the roadmap, count as a clash, because GitHub does not have that rule. A train holds at most five changes, the oldest first, counted after the clashes are taken out. Forge names each change that stays out, and why. (Source: the planner's choice; confirm)
- Forge runs the combined check on a temporary draft pull request (a pull request that GitHub does not merge until someone marks it ready). Its branch name starts with "forge-merge-train/" and ends with the code of the tested commit, and its title is "Forge merge train: ... (do not merge)". Forge never overwrites or deletes a branch or pull request that it did not make in the same run: if the branch name already exists, Forge runs no train. Forge's own review check on the draft stays red on purpose, so nobody can merge it, and Forge does not count that check. When the train ends, also after a failure, Forge closes this pull request and deletes its branch. The CI workflow of the repo does not change. (Source: the planner's choice; confirm)
- When the combined check passes, Forge merges each change in order. Each change keeps its own pull request, record and outcome, and the last part of a story still records the story as done. Before each merge, the default branch must hold exactly what the train tested so far, and the change's pull request must still hold the commit that the train tested. If not, that change and the remaining changes merge one at a time, each with its own check. After the last merge, Forge compares the default branch with the tested combination and names any difference at the end of its summary. (Source: the planner's choice; confirm)
- Other changes in the same run still close while the train runs, but they merge only after the train ends. This includes ready changes that stay out of the train. Without this hold, one of their merges would move the default branch and make the train's check useless. A change that is not ready and edits a file that a change in the train also edits waits until the train ends before it closes, as it waits for an older change today. This keeps it from a second review. (Source: the planner's choice; confirm)
- When the combined check fails, Forge waits until every job of that check has finished. Then it looks in the failed jobs' logs for the changed files of each change in the train. If the logs name the files of exactly one change, that change leaves the train. When two or more others remain, they run once more as a new train; a single other change merges one at a time. The change that left merges last, one at a time, with its own check. If that check fails too, it stops under "Needs you" with the failure. If the logs name no change, Forge runs the failed jobs again once, because a flaky test (a test that sometimes fails with no code problem) or a CI problem can cause this. If they fail again, or the logs name several changes, every change merges one at a time as today. This first version does not split a failed train into halves to find the cause. (Source: the planner's choice; confirm)
- In a repo where GitHub requires each pull request to be up to date with the default branch before it merges, a train cannot save checks. When Forge can read that rule, it runs no train. When it cannot read the rule and GitHub then says a pull request in the train is behind, the remaining changes merge one at a time. In both cases Forge says so in one line. (Source: the planner's choice; confirm)
- What to expect in the reported case. These numbers are reasoned, not measured. A train removes repeated runs. It does not remove real file clashes: about 10 of the 23 stops on the one change stay, and so do its own 2. Up to 7 stops came from other merges that broke the default branch; a train prevents those when the changes that broke it are in the same train, because Forge tests the combination before any of them merges. The 4 flaky or CI stops can become fewer, because fewer runs happen, but one flaky run now delays every change in the train. So expect about 7 to 9 fewer stops of the 23. For time: with 4 ready changes that merge one after another, today each one waits for its own new run, 3 or 4 runs of 26 to 57 minutes, so about 80 to 230 minutes, and more when a change must run again after another merge on the same files. A train needs one combined run, which takes about as long as the longest check in the group, so about 30 to 60 minutes. When the land run already handles the changes side by side, today's runs partly overlap in time, so the time saved is smaller: about one run for each change that edits the same files as a change that merged before it. (Source: the client team's report, 12 Nov 2026)
- Cost. The train makes no model call, so model cost does not change. CI minutes: one combined run in place of one run per change when the train passes; one extra run when a train fails. (Source: the planner's estimate)
- A new client repo gets the train in its first land run once the agent merges and CI runs its tests, and the guide explains it from setup. An existing client repo gets the train when it upgrades to this release, with no setting to change and no change to its CI workflow; it gets the guide text on sync. (Source: Forge's rule for new and existing repos)

Design: none (the change is lines that Forge prints in the terminal and a paragraph in the guide; there is no screen)

## Why

A client team that lets the agent merge and runs its tests in CI reported this on 12 Nov 2026. Often 3 to 5 changes are ready at the same time. Each merge moves the default branch. Then each other waiting change takes in the default branch and runs its full pull request check again. One check takes about 26 minutes for a normal fix and up to 57 minutes for a large part. The team merges about 11 changes in a day, and most of the wait is in these new runs. One change stopped about 23 times: about 10 real file clashes, about 7 failures from tests that other merges broke on the default branch, about 4 flaky tests or CI problems, and 2 of its own.

Forge added the new run on 28 Oct 2026, after two changes that each passed close left the default branch red together. The new run protects the default branch, but it tests each change again after each merge. GitHub does not ask for it: Forge does not turn on GitHub's rule that branches must be up to date. Today the team can only wait, or merge by hand without a new check and risk a red default branch.

## Done when

1. **When Forge merges all ready changes in one run, in a repo where the agent merges and CI runs the tests, it tests two to five ready changes together once on a temporary draft pull request that it closes afterwards, and then merges each change in order without a new run of its own check.**
2. **A change that clashes with the default branch or with a change already in the train, a change built on a change that has not merged, and a change to Forge's settings file stay out of the train and merge one at a time as today; with laptop tests, a human merge setting, or a GitHub rule that each pull request must be up to date, no train runs or the rest of it goes one at a time, and for that rule Forge says why in one line.**
3. **When the combined check fails and the failure names the files of exactly one change, that change leaves the train, the others are tested together once more when two or more remain, and that change merges last, one at a time, with its own check or stops with that check's failure for you.**
4. **When the combined check fails and names no change, Forge runs the failed jobs again once; when they fail again, or the failure names several changes, every change merges one at a time as today.**
5. **Before each merge the default branch must hold exactly what the train tested so far and the change's pull request must hold the tested commit, or that change and the rest merge one at a time, and after the last merge a default branch that differs from the tested combination is named at the end of the run's summary.**

## Risks

Risks: none one-way. Each part reverts with its pull request. The train merges only changes that already passed close, through the normal merge. It deletes only the branch it made in the same run, and only while that branch still holds the commit it pushed.

Trade-offs, in plain words:
- Only the final combination is tested. While the train merges, for a few minutes the default branch holds the first changes without the later ones, and no check tested that middle state alone. If the merges stop half way (for example, GitHub refuses one merge), the default branch keeps such an untested state until the next pull request check or the nightly full run.
- A flaky test in the combined check delays every change in the train by one more run.
- A failure that names no change costs one extra run before the changes go one at a time.
- A failure can name the wrong change, for example when two changes break a test together. That change then runs its own check, and it merges if that check passes. This costs one run.
- A failure in a test that no change in the train edits, with a log that names none of their files, names no change. It counts as "names no change" above.
- When the default branch moves outside the train after the combined check, that check is wasted, and the changes go one at a time.
- Ready changes that stay out of the train, and other changes in the same run, now merge after the train ends, so they can merge up to one combined check later than today. A change that shares a file with the train also starts its close later.
- If the land run stops in the middle (for example, the terminal closes), the draft pull request and its branch stay. Forge does not use them again. Close that pull request and delete its branch; it never merges.
- A repo whose own CI skips draft pull requests gets no result for the train. Forge waits up to 30 minutes with no progress, then merges one at a time.

## Notes

- **Owner decision (12 Nov 2026, settled).** Plan the merge train first, for the problem that a client team with agent merges and CI tests reported.
- **The planner's choices, for the owner to confirm (recommendation first).**
  1. Where the train runs: inside the land run for all ready changes, with no new command and no new setting, only with agent merges and CI tests, for two to five ready changes. Other option: a new setting to turn it on per repo.
  2. How the combination is tested: a temporary draft pull request on a new branch whose name holds the tested commit, closed after. Other option: a branch push with no pull request, which needs a workflow change in every existing repo.
  3. What a failure in one change does: that change leaves, the others run once more, and that change then merges last with its own check, which also stops the loop where it would join the next train with the same code. Other option: send it straight back to its worker, which saves one run when the blame is right but needs a new record to stop that loop.
  4. No check of the default branch's health before a re-run: the only signal is the nightly full run, which can be up to a day old. Other option: a later story.
  5. Other changes in the run merge after the train ends, and a change not yet ready that shares a file with the train waits to close. Other option: let them merge, and accept that a train then often fails its default-branch match.
  6. A change to Forge's settings file stays out, because it can change how the tests run.
  7. At most one second train per run.
