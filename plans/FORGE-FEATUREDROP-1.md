# Remove a feature from a client app in one change

2 parts · Risks: none one-way · New moving parts: none

## What changes for you

- A person tells the agent to remove a feature, for example "we do not need invoices any more". The agent runs one Forge step that removes the feature's API (the part of the app that screens and other programs call), its agent tools, its access rules, its tests and the lines that connect it to the rest of the app. It all happens in one change, and the app still builds and passes its own tests. (Source: your words, 10 Nov 2026)
- The same step then checks the whole app for anything that still points at the removed feature: screens, menu entries, routes, access rules, tests, imports and sample-data lines. It lists each one. Forge ships no screens, so the agent removes these from the client's own files, in the same change, and runs the step again until the list is empty.
- If another feature uses the one being removed, for example jobs that link to clients, the step stops before it changes anything and names the features that use it. The agent tells the person and asks which feature to remove first.
- No customer data is deleted. The feature's table, every row in it and its change history stay in the database. The made-up records of a sample-data prototype leave with the feature, because the agent removes the lines that load them. Deleting the table is a separate step for later. The agent takes it only when the person asks, and the guide says how. This story does not build that step. The same rule holds with real data or with made-up data, so there is one path to learn.
- A feature that the build step did not make, or that people changed a lot by hand, uses the same step. It removes the parts it knows and lists the rest. The agent finishes by hand with a list of places in the guide, then runs the step again as the check.
- A new client repo gets the guide text at start. An existing client repo gets the step and the guide text after upgrade and sync, and its app files do not change. An app that did not start from the Forge starter, such as one made before the build step existed, gets a refusal from the step that names what is missing. Its agent removes the feature by hand with the guide's list.

Design: none (Forge ships no screen; the client's agent changes the client's own screens)

## Why

Sales build a prototype with the Forge design system and made-up data, and it goes live so the customer can try it. Later the team adds features and removes the ones that are not needed. Adding a feature has one Forge step today. Removing one has none. The agent deletes files by hand and can leave a route, a menu entry, an access rule, a test or a sample-data line behind, or delete something that another feature uses. The owner asked for the reverse of the build step on 10 November 2026.

## Done when

1. **In an app made from either starter, removing a feature that the build step made removes its API, agent tools, access rules, tests and connecting lines in one change. The app still builds and its own tests pass.**
2. **When another feature uses the feature, the removal stops before it changes anything and names each feature that uses it.**
3. **After a removal, by the step or by hand, the check lists each screen, menu entry, route, access rule, test, import and sample-data line that still points at the removed feature, and it fails until none is left.**
4. **A removal writes no migration and changes no table. The table, its rows and the change history stay, the app's own database tests still pass, and the feature's sample-data lines are among the leftovers the check lists.**
5. **The guide and the worker brief turn "remove this feature" into this path, say what happens to data, and list the places to clean by hand for a feature the step cannot remove. A new repo gets the text at start. An existing repo gets the step and the text after upgrade and sync with no app file changed. An app that is not a starter app gets a refusal that names what is missing.**

## Risks

Risks: none one-way. Each part reverts with its pull request, and a removal in a client app is code only, so a revert brings the feature back.

The story builds no data deletion. The guide names the later table drop as a separate one-way step. The agent takes it only when the person asks, after the release that no longer reads the table has been live, and after the backup that Mainline takes when a release adds a migration. Forge already asks for a written reason in such a migration.

Trade-off: a removed feature leaves its table and its model in the database layer. The app's own database tests need the model while the table exists, so the table, its data model and its migration stay until the separate drop. A demo database keeps the old sample rows, unseen.

Trade-off: Forge does not find a removal that someone did by hand and never checked. The guide tells the agent to run the check; no gate forces it.

Model cost: none added. The step and the check read and edit files. They make no model call.

### Words this story pins

- **The option.** `forge task feature <plural> --remove`. `--one` and `--field` stop being required by the parser. Without `--remove`, `build` refuses a missing `--one` or `--field` with the plain message `forge task feature needs --one and at least one --field.` and the next step `add them, or add --remove to remove the feature.` With `--remove`, giving `--one` or `--field` is refused with `--remove takes only the feature's plural name.` The listing in `COMMANDS` becomes `Builds a feature from the starter, or removes it with --remove`.
- **One flow, in `src/forge/feature_remove.py` (new, under 1,200 lines).**
  1. Starter check. The app is a TypeScript starter app when `apps/api/src/app.module.ts` is there, and a Python starter app when `apps/api/app/main.py` is there. Neither: refuse `forge task feature --remove needs a starter app (one made with forge init --starter), and this app has neither apps/api/src/app.module.ts nor apps/api/app/main.py.` with `Next: remove the feature by hand with the guide's list, then check it with forge task feature <plural> --remove.` Nothing is written. No other guard: an older starter app without organisations or history still passes, because removal reads only the feature's own folder and lines.
  2. Users check. Users are files of another module that import the feature: TypeScript files under `libs/<other>/` that contain `@app/<plural>-contracts`, `@app/<plural>-server` or `<PLURAL>_API`; Python files under `apps/api/app/<other>/` that import `app.<module>`. Files under the feature's own folders, the wiring lines the command itself added, and everything outside the module folders (`apps/web`, the demo loader, other tests) are not users. Any user: refuse with `The feature <plural> is used by <other module>, <other module> (<first file of each>).` and `Next: remove that link or that feature first, then run this line again.` Nothing is written. There is no override option.
  3. Removal (REMOVE only). Delete and unwire as the lists under item 1 say, in memory first and then write, as `build` does.
  4. Leftover check (CHECK). Scan the files `git ls-files -co --exclude-standard` lists, skipping `.git`, `docs/`, `plans/`, `.factory/`, `.claude/`, `.codex/`, `apps/api/prisma/`, `apps/api/migrations/` and the kept data-layer files. Token classes, each with one case in the test: (a) `@app/<plural>-(contracts|server|web)` and `libs/<plural>/`; (b) `/api/v1/<plural>` and a quoted route `/<plural>`; (c) the permission names `<plural>.(view|create|edit|delete|restore)`; (d) Python `app.<module>`, `<module>_router`; (e) `<Title>Module`, `<Title>Tools`, `<PLURAL>_API`; (f) a Prisma accessor such as `prisma.<camelSingular>` or `tx.<camelSingular>`, and a tool name that starts with `<module>_`. Print each match as `path:line  text`, then fail with `Forge found <n> places that still point at <plural>.` and `Next: remove them (screens, menu entries, routes, tests and the demo loader are yours to change), then run this line again.` Exit 0 with `Nothing points at <plural> any more.` when none is left.
  5. If the feature folder is already gone, run only step 4. If it is gone and nothing matches, print `Nothing named <plural> is left.` and exit 0.
- **Output of a removal.** `Removed <path>` for each deleted file or folder, `Edited <path>` for each wiring file, `Kept <path>` for each kept data-layer file, then the check's result. A Python removal ends with the line `Next: run corepack pnpm run api-types, then the tests.` because the shared API types still hold the removed routes.
- **The kept data layer.** TypeScript: `apps/api/prisma/schema/<plural>.prisma`, the migration folder, the name in `base.prisma`'s `schemas`, the relation lines in `Account` and `Organisation`, and the `database.e2e-spec.ts` catalog entry. Python: `apps/api/app/<module>/models.py` (with `__init__.py` cut down to the one line that imports it), the Alembic revision, `import app.<module>` in `env.py`, the `<plural> internals` contract, and the inventory and filter lines in `test_module_schemas.py`. A wiring line that someone changed stays in the file, and the check lists it. Files outside the feature's folders are never deleted or rewritten except those wiring lines.

## Notes

- **Open owner questions.** Recommended answer first.
  1. Build the removal itself, or only the check and the guide? Recommended: build it, as the second part on top of the check. The two parts ship as one release, and the first part already works alone. The score from AGENTS.md: F is 3 (a prototype team removes features daily across many users), H is 2 (a leftover route, access rule or deleted shared code is a broken step or wrong information), C is 3 (two stacks and about 250 changed lines outside tests). F x H is 6 and 2 x C is 6, so it passes on equality only. The check and guide alone score C 2, so 6 against 4, and they catch every leftover the owner listed, but the agent still edits about ten wiring files by hand in each stack. If you pick the cheaper version, drop REMOVE and the story is the first part only; Done-when 1 and 4 then fall away.
  2. Does a sample-data prototype drop the table in the same change? Recommended: no, one rule for all apps. The table stays and the made-up rows leave with the feature through the demo loader. Reasons: the app's own database tests need the model while the table exists, the drop needs a migration with a written reason, and an unused empty-looking table in a demo costs nothing. The separate drop remains available when the person asks.
  3. A feature that someone built by hand: same step, removes what it knows and lists the rest (recommended), or refuse and leave everything to the agent. The first follows the rule that Forge does the right thing by default and refuses only when a mistake costs a lot; a removal is one pull request and a revert undoes it.
- **Planner choices.** (1) An option on the existing command, `--remove`, so there is no new top-level command and the 25-command cap holds. (2) The users check refuses with no override option. (3) The check reads files for text, with no parser, because the module boundary rules already decide who may import whom and the generated imports have fixed text. (4) The check also runs when the folder is already gone, so a removal by hand gets the same check. (5) The step edits only the wiring lines that the build step wrote, and reports everything else, so no client file is rewritten. (6) Docs, plans and records are not scanned; the guide tells the agent to update the brief's record types, the Roles table and the demo steps. (7) The first change keeps the data layer, so the app's own schema tests stay green and the previous release can still roll back.
- **F x H >= 2 x C for the check.** F 3, H 2, C 2 (about 150 lines, no model call): 6 against 4. The users refusal is part of the same module and adds under 30 lines.
- **What a new and an existing client repo get.** New repos (`forge init`, either starter, or plain): the guide text and brief text, and the step, which Forge itself provides; plain init gets the step's refusal. Existing repos on upgrade and sync: the same texts and the step, with no app file changed. An existing starter app, including one made from an earlier starter, can use the step at once.
