# Remove a feature from a client app in one change, with a check

2 parts · Risks: none one-way · New moving parts: none

## What changes for you

- A person tells the agent to remove a feature, for example "we do not need invoices any more". The guide gives the agent one fixed list of places to clean, for each of the two starters. The list covers the feature's API (the part of the app that screens and other programs call), its agent tools, access rules and tests, the lines that connect it to the app, and the client's own screens, menu entries and sample-data lines. The agent works through the list by hand, in one change, and runs the app's own tests. (Source: your words, 10 Nov 2026; your choice of the check and the guide, 10 Nov 2026)
- Then Forge checks, with no model call, that nothing still points at the removed feature. It lists each screen, menu entry, route, access rule, test, import and sample-data line that is left, and it fails until none is left. If it cannot find the feature's data model, it says so and does not report all clear. The check changes no file.
- The agent runs the check before it starts, too. If another feature still uses the one being removed, for example jobs that link to clients, the check names the features that use it. A feature uses another when its code imports it or calls its web address. A comment or an example text is not a use. The agent tells the person and asks which feature to change first.
- No customer data is deleted. The feature's table, every row in it and its change history stay in the database. The made-up records of a sample-data prototype leave with the feature, because the check lists the lines that load them and the agent removes those lines. Deleting the table is a separate step for later. This story adds no rule for it: the guide points to the database rule and the backup rule that already exist.
- A feature that the build step did not make, or that people changed a lot by hand, uses the same list and the same check.
- A new client repo gets the guide text and the check at start. An existing client repo gets the check and the guide text after upgrade and sync, and its app files do not change. In an app that did not start from the Forge starter, such as one made before the build step existed, the check refuses and says what is missing. The guide then tells the agent to search the code for the feature's name and to run the app's own build and tests.
- Not in this story: Forge deleting the feature's files itself. See the Notes.

Design: none (Forge ships no screen; the client's agent changes the client's own screens)

## Why

Sales build a prototype with the Forge design system and made-up data, and it goes live so the customer can try it. Later the team adds features and removes the ones that are not needed. Adding a feature has one Forge step today. Removing one has none. The agent deletes files by hand and can leave a route, a menu entry, an access rule, a test or a sample-data line behind, or delete something that another feature uses. The owner asked for a way to remove a feature on 10 November 2026 and chose a fixed list plus a check on the same day.

## Done when

1. **After the agent removes a feature by hand, the check lists each screen, menu entry, route, access rule, test, import and sample-data line that still points at it, and it fails until none is left.**
2. **When another feature still uses the feature in its code, by an import or by calling its web address, the check names each feature that uses it. A comment or an example text is not a use.**
3. **A removal leaves the feature's table, rows and change history in place and writes no migration. The check passes with the table's data model present, and it still lists the feature's sample-data lines.**
4. **The guide and the worker brief give the fixed list for each starter, the data rule, and the order: check, remove, check again, run the app's tests. A new repo gets the text and the check at start. An existing repo gets them after upgrade and sync, and its app files do not change.**

## Risks

Risks: none one-way. Each part reverts with its pull request. The story builds no way to delete data.

Trade-off: the check reads text. It does not build the app. The agent's own test run is what shows that the app still builds. A test applies the fixed list to Forge's own generated features and runs the check, but no live app run proves the list.

Trade-off: the check has no skip option. A line that mentions the feature's name for another reason is listed, and the agent changes the wording.

Trade-off: a removed feature leaves its table and its data model in the database layer. The app's own database tests need the model while the table exists. A demo database keeps the old sample rows, unseen.

Model cost: none added. The check reads files and makes no model call.

### What exists (evidence)

- The build command is `forge task feature <plural> --one <singular> --field '<name>:<kind>'` in `src/forge/feature.py`; `--one` and `--field` are `required: True` there. It is routed in `src/forge/cli.py` (`ROUTES`, `"task feature": "feature"`). `forge --help` is at its 25-command cap (`tests/test_rules.py::test_5_forge_stays_small`); a subcommand of the `task` group does not count. `sync.command_page` builds `docs/commands.md` from each module's `COMMANDS` `listing`, and `changes_state: True` makes the command run `repo.check_pin` (`cli.py`), which a read-only check does not need.
- `feature.py::build` validates names with `^[a-z][a-z0-9]*(?:-[a-z0-9]+)*$` and refuses with `Feature names need lower-case words separated by hyphens.` The build then uses `libs/<plural>` as a path, so a check that skips the same validation could read outside the app.
- What a TypeScript feature adds (`feature.py::build`, `feature_api.py`, `feature_schema.py`): `libs/<plural>/contracts` and `libs/<plural>/server`; `apps/api/prisma/schema/<plural>.prisma` (its `model <Model> {` line holds the model name, whatever the singular was); `apps/api/prisma/migrations/<UTC timestamp>_<plural>/migration.sql`; `apps/api/test/<plural>.e2e-spec.ts`; and wiring: in `apps/api/src/app.module.ts` the line `import { <Title>Module } from '@app/<plural>-server';` and the entry `    <Title>Module,`; in `apps/api/prisma/schema/base.prisma` the name in `schemas = [...]`; the relation lines in `model Account` (`auth.prisma`) and `model Organisation` (`organisations.prisma`); `@app/<plural>-server` in `apps/api/package.json`; a reference in `apps/api/tsconfig.json`; a `scope:<plural>` line in `eslint.config.mjs`; `libs/<plural>/server/dist` and `libs/<plural>/contracts/dist` in `scripts/test-build.mjs`; an entry in the catalog in `apps/api/test/database.e2e-spec.ts`; importer blocks in `pnpm-lock.yaml`. Apps from earlier releases can also hold `libs/<plural>/web` and its wiring in `apps/web`.
- What a Python feature adds (`feature.py::_build_python`, `feature_python.py`): `apps/api/app/<module>/` (`__init__.py`, `models.py`, `schema.py`, `service.py`, `routes.py`, `permissions.py`, `tools.py`), an Alembic revision, `apps/api/tests/test_<module>.py`, `libs/<plural>/contracts/`; wiring: two lines in `apps/api/app/main.py`, `import app.<module>` in `apps/api/migrations/env.py`, a `<plural> internals` contract in `apps/api/pyproject.toml`, the table in `EXPECTED_TABLE_SCHEMAS` and the two schema filters in `apps/api/tests/test_module_schemas.py`, the `typecheck` path in the root `package.json`, and an importer in `pnpm-lock.yaml`.
- Who uses a feature: a link field makes the other feature's server package list `@app/<target>-contracts` and inject `<TARGET>_API` (TypeScript), or import `app.<module>` (Python). The link column is a plain `uuid` with no foreign key, so only the code can name the user. The boundary rules (`depConstraints` in `eslint.config.mjs`, the `<plural> internals` contract) limit what a module may import, but a module's web code can also call another feature's route by URL, as `src/forge/templates/conventions/frontend.md` shows with `api.post(...)`. That is not an import.
- Why the data layer stays: the app's own tests compare the database to the code. TypeScript `apps/api/test/database.e2e-spec.ts` lists every table with its schema and runs `prisma migrate diff --exit-code`; Python `apps/api/tests/test_module_schemas.py` lists `EXPECTED_TABLE_SCHEMAS` and runs `alembic check`. Removing the model while the migration stays would fail both. Dropping the table in the same change would break a rollback to the previous release (`skills/database/SKILL.md`, "Migrations"). The same two test files also call the starter's own `projects` feature through its API (`/api/v1/projects`), and the starter's Python `projects/models.py` imports `ProjectStatus` from `projects/schema.py`.
- Sample data: `conventions/demo-data.md` puts a prototype's loader in the app, at `apps/api/src/demo/` or `apps/api/app/demo/`. It is the client's code. The starter ships no loader.
- The later table drop is already covered: `skills/database/SKILL.md` "Migrations" (expand, then contract; keep the old table for two releases; a `-- Contract:` or `# Contract:` line) and `conventions/deploy.md` and `skill.md` (Mainline takes a backup at Promote when a release adds a migration file). This story adds no rule for the drop.

### Words this story pins

- **The command.** `forge task feature-check <plural>`, a read-only sibling of the build command under `task`. It is a new entry in `src/forge/feature_remove.py` (new, under 1,200 lines) with `COMMANDS` `words: "task feature-check"`, `args: [(["plural"], {})]`, `run: "check"`, `changes_state: False`, `position: 106` and the listing `` | `forge task feature-check <plural>` | Checks that a removed feature left nothing behind | ``. `cli.py` gets one `ROUTES` line. Why not an option on the build command: `--one` and `--field` are required there, so an option would need new refusal code inside the build path that every feature build runs through. A sibling leaves the build untouched and adds no top-level command. The build command is not changed.
- **Name check first.** The plural must match the build command's name pattern (copy the one pattern; it is a single line) and is refused with the same message before any path is built. `../apps` is refused and nothing is read.
- **Starter check.** A Python starter app has `apps/api/app/main.py`; a TypeScript starter app has `apps/api/src/app.module.ts`. When both exist, Python wins, as in the build command (`feature.py::build` tests `apps/api/app/main.py` first). The earlier-adopted Python fixture (`_adopted_python_starter`) has both, because it lays the Python starter over an earlier TypeScript starter. Neither: refuse `forge task feature-check needs a starter app (one made with forge init --starter), and this app has neither apps/api/app/main.py nor apps/api/src/app.module.ts.` with `Next: search the code for the feature's name, then run the app's own build and tests.` The guide sends the agent to the check only in a starter app, so the guide never loops back to this refusal.
- **The data-model names (TypeScript only).** The check does not take a singular name. It reads every `model <Name> {` block in `apps/api/prisma/schema/*.prisma` that holds `@@schema("<snake plural>")`; the accessor is the model name with a lower-case first letter (`model Person` gives `person`, so `people --one person` works). This rule does not depend on the file name, so a hand-built feature whose model sits in another schema file is found too, and a feature with two models gets two accessors. When no such model is found, the check lists everything else, then prints `Forge could not find the data model for <plural> in apps/api/prisma/schema, so it did not look for database calls by model.` with `Next: search the code for that model's calls by hand and tell the person the check could not confirm them.`, exits non-zero and never prints the all-clear line. Python reads no model name: its imports use the module name.
- **What counts as removed.** None of these exists on disk: `libs/<plural>/`; TypeScript `apps/api/test/<plural>.e2e-spec.ts`; Python `apps/api/app/<module>/routes.py`, `service.py`, `tools.py`, `permissions.py` and `apps/api/tests/test_<module>.py`. Each that exists is listed as `still there`. The kept data layer is the TypeScript `apps/api/prisma/**`; and in Python `apps/api/migrations/**` and the kept module `apps/api/app/<module>/**`.
- **The text scan.** It reads the files `git ls-files -co --exclude-standard` lists, skips `.git`, `docs/`, `plans/`, `.factory/`, `.claude/`, `.codex/`, the kept data layer, files over 1 MB and files that are not UTF-8 text. It skips a comment line: after its leading spaces it starts with `//`, `/*`, `*`, `#`, `{/*` or `<!--`. Test files and the database test files are scanned. Every name below has the same boundary: the character before it and the character after it are not a letter, a digit, an underscore or a hyphen, so `clients` never matches `clients-archive`, `ClientsModule` never matches `ClientsArchiveModule` and `person` never matches `personAddress`. A name with hyphens has three forms: kebab (`work-orders`: packages, folders, routes, permission names), snake (`work_orders`: the Python module, router and SQL schema) and Pascal (`WorkOrders`: classes). The classes, one planted line each in the test:
  - (a) `@app/<plural>-(contracts|server|web)`, `libs/<plural>/` and `scope:<plural>` (the lint rule line and the lock file's importer keys).
  - (b) A route: `/api/v1/<plural>` or a quote or backtick followed by `/<plural>`, with the boundary after the name (so `/api/v1/clients-archive` is not a route of `clients`).
  - (c) The permission names `<plural>.(view|create|edit|delete|restore)`.
  - (d) A Python import of the module: after any leading spaces, `import app.<module>` or `from app.<module>` (an indented import inside a function counts), and the name `<module>_router`.
  - (e) `<Title>Module`, `<Title>Tools`, `<Title>Api` and `<PLURAL>_API`.
  - (f) The TypeScript Prisma accessor `prisma.<model>` or `tx.<model>` for each model name read above.
  - (g) An SQL insert into the feature's schema: `INSERT INTO`, then optional double quotes, then the snake plural and a dot, matched case-insensitively across line breaks (`INSERT INTO clients.client`, `INSERT INTO "clients"."Client"`), in a SQL file or in code. A demo loader written as SQL is found this way.
  - Inside the kept Python module the only lines scanned are imports of a removed file of that module: `app.<module>.(routes|service|tools|permissions)` or the relative form `from .(routes|service|tools|permissions)` or `from . import` of those names. So the starter's `__init__.py`, which imports `routes`, `service` and `tools`, is listed until the agent cuts it, while `models.py` and the files it imports are left alone.
  - There is no class for the bare feature name in prose.
- **Users and leftovers.** A use is a match of class (a), (b), (d), (e), (f) or (g) on a non-comment line in the code of another module. Another module is any folder under `libs/` or `apps/api/app/` except the feature's own folders, `core`, `shared` and `demo`. Permission names (c) are never a use, and neither is a comment or any file outside module folders (`apps/web`, `apps/api/src`, `apps/api/test`, `apps/api/tests`, the demo loader, `libs/shared`, which holds the Python app's generated API types). That excludes the starter's own examples: the sample permission list in the auth module's response example is class (c), and the page path example in `libs/shared/util` is outside module folders; both are leftovers when the agent removes the starter's `projects`, never users. A use: print `The feature <plural> is used by <other>, ... (<path>:<line> ...)` and fail. Every other match is a leftover: print `path:line  text` for each. The check changes no file and uses the same scan for both, so a use by URL is found the same way as a use by import. Exit 0 and print `Nothing points at <plural> any more.` only when no file is `still there`, no use and no leftover is found, and the data-model step above did not fail.
- **The calls inside the database tests.** The two database test files are not skipped. After the agent removes the starter's own `projects` feature, the lines that call `/api/v1/projects` in them are listed like any other test line. The agent changes those tests to create a row another way or to drop that step, while the table list entry stays. The guide says so.

- **Planner choices.** (1) A sibling of the build command under `task`, not an option on it, because an option would change the build path (see Words). (2) The check reads text, with no parser; the module boundary rules decide who may import whom, and URLs are found by the same text scan. (3) The check takes only the plural; the model names are read from the schema files by their `@@schema` line. (4) No skip option for a match. (5) The agent runs the check first as well as last, so one command answers both "who uses it" and "what is left". (6) A use is code in another feature module, not a comment, not a permission name, and not a file outside the module folders; this keeps the starter's own examples out of the users list. (7) Every name pattern has one boundary rule (no letter, digit, underscore or hyphen on either side), so features whose names start alike stay apart. (8) When both starter markers exist, Python wins, as in the build command. (9) A missing data model ends in a refusal, not an all-clear.
- **F x H >= 2 x C.** F 3 (a prototype team removes features daily across many users), H 2 (a leftover route or access rule, or deleted shared code, is a broken step), C 2 (about 150 lines, no model call): 6 against 4. The guide is text only.
- **What a new and an existing client repo get.** New repos (`forge init`, either starter, or plain): the guide and brief text, and the check, which Forge itself provides; plain init gets the check's refusal. Existing repos on upgrade and sync: the same texts and the check, with no app file changed. An existing starter app, including one made from an earlier starter, can use the check at once. An app made before the build step existed has no starter folders: the check refuses and the guide gives the search-and-test path.
- **Lane for a removal in a client repo.** Removing an API is an interface change and touches many files, so after sign-off Forge probably picks a story; before sign-off a prototype fix may be larger. `forge start` decides, not the guide.
