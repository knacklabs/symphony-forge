# One shared design system and theme, set in Claude and checked at close

2 parts · Risks: none one-way · New moving parts: none

## What changes for you

- Forge keeps one set of shared screen parts (buttons, tables, forms) and one list of theme names, such as the page colour, the main colour, the corner size and the heading font. A theme is the set of colours, fonts, sizes and shadows that gives an app its look. Both live once, in Forge's code. Each name is the same in Forge's code and in Claude. (Source: your decision, 10 Nov 2026)
- For each client, the agent builds that client's own design system in Claude from those parts and names. A design system is the shared parts together with the theme they use. The agent decides the client's theme itself: colours for light and dark, fonts, sizes, spacing, corner size and shadows. It takes five facts from the client's notes: the industry, the users, the main job of the screens, the brand's words and the brand's files. It asks the Sales person only for a fact that is missing. Then it shows the finished look on the shared parts. The Sales person says yes, or says in plain words what to change, for example "warmer" or "more serious", and the agent changes it. The Sales person sets no value by hand. The design system also holds a short brand guide, written by the agent from Forge's design rules and the client's facts. It says which colour and font is for what, how dense the screens are, and which looks to avoid. Every screen design starts from that guide, so nobody has to give design instructions. The repo keeps the link to that system, so the agent always opens the right client's system. The screens are designed with it, so a client sees the Forge look before any app exists. (Source: your words, 10 Nov 2026: "The UI need to start with Claude artifact, design system and theming in it which can next transferred to prototype"; your words, 11 Nov 2026: "I want agent to decide based on few questions and take the best call possible")
- When the design is approved, the agent copies the theme into the prototype before it builds the first screen. It also keeps the approved theme as a file in the repo. A font is copied into the app so that it really loads; a font the app cannot load is reported to the person and is not copied silently. The prototype then looks like the approved design. (Source: your decision, 10 Nov 2026)
- The final check before a change is finished reports any theme value in the app that differs from the approved copy; it looks every time a screen or the theme changes, and it stops the change until the agent fixes it. One short comment with a reason sets one value aside, and the comment names that value and the theme (light or dark). The check makes no model call and starts no browser. A screen built on the plain gray starter theme, with no approved copy, is reported by the reviewer as a finding instead; the final check does not stop it. (Source: your request, 10 Nov 2026; your decision, 10 Nov 2026: "Make it a review rule")
- The step that picks the look in code stays in two places only. The agent still uses its five facts about the client to propose the first colours and fonts for the design system. A session with no Claude design tools uses the step to write the theme in code, as today. (Source: the planner's choice, for you to confirm)
- The agent says so in one line when Claude's design tools are not available in a session. It then carries on with plain page drawings and a theme written in code, and builds the Claude design system when the tools return. In the same change it saves the approved theme in the repo, so the check has a copy from then on. (Source: your request, 10 Nov 2026)
- Animation speed, button press feedback and the loading, empty and error parts belong to another story. This story does not touch them. (Source: your decision, 10 Nov 2026)
- A new client repo gets all of this when it starts. An existing client repo keeps its theme file and every app file. After it upgrades and refreshes its Forge files, it gets the guide text and the check. The check can first stop a change when that repo's next screen change is finished. ## Why

The look of a prototype is picked in code, at a later step, from a short brief. A prototype can drift from the design the client approved, and nothing reports the difference. Sales are not designers, so nobody can ask them to choose each colour and font, and an app that keeps the plain gray starter theme looks like every other machine-made app.

## Done when

1. **The theme names are fixed once, in the starter's theme file, and the Claude design system uses the same names.**
2. **The guide tells the agent to build each client's design system in Claude from the app's parts and names, to find it again from a link kept in the repo, to design the screens with it, and to copy the approved theme, with a font the app can load, into the app and the repo before the first screen.**
3. **The final check reports each theme value that differs between the app and the approved copy, whenever a screen or the theme changes.**
4. **The reviewer reports a screen built on the untouched starter theme when no approved copy exists.**

## Risks

Risks: none one-way. Each part reverts with its pull request. Nothing is deleted and no data changes.

Trade-off: Forge cannot see Claude. The check compares the app with the approved copy in the repo. If the theme changes in Claude after the approval and nobody copies it, the check stays green. The guide tells the agent to copy again after every theme change in Claude.

Trade-off: the reviewer, not the final check, catches a gray screen. A review can miss it, and nothing stops the change in code. You chose this on 10 Nov 2026.

Trade-off: a font that the app cannot load is not copied. The check then reports a difference for that font until the agent sets it aside with a comment that names it. The person is told in one line which font did not load.

Trade-off: building the design system needs Claude's design tools. Without them in a session, the agent works as it does today and builds the system later. The look then comes from code for a while. The check does not stop that path, because a theme written in code is no longer the stock one.

### The theme contract

The Claude design system's `tokens.json` and the app use the same names, and the copy is mechanical: token `N` is the variable `--N`.

| Claude `tokens.json` | The app's theme file |
|---|---|
| `color` tokens, `value.light` and `value.dark` | `--N` in `:root` and in `.dark` (the 31 names above) |
| `radius` token `radius` | `--radius` in `:root` |
| font tokens `font-sans`, `font-heading` | `--font-sans` (`@theme inline`, kept) and `--font-heading` (new, `@theme`) |
| size tokens `text-xs`, `text-sm`, `text-base`, `text-xl`, `text-2xl`, `text-3xl` | the same names, new, in `@theme` (12, 14, 16, 20, 24 and 30 pixels, the fixed baseline scale as defaults) |
| spacing token `spacing` | `--spacing` (new, `@theme`, `0.25rem`) |
| shadow tokens `shadow-xs`, `shadow-sm`, `shadow-md`, `shadow-lg` | the same names, new, in `@theme` (Tailwind's own defaults) |

- Kept as they are: the 31 colour names, `radius` and `font-sans`. Added, because the owner's list needs them and the file has none: `font-heading`, six `text-*`, `spacing`, four `shadow-*`. That is 12 lines in one new `@theme` block plus one base-layer rule that gives `h1` to `h6` the heading font. Every added default equals what Tailwind already uses, so a new app renders as before.
- Every contract value is literal. The app keeps `var()` and `calc()` only in the mapping and derived lines (`--color-*`, `--radius-sm` and the rest), which are not contract names. The added `--font-heading` repeats the `--font-sans` list as text and does not point at it.
