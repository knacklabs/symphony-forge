# Codex build rounds run on a machine you own

2 parts · Risks: a Codex worker on your machine can read and change what the developer's user there can; turning it off deletes Forge's folder there · New moving parts: your own Linux machine, reached with ssh; one small shared setting and record for work on other machines

## What changes for you

In this plan, "your machine" is a Linux computer that your team owns and that a developer can reach with `ssh` from the laptop.

- A Codex build round can run on your machine instead of on the laptop. The laptop sends the code to your machine over ssh, Codex works there, and the commits come back to the laptop. The laptop then pushes to GitHub, as today. (Source: your decisions of 17 Nov 2026)
- Your machine goes first, because it costs nothing more. A round starts there while its load is under 1.5 per core and it has a free place (half its processors), the same rule that the laptop uses. Otherwise the round runs on the laptop. (Source: your decisions of 17 Nov 2026)
- Only Codex build rounds go to your machine. Claude rounds, reviews, cold reads and the tests that close runs stay on the laptop. Claude has one way to run on your own machine with no person at the screen, and it needs a Team or Enterprise plan, a switch by the plan's owner, and a feature that is still in beta. Codex rounds that a Codex session runs as its own helpers also stay on the laptop. (Source: your decision of 17 Nov 2026)
- The worker's own test runs move with its round: they run on your machine, with its processors. (Source: your decision of 17 Nov 2026)
- It is off in every repo. The agent turns it on only after you agree, in a small settings change: `boxes = "ssh"` in `forge.toml`. This is the same setting that the cloud machine story uses; a repo uses one of the two. Each developer then names their own machine once, in the setup step (`forge lanes --box setup --host <the name they give ssh>`); Forge keeps the name in its own record for that copy of the repo, which git does not share. A new client repo has it off at setup. An existing client repo also has it off after it upgrades and syncs; its settings and its work do not change. Both get the new steps in Forge's guide. (Source: your decisions of 17 Nov 2026; the name goes with the setup step by your answer of 17 Nov 2026)
- One machine per developer in this first version. (Source: your decision of 17 Nov 2026)
- Setup happens once for each copy of the repo on the laptop, with one Forge step that the agent runs. It checks that ssh reaches the machine without a password, and that the machine has git, Forge at this repo's version and a Codex sign-in. It installs the Codex kit that Forge drives (about 300 MB) when it is missing, and it makes Forge's own folder there, with the laptop's git name and email, so the worker's commits carry the developer's name. - The developer signs in to Codex on the machine once, with their own account (`codex login --device-auth`). Forge never copies or reads a sign-in. On a shared machine, each developer uses their own user. (Source: your decision of 17 Nov 2026)

- Your machine needs no GitHub sign-in. Code goes to it straight over ssh, and commits come back the same way. (Source: your decisions of 17 Nov 2026)
- Each round starts in a new folder on your machine. Forge never deletes a round's folder by itself: the folders stay on the machine until turn-off, so its disk use grows with each round, and turn-off clears it. (Source: your decision of 17 Nov 2026; keeping the folders until turn-off is your answer after the third cold read)
- Only committed files reach your machine. A repo whose tests need an ignored settings file (such as `.env.test`), or a service that the machine does not have, keeps this off for now. (Source: the planner's choice; confirm)
- The machine view and the Forge pane show the round as an ordinary row with the words "on <machine name>". It takes none of the laptop's places. `forge stop` ends it, as it ends a laptop round. (Source: your decisions of 17 Nov 2026)

Design: none (no screen: setup and turn-off print lines in the agent's terminal, and the machine view and the pane gain the words "on <machine name>").

## Why

Every Codex build round runs on the laptop. A new round waits while the laptop's load is at 1.5 per core or more, or while all its places are taken, and the team's own Linux machines sit idle. A client team waits for this. Today's workaround: the agent starts fewer rounds at once, and the rest wait. In Forge's own repo, build rounds took about 8% of item time (measured over 86 items, 11 to 14 Oct 2026); how long the client team's rounds wait is not measured.

## Done when

1. **A developer names and sets up their own Linux machine for a copy of the repo once: Forge checks it, installs what it can, and says in one line what is missing and what to do next.**
2. **With the setting on, a Codex build round starts on that machine while it has room, its log shows on the laptop as it runs, and its commits come back to the laptop's branch.**
3. **The machine view and the pane show such a round as an ordinary row marked with the machine's name, it takes none of the laptop's places, and stop ends it.**
4. **When the machine is busy, not set up or cannot be reached, the round runs on the laptop and Forge says why in one line, and commits that a cut-off round left on the machine come back before the item's next round.**
5. **Rounds on a machine you own are off in every repo until a settings change turns them on, and turning them off lists what Forge's folder on the machine still holds and deletes it only after the developer agrees.**

## Risks

These steps are sensitive or cannot be undone:

- Forge runs Codex with full access on your machine, as it does on the laptop. A worker there can read and change anything that the developer's user can: other repos, keys and files. Use a user that holds only what the work needs.
- Turning it off deletes Forge's folder on the machine, with every round's folder in it, once the developer agrees to the list it shows. What the list names (changes not committed, ignored files, stashes, commits not yet back) is then gone.
- Codex's trust entry for Forge's folder stays in Codex's settings on the machine after turn-off; the developer removes it there if they want.

Accepted limits, in plain words:
- Codex build rounds only. Claude rounds stay on the laptop until Claude's own way is out of beta and on the team's plan.
- A sleeping laptop or a broken connection stops the laptop following the round; its work waits on the machine until the item's next round, which waits while the old round still runs.
- One machine per developer.
- Turn-off checks the machine and then deletes Forge's folder. A round of the same copy of the repo that starts in the seconds between the two is not guarded against; the developer runs both, so this is rare.
- Run folders stay on your machine until turn-off, so its disk use grows with each round.
- Known issue: a commit that someone makes by hand in a kept round folder on your machine, after its round ended, is not seen by close, which can merge without it.
- Known issue: a teammate who closes the same task from another copy of the repo does not see commits that are still on your machine; close there can merge without them.
- A Codex turn that hangs on your machine keeps that item's next rounds and turn-off waiting; the refusal says how to stop it there by hand.
- Close runs its tests on the laptop. A pass that the worker's tests recorded on your machine does not count there, because each machine keeps its own record of passed tests.
- A conversation that ran on your machine is not linked to the pull request in the Codex app on the laptop.

### Shared names

HOST commits these with its tests; ROUND uses them and changes none of them. They match the names that the cloud machine story (FORGE-PROVIDER-1) pinned, so that story adds to them.

- **Setting.** `forge.toml` key `boxes`, a string, `"off"` or `"ssh"`, default `"off"`: added inside the existing `KEYS`, `DEFAULTS` and `CHOICES` lines. This is the only `repo.py` change. The machine's name is not a setting: `forge lanes --box setup --host NAME` takes it and the record keeps it (below). `box_ssh` checks the value: it must match `[A-Za-z0-9_.@:%\[\]-]+` and must not start with `-` (an ssh option), else `--host "{host}" is not a name ssh takes; use the name from your ssh settings.` / `Next: forge lanes --box setup --host <name>`.
- **`src/forge/box.py`** (new): `class ProviderError(Exception)` with `code: str` and `message: str`; `PROVIDERS = {"ssh": box_ssh}`; `provider(name: str) -> ModuleType`; `record(top: Path) -> dict | None` and `save(top: Path, record: dict | None) -> None` (None removes it), at `repo.forge_dir(top) / "box.json"`, shared by every worktree of one clone and never committed; `command(top: Path, args) -> int`, the `--box` dispatch: setup with `boxes = "off"` refuses `This repo's forge.toml has boxes = "off", so Forge runs no work on another machine.` / `Next: ask the owner, then turn it on in a settings fix: boxes = "ssh" for a machine you own`; setup otherwise calls `provider(cfg["boxes"]).setup(top, args)`; off with no record prints `This clone has nothing set up on another machine, so there is nothing to delete.` and returns 0, else calls `provider(record["provider"]).off(top, record, args.yes)`, whatever `boxes` says. `box_ssh` reads box names at call time, so the two modules can import each other.
- **The record of an ssh machine.** `{"provider": "ssh", "host": "<alias>", "clone": "<absolute path of Forge's clone on the machine>"}`. The record is the one home of the machine's name: rounds, the bring-back and turn-off all read `host` from it. No record means this clone has no machine.
- **The item's machine.** `start` writes `host` into the item's record (`codex._record`); the bring-back clears it once the machine holds nothing of the item. The item's record is the one place that says the item has work on a machine.
- **Places on the machine.** `FOLDER = "forge-host"` under the machine's home. Each clone of the repo gets `forge-host/<main checkout's folder name>-<first 6 hex digits of the SHA-256 of the main checkout's absolute path>/`, so every setup of one clone names the same folder, with `clone/` (a `git init` repo with no checked-out files) and `runs/`. A run's folder is `runs/<item>/<lane entry id>/` (the item's `/` stays a folder level, so `BOARD/UI` and `BOARD/UI-FORM` never share a folder), with its driver file `<lane entry id>.py` and its process file `<lane entry id>.pid` beside it in `runs/<item>/`, outside the worktree, so git never sees them. Forge finds an item's runs only by listing that exact folder, never by matching names or command lines.
- **Is a round still running.** A round has ended only when its done file exists: `runs/<item>/<entry>.done`, beside the driver file `<entry>.py` and the folder `<entry>/` (the constant `box_ssh.DONE = ".done"`). The round's remote command runs the driver and then writes it: `<driver>; echo done > <run>.done` (no `exec`). A round entry with no done file reads as running; Forge runs no `ps`, `kill` or `/proc` check. Turn-off refuses and names the entry and its `touch <entry>.done` command, to run by hand after the developer has checked that nothing of the round runs. Forge itself stops nothing there.
- **ssh.** `SSH = ["ssh", "-o", "BatchMode=yes", "-o", "ConnectTimeout=10", "-o", "ServerAliveInterval=30", "-o", "ServerAliveCountMax=4"]`; git's own ssh calls get the same options through `git -c core.sshCommand=...`. Every remote command starts with `PATH="$HOME/.local/bin:$PATH";` (uv puts Forge there, and a non-login shell may lack it). `box_ssh.ssh(host, script, *, input=None) -> CompletedProcess`: exit 255 raises `ProviderError("ssh", <last line of stderr>)`. The machine's Codex kit python is the shell text `"${XDG_DATA_HOME:-$HOME/.local/share}/forge/codex-sdk/openai-codex-<codex.SDK_PIN>/bin/python"`. The machine's git URL is `<host>:<clone path>`.
- **Lane rows (ROUND adds these; it is their first user).** `machine.join(..., read_round=None, box: dict | None = None)` and `agent_slot(..., box=None)`: with `box`, the entry gets those fields and `admitted: True`, and `join` returns it without `_wait`. Rows with a `box` field are left out of the laptop's counts: the lane filter in `_wait`, `test_allocation` and `counted` in `lanes`. `machine.back_to_laptop(entry) -> dict`: in the queue row and in the entry, remove `box`, `host` and `box_copy`, set `admitted` False and `started_at` None (and `processes` 0 for a test entry), then return `_wait(entry)`.

### The test machine

`tests/ssh_host.py`, a helper module (not a test file), shared by both parts. `machine(repo, name="devbox", **facts)` puts a program named `ssh` first on the test `PATH` and makes `tmp_path/hosts/<name>/home`. The `ssh` program skips options, takes the host, runs the remaining words with `sh -c` in that home, in a new session (`start_new_session=True`), and returns its exit code. Like the real `ssh`, it relays rather than hands over its pipes: the child gets pipes of the stand-in's own, and two threads copy stdin to the child and the child's stdout and stderr back. So when the stand-in ends (`forge stop` ends it), the child's stdin closes and the laptop's read of stdout ends, as with a closed connection; the stop test cannot hang on a child that holds the laptop's pipe. It removes `GIT_CONFIG_GLOBAL`, `GIT_CONFIG_NOSYSTEM` and every `GIT_AUTHOR_*` and `GIT_COMMITTER_*` value, so the test machine has no git name unless setup gives the clone one. It also removes every `FORGE_*` and `PYTEST_*` value, as ssh forwards no environment, so the remote driver has `FORGE_WORKER` only when the round's command exports it; test_2 checks it (`STUB_CODEX_RUN` also writes `$FORGE_WORKER` to a file that comes back in the commit, and it must read `1`). An unknown host, or a `down` file in the host folder, exits 255 with `ssh: Could not resolve hostname <name>`; a `fail-<word>` file makes the next call whose command holds that word (`git-upload-pack`, `git-receive-pack`) exit 255 once. It sets `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME` and `CODEX_HOME` under that home (so the machine has its own lanes, passed-test records, Codex kit and Codex settings), puts `<home>/.local/bin` first on `PATH`, keeps `CODEX_BIN` and the rest, and logs each call to `ssh-calls.jsonl`. git's own ssh calls (push, fetch) go through the same program.
