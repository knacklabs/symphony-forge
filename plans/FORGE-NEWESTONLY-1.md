# Forge supports only its newest release

8 parts · Risks: none one-way in data; repos on an older release stop until they upgrade · New moving parts: none

## What changes for you

- Forge compares two releases: the release that a repo pins in forge.toml (the "pin") and the Forge release that is installed on the laptop. When they are the same, Forge works as today. When they differ, Forge commands stop with one line. That line names the pin and one next step that works: upgrade, pull or merge the default branch, or install the release that the repo pins (when the repo pins a newer release). The pin stays in forge.toml as a record. Forge no longer runs a repo's pinned release through uv (uv is the tool that installs Forge). (Source: your decision, 15 Nov 2026: "Refuse and say upgrade")
- Some commands keep working, because the upgrade or the laptop needs them. Upgrade itself. The close and merge of an upgrade fix that waits for its merge, so the upgrade can finish. Two laptop-wide commands: the one that lists the runs on this laptop (the /forge pane reads it every 3 seconds) and the one that stops a run. The hooks that git, Claude Code and Codex start by themselves, so a commit or an agent session does not lock up. forge doctor stops too, and it no longer installs a newer pinned release itself: the stop line gives the same install command. (Source: the planner's choice, to make your decision "every command except upgrade stops" work; confirm)
- Forge upgrades a repo only from the release just before the newest one. For a repo on any older release, the upgrade stops with one line: upgrade through each release in order, starting with the release that the line names. Forge keeps upgrade code for one release at a time, and each release deletes the upgrade code that it no longer needs. (Source: your decision, 15 Nov 2026: "One step back only")
- "Newest" means the release that is installed on the laptop. The release just before is the same number with the last part one lower (v1.2.41 comes after v1.2.40), because Forge numbers its releases one by one. Only a release that starts a new line, such as v1.3.0, names its release before by hand, and the release test fails when it does not. Forge makes no network call for this check. (Source: the planner's choice; confirm)
- What each repo gets. A new repo (made with forge init, also for an existing app): nothing changes, because it starts on the newest release. An existing repo on v1.2.40: it upgrades in one step, as today; after that, it must take each later release in order. An existing repo on a release older than v1.2.40: with the new release installed, every command stops. To recover, install v1.2.40, upgrade the repo to v1.2.40, then upgrade to the newest release. (Source: Forge's rule for new and existing repos)
- What a team sees during an upgrade, in order. (Source: the planner's choice, from your decision of 15 Nov 2026 that every command except upgrade stops; confirm)
  1. forge next says that a newer release is out. The agent asks you, then starts the upgrade. The upgrade installs the new release and opens one fix that changes the pin.
  2. Until that fix merges, other Forge work in the repo stops with one line: the upgrade waits for its merge, so close the upgrade fix first. Today other work continues on the old release meanwhile.
  3. The upgrade fix merges: you merge it, or the agent does where the repo lets the agent merge.
  4. If the laptop's copy of the default branch is behind, Forge says to pull it.
  5. Each open story part or fix takes the new release when the agent next runs its worker. The worker merges the default branch first, as today, and a merge conflict goes to the worker. A command run inside the folder of an older branch says to merge the default branch there first.
  6. A teammate with the old release installed sees one line that says to install the new release.
- forge migrate (for a repo with a copied-in old Forge) stays for one more release. Each time it runs, it says in one line, at the end of its messages, that the next release removes it. The removal is a later, separate change. (Source: your decision, 15 Nov 2026: "Keep it one more release")
- Forge's own tests check each rule on a new repo only. One test checks the upgrade from the release before to the newest one, and one test checks the refusal on an older pin. Measured today: about 960 of 4,674 test cases (in about 470 of 828 test files) run a rule a second time on a repo adopted on release v1.2.2. These cases go, and so do five folders of old-release test data (about 10,200 lines, of which 8,374 lines are a copy of Forge v1.2.2's code). The test rule in Forge's own instructions for reviewers and builders is rewritten to say this. (Source: your decision, 15 Nov 2026: "New repo only, plus one upgrade test")
- Code that only older releases need goes. Measured: about 275 lines of Forge's code, in these areas: running a pinned release through uv (also in the hooks, which today fall back to uv when Forge is not installed), doctor's install of a pinned release, moving worker chats that releases before v1.2.10 kept on the laptop, converting the shared run list and process records of releases before v1.2.8, hook lines of releases before v1.2.9, and the pane's line about an older Forge. forge migrate (673 lines) goes in the later change. (Source: your decision, 15 Nov 2026: "Support only the newest release")
- Test time. Today the full test run takes about 90 minutes on this laptop, and each of the six CI test groups takes 12 to 20 minutes (your measurement). In Forge's recorded test times, the cases that go take 56 of 242 minutes (23%), and tests about older releases take about 3 minutes more. Estimate after the cut: about 70 minutes on this laptop, and about 10 to 16 minutes per CI group. These are estimates, not measurements. (Source: the planner's measurement of the recorded test times, 15 Nov 2026)
- The release with the cut goes out only after the client repo in daily use is on v1.2.40, because v1.2.40 is the last release that upgrades from any older release. Until then, Forge publishes no new release once a part of this change has merged. (Source: your decision, 15 Nov 2026: "After the client is on v1.2.40")
- Cost. The cut adds no model call, so the model cost does not change. CI minutes go down with the test time. (Source: the planner's estimate)

Design: none. The change is lines that Forge prints in the terminal and text in the guides; there is no screen. The changed flow is the step list above, and the builders' part holds every line that Forge prints, state by state.

## Why

Today Forge works for repos on any older release. When a repo pins an older release, Forge runs that release through uv. Forge also reads record formats from releases back to v1.0. To keep this safe, most rules are tested twice: on a new repo, and on a repo adopted on v1.2.2. These second runs are about 960 of 4,674 test cases and about 23% of the recorded test time, and each release adds more. Every change must also keep the old paths working, so each change costs more to build and to review.

Only one client repo is in daily use, and it moves to each new release. So the old paths serve almost nobody. Today there is no workaround: every pull request pays the extra test time, and every builder carries the old code.

## Done when

1. **In a repo whose pin differs from the installed Forge, every Forge command stops with one line that names the pin and one next step that works, except upgrade, the close and merge of a waiting upgrade fix, the two laptop-wide run commands and the hooks that git and the agent apps start, and Forge never runs a repo's pinned release through uv.**
2. **Upgrading to the installed release moves a repo from the release just before it in one fix, and for a repo on any older release the upgrade stops with one line that says to upgrade through each release in order and names the release to install first.**
3. **forge migrate still works and says on every run, in one line, that the next release removes it.**
4. **Forge's own tests check each rule on a new repo only, plus one test of the upgrade from the release before and one test of the refusal on an older pin, no earlier-adopted test case or old-release test folder remains, and the test rule in Forge's own instructions says this.**
5. **Forge's code holds no path that runs a pinned release through uv, moves chats of earlier releases, reads run or process records of releases before the release just before, or tells the person in the pane that Forge is older.**
6. **The release that holds the cut goes out only after the client repo in daily use is on v1.2.40.**

## Risks

Risks: none one-way in data. No record format changes: the cut deletes readers and adds no new writer, so a repo that reverts its upgrade can still use v1.2.40. Each part reverts with its pull request. In Forge's own repo, a revert brings back the deleted tests and code.

What a repo can lose, in plain words:
- A repo on a release older than v1.2.40 stops working with the new release installed, until it upgrades. The recovery: install v1.2.40, run the upgrade to v1.2.40 (v1.2.40 upgrades from any older release), then upgrade to the newest. The stop line names the first step.
- A laptop with two repos on two releases: the repo on the older release stops until it upgrades. Today Forge runs the older release for it through uv.
- A team in the middle of a story when it upgrades: from the start of the upgrade until its fix merges, other Forge work in that repo stops. Where a person merges by hand, this wait can be long.
- A laptop where Forge is not installed: today the agent hooks fall back to running Forge through uv; after the cut they stop with the line that says how to install Forge.
- A repo cannot go back to the old release per branch. To leave the new release, revert the upgrade's pull request and install v1.2.40 again.
- Gap: the v1.2.40 upgrade command is already published and does not know the new one-step rule. A repo on a release older than v1.2.40 can use it to jump straight to the release with the cut. That repo then misses the old chat moves, and its old worker chats on that laptop start again. In practice only the client repo in daily use upgrades, and it will be on v1.2.40 first. A guard would need a check in sync (about 15 lines); this plan adds none.
- Fewer tests: a rule that behaves differently on a repo that came from an older release is no longer tested there. After the cut, no such repo can run the new release.
- Releases wait: from the first merged part until the client repo is on v1.2.40, Forge publishes no release.

### Decisions

- **The release before.** One function, `repo.previous_release()`: the same first two numbers as `__version__` and the last number one lower (`1.2.40` gives `1.2.39`). Only a release whose last number is 0 sets `__previous__` in `src/forge/__init__.py` by hand, and the function returns it then. `tests/test_release_version.py` gets one check that needs no network and no tags: when the last number of `forge --version` is 0, the release test reads `__previous__` from `src/forge/__init__.py` and it must be set and lower; otherwise `__previous__` must be absent, so a value left from an earlier minor release also fails. So a normal release fix has nothing to remember, and the one manual case fails when it is forgotten. `docs/guide.md` "Releasing Forge" step 1 says this in one sentence. Assumption: Forge numbers its patch releases one by one, as tags `v1.2.0` to `v1.2.40` do.
- **The states (Done-when 1).** `cli._run` runs the check before anything else in the command, also before `install_mod` for `forge sync`, for every command except `upgrade`, `lanes`, `stop` and `hook ...`. `init` and `migrate` need no exception: their repos have no `forge.toml` yet, and the check returns there. `repo.check_pin` takes these states in this order and stops at the first that holds. `{pinned}` is the pin of the checkout the command runs in, `{installed}` the installed release, `{previous}` `previous_release()`, `{default}` the default branch, `{fix}` `upgrade.PREFIX` plus the installed release with dashes; versions print with their `v`.
