# Forge supports only its newest release

7 parts · Risks: none one-way in data; repos on an older release stop until they upgrade · New moving parts: none

## What changes for you

- Forge compares two releases: the release that a repo pins in forge.toml (the "pin") and the Forge release that is installed on the laptop. When they are the same, Forge works as today. When the repo pins an older release, every Forge command except upgrade stops with one line. That line names the pin and the next step. The pin stays in forge.toml as a record. Forge no longer runs a repo's older pinned release through uv (uv is the tool that installs Forge). (Source: your decision, 15 Nov 2026: "Refuse and say upgrade")
- Forge upgrades a repo only from the release just before the newest one. For a repo on any older release, the upgrade stops with one line: upgrade through each release in order, starting with the release that the line names. Forge keeps upgrade code for one release at a time, and each release deletes the upgrade code that it no longer needs. (Source: your decision, 15 Nov 2026: "One step back only")
- "Newest" means the release that is installed on the laptop. Forge knows "the release just before" from one value in its own code. The step that makes a new release moves this value, and the release test fails when it is not moved. Forge makes no network call for this check. (Source: the planner's choice; confirm)
- What each repo gets. A new repo (made with forge init, also for an existing app): nothing changes, because it starts on the newest release. An existing repo on v1.2.40: it upgrades in one step, as today; after that, it must take each later release in order. An existing repo on a release older than v1.2.40: with the new release installed, every command stops. To recover, install v1.2.40, upgrade the repo to v1.2.40, then upgrade to the newest release. (Source: Forge's rule for new and existing repos)
- Work in progress during an upgrade. While the upgrade waits for its merge, a command on another branch stops and says to merge the upgrade first. After the upgrade merges, each open branch takes the new release from the default branch the next time its worker runs. Today such work continues on the old release. (Source: the planner's choice, from your decision of 15 Nov 2026 that every command except upgrade stops; confirm)
- forge migrate (for a repo with a copied-in old Forge) stays for one more release. Each time it runs, it says in one line that the next release removes it. The removal is a later, separate change. (Source: your decision, 15 Nov 2026: "Keep it one more release")
- Forge's own tests check each rule on a new repo only. One test checks the upgrade from the release before to the newest one, and one test checks the refusal on an older pin. Measured today: 930 of 4,674 test cases (in 469 of 828 test files) run a rule a second time on a repo adopted on release v1.2.2. These cases go, and so do five folders of old-release test data (about 10,200 lines, of which 8,374 lines are a copy of Forge v1.2.2's code). The test rule in Forge's own instructions for reviewers and builders is rewritten to say this. (Source: your decision, 15 Nov 2026: "New repo only, plus one upgrade test")
- Code that only older releases need goes. Measured: about 260 lines of Forge's code, in these areas: running an older pinned release through uv, moving worker chats that releases before v1.2.10 kept on the laptop, converting the shared run list and process records of releases before v1.2.8, hook lines of releases before v1.2.9, and the pane's line about an older Forge. forge migrate (673 lines) goes in the later change. (Source: your decision, 15 Nov 2026: "Support only the newest release")
- Test time. Today the full test run takes about 90 minutes on this laptop, and each of the six CI test groups takes 12 to 20 minutes (your measurement). In Forge's recorded test times, the cases that go take 54 of 242 minutes (22%), and tests about older releases take about 3 minutes more. Estimate after the cut: about 70 minutes on this laptop, and about 10 to 16 minutes per CI group. These are estimates, not measurements. (Source: the planner's measurement of the recorded test times, 15 Nov 2026)
- The release with the cut goes out only after the client repo in daily use is on v1.2.40, because v1.2.40 is the last release that upgrades from any older release. Until then, Forge publishes no new release once a part of this change has merged. (Source: your decision, 15 Nov 2026: "After the client is on v1.2.40")
- Cost. The cut adds no model call, so the model cost does not change. CI minutes go down with the test time. (Source: the planner's estimate)

Design: none (the change is lines that Forge prints in the terminal and text in the guides; there is no screen)

## Why

Today Forge works for repos on any older release. When a repo pins an older release, Forge runs that release through uv. Forge also reads record formats from releases back to v1.0. To keep this safe, most rules are tested twice: on a new repo, and on a repo adopted on v1.2.2. These second runs are 930 of 4,674 test cases and about 22% of the recorded test time, and each release adds more. Every change must also keep the old paths working, so each change costs more to build and to review.

Only one client repo is in daily use, and it moves to each new release. So the old paths serve almost nobody. Today there is no workaround: every pull request pays the extra test time, and every builder carries the old code.

## Done when

1. **In a repo that pins an older release than the installed Forge, every Forge command except upgrade stops with one line that names the pin and the next step, and Forge never runs an older release through uv.**
2. **forge upgrade moves a repo from the release just before the installed Forge to the installed Forge in one fix, and for a repo on any older release it stops with one line that says to upgrade through each release in order and names the release to install first.**
3. **forge migrate still works and says on every run, in one line, that the next release removes it.**
4. **Forge's own tests check each rule on a new repo only, plus one test of the upgrade from the release before and one test of the refusal on an older pin, no earlier-adopted test case or old-release test folder remains, and the test rule in Forge's own instructions says this.**
5. **Forge's code holds no path that runs an older release, moves chats of earlier releases, reads run or process records of releases before the release just before, or tells the person in the pane that Forge is older.**
6. **The release that holds the cut goes out only after the client repo in daily use is on v1.2.40.**

## Risks

Risks: none one-way in data. No record format changes: the cut deletes readers and adds no new writer, so a repo that reverts its upgrade can still use v1.2.40. Each part reverts with its pull request. In Forge's own repo, a revert brings back the deleted tests and code.

What a repo can lose, in plain words:
- A repo on a release older than v1.2.40 stops working with the new release installed, until it upgrades. The recovery: install v1.2.40, run the upgrade to v1.2.40 (v1.2.40 upgrades from any older release), then upgrade to the newest. The refusal line names the first step.
- A laptop with two repos on two releases: the repo on the older release stops until it upgrades. Today Forge runs the older release for it through uv.
- A team in the middle of a story when it upgrades: while the upgrade waits for its merge, commands on other branches stop and say to merge the upgrade first. After the merge, each branch takes the new release from the default branch (the worker does this when it starts). Where a person merges by hand, this adds one wait between the upgrade and other work.
- A repo cannot go back to the old release per branch. To leave the new release, revert the upgrade's pull request and install v1.2.40 again.
- Gap: the v1.2.40 upgrade command is already published and does not know the new one-step rule. A repo on a release older than v1.2.40 can use it to jump straight to the release with the cut. That repo then misses the old chat moves, and its old worker chats on that laptop start again. In practice only the client repo in daily use upgrades, and it will be on v1.2.40 first. A guard would need a check in sync (about 15 lines); this plan adds none.
- Fewer tests: a rule that behaves differently on a repo that came from an older release is no longer tested there. After the cut, no such repo can run the new release.
- Releases wait: from the first merged part until the client repo is on v1.2.40, Forge publishes no release.

### Decisions

- **The release before.** `src/forge/__init__.py` gets `PREVIOUS = "1.2.39"` beside `__version__`, with the comment `# The release this one upgrades from; the release fix moves it with __version__.` It is the release just before the current `__version__` (1.2.40). The release fix that makes v1.2.41 sets `__version__ = "1.2.41"` and `PREVIOUS = "1.2.40"`. `tests/test_release_version.py::test_1` asserts `PREVIOUS`, so a release fix that forgets it fails. `docs/guide.md` "Releasing Forge" step 1 says to set both. Why a constant: comparing version numbers cannot know that v1.3.0 follows v1.2.45, and a GitHub read needs a network and fails offline; the constant is always right once the release test passes.
- **The check (Done-when 1).** `cli._run` calls `repo.check_pin` for every command except `upgrade`, `init`, `migrate`, `lanes`, `stop` and every `hook ...` command. `lanes` and `stop` serve the whole laptop (the pane calls `forge lanes --json` from any folder); hooks keep running as today, so git and the host never block on a pin. `repo.check_pin` keeps its first steps (no `forge.toml`, pin equal to the installed release, the `task start` case, the waiting-upgrade case on the default branch, `pin_elsewhere`). Then, with `pinned` the checkout's pin, `landed` the fetched default branch's pin and `installed` the installed release:
  1. `pinned` newer than `installed`: refuse `pin` (unchanged text, `repo.py:53-56`).
  2. `pinned` equals `PREVIOUS`, `landed` equals `installed`, and the checkout is not the default branch: refuse `branch_older`.
  3. `pinned` equals `PREVIOUS`: refuse `older`.
  4. Otherwise (`pinned` older than `PREVIOUS`): refuse `too_old`.
  The uv path (`:1005-1013`) goes. `resume_pin` keeps its name and callers; when the new pin is neither the old one nor `installed`, it refuses `pin` with the new pin, instead of running it. `githooks.py:139-145` does the same. `run_release` stays only for `upgrade`.
- **Exact lines** (`{installed}`, `{pinned}`, `{previous}` with their `v`):
  - `older`: `This repo pins Forge {pinned}, and Forge {installed} runs only in repos on {installed}.` Next: `forge upgrade`
  - `branch_older`: `This branch pins Forge {pinned}, but the default branch pins {installed}.` Next: `forge work {item}` when the branch holds a task or fix (`task.branch_item`), else `git merge origin/{default}, then run the command again`.
  - `too_old`: `This repo pins Forge {pinned}, and Forge {installed} upgrades only from {previous}, so upgrade through each release in order.` Next: `uv tool install --force git+https://github.com/knacklabs/symphony-forge@{previous}, then forge upgrade {previous}`
- **The upgrade (Done-when 2).** In `upgrade.upgrade`, after the release is known and the `running` check: when the target is not the installed release, install it (the existing `INSTALL` and `_on_path` steps, moved before the fix starts), print `Installed Forge {release}.` and `The forge on your PATH is Forge {release}.`, then `Forge {release} continues the upgrade.`, and return the exit code of `forge upgrade {release}` run from PATH in the main checkout. Nothing else happens in this process, so the target release's own rules decide. When the target is the installed release: `not_newer` as today when the default branch pins it or a newer one; refuse `too_old` when the default branch pins a release other than `PREVIOUS`; otherwise steps 1 to 8 as today, with the install skipped. The `listing` text of `upgrade` in `COMMANDS` adds "from the release just before"; `forge sync` writes it to `docs/commands.md`. The first upgrade to the release with the cut is run by v1.2.40's own command (install, then that release's sync and close through uv); it does not pass this check (see Risks).
- **forge migrate (Done-when 3).** `migrate.migrate` prints, as its first line on every run, also with `--dry-run`: `forge migrate goes away in the next Forge release. Run it in this release if this repo still has a copied-in Forge.` `migrate-skill.md` step 1 gets the same sentence.
- **Guides in REFUSE.** `skill.md`: "Upgrade Forge" (`:1458-1515`): the one-step rule, the three lines and their next steps, the hand-off to the installed release; delete the uvx paragraph (`:1508-1513`) and the sentence that older branches keep their pinned release. New and existing repos: both get the rule from the installed release; the guide text reaches existing repos on sync.

  - `:111` becomes: "Every change says what a new client repo and an existing client repo each get. An existing client repo is always on the release just before the newest one, because Forge refuses older pins."
